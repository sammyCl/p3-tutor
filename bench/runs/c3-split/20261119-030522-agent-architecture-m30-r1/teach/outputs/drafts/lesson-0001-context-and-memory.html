Context and memory: what an agent sees, keeps and looks up

By the end of this lesson you can decide, for the makerspace assistant, what goes in the model's context on each step, what gets saved between visits, and how it finds the right page in a long manual.

Warm-up 2 min

Before new material, pull something out of memory. Answer in your head or on paper first.

Recall

In the agent loop, who actually runs a tool such as "check the booking calendar": the model or your program? And is each trip around the loop one model call or one long call?

Check your answer

Your program runs the tool. The model only writes a request for it. Each trip around the loop is a separate model call. That second fact matters today: if every step is a separate call, then the model cannot be carrying anything over from the last step by itself. Something has to hand it the past each time.

The window is all the model sees 5 min

Start with the big picture. A model does not remember anything between calls. Everything it knows about your request, it reads fresh from the text you send it that time. That text has a name.

The context window is all the text a model can look at when it writes a response, including the response itself. Anthropic's documentation calls it the model's "working memory", and separates it from the training data the model learned from (Anthropic, Context windows). If you know operating systems, think of RAM: fast, small, and wiped when the program ends.

The window is measured in tokens, the small pieces of text a model reads and writes, roughly a short word or part of a word. Your earlier lesson said a model writes one token at a time; the window limit counts the tokens going in and the tokens coming out.

What is inside it? Everything in the request counts: the system prompt (your standing instructions), every message so far, including tool results, and the tool definitions (Anthropic, Context windows). Each turn, the input contains all previous history plus the new message. Your program builds that list and sends it again, in full, every call.

A common mix-up

"The model remembers our chat." It feels true because chat apps show a continuous conversation. But the continuity is your program re-sending the history. If the program sent only the latest message, the model would answer as if it had never met you. This is why "memory" in an agent is a design job: you choose what gets re-sent.

Check yourself

The assistant answers a student's second question in a chat, and it refers correctly to the first question. What made that possible?

Show the answer

The third option. The program re-sent the earlier messages with the new one. The model keeps nothing between calls on its own, and training data cannot hold a conversation that had not happened yet.

Why a full window costs you twice 5 min

If the whole history is re-sent each call, you might ask: why not give the model everything, always? Because a large window costs you in two ways: money and quality.

Cost grows every step

You pay by tokens, and the input is re-sent on each call. In an agent, one request may take five model calls. Call 5 re-sends everything from calls 1 to 4, plus the tool results. So a long manual page returned in step 1 is paid for again in every later step of that request. Under a small budget, this is the part that bites. (Prompt caching can lower the price of repeated text, but cached tokens still take up room in the window, per Anthropic, Context windows.)

Quality can drop as it fills

Anthropic's guide describes context rot: as the number of tokens in the window grows, the model's ability to recall information from it decreases. It treats the window as an "attention budget" that every added token uses up (Anthropic, Effective context engineering for AI agents). The Context windows page agrees that more context is not automatically better, and that curating what is in the window matters as much as how much room there is.

An independent, peer-reviewed study found something specific. When a model had to find a relevant passage in a long input, accuracy was highest when the passage was at the start or the end, and fell when it sat in the middle (Liu et al., Lost in the Middle). So pasting a whole 200-page manual into the window is both expensive and risky.

The goal, in Anthropic's words, is the smallest set of high-signal tokens that gets the job done. Keep that sentence in mind: it is the rule behind the rest of this lesson.

A common mix-up

"A bigger window means I can skip the design work." It is tempting because a window of a million tokens sounds like it fits every manual you own. Fitting is not the same as using well: you still pay for every token on every call, and the evidence above says recall gets worse in the middle of long inputs.

Keeping a long task alive 5 min

So what is kept between steps of one task? By default, all of it: the history only grows. That is fine for a three-step booking. It is a problem for a long task, such as a session where a student works through a whole safety checklist. Two fixes exist, and both give something up.

  • Clear old tool results. Once the model has used a calendar lookup or a manual page, the raw result can be dropped from later calls. Anthropic describes this as a light-touch first move (Anthropic, Effective context engineering), and its platform offers it as "tool result clearing" (Context windows).
  • Compaction. Compaction means that when the conversation nears the limit, the agent summarizes it and starts a fresh window that holds the summary. You give up detail; you keep the thread.

Both are lossy. A summary might drop the one detail you later need, such as "this student said they are left-handed", so what you keep in a summary is a design decision, not an automatic one.

Some chat products simply drop the oldest messages once the window is full ("first in, first out"). That is simple, but the dropped part is gone, including the original instructions of the task if you are not careful.
Check yourself

Which trade-off does compaction make?

Show the answer

The third option. A summary is smaller, so it costs less and leaves room, but anything the summary leaves out is no longer visible to the model.

Notes that outlive the session 5 min

When the session ends, the window is gone. The next visit starts empty. To remember a student's training status on Monday that was recorded last Thursday, you need storage outside the window: memory in the real sense. The simplest form is notes.

Notes as memory means the agent writes facts to a file or database outside the window, and a later session reads them back. Anthropic calls this structured note-taking: the agent regularly writes notes persisted outside the context window, and pulls them back in later (Anthropic, Effective context engineering). The DeepLearning.AI and Letta course uses the operating-system picture: a small in-context memory like RAM, and a larger store outside it like a disk, with the agent editing its saved facts (Letta course).

Who does the saving? In Anthropic's memory tool, the model asks for file operations such as view, create and edit, and your application carries them out against storage you control, such as a folder per user (Anthropic, Memory tool). That is the agent loop you already know, applied to memory: the model requests, the program acts, the result goes back.

You can also skip the model for some memory. A training status is a fixed fact. Your program can look it up by student ID and put one line in the window at the start of the session. That is cheaper and more reliable than hoping the model asks for it.

A common mix-up

"Saving everything is safest." It is tempting, but notes you read back are re-sent into the window and cost tokens every call. Save the few facts a future session needs, such as training status and open bookings, not whole transcripts. Treat what is stored as data to check, too: the memory tool's documentation recommends validating file paths and limiting sizes (Memory tool).

Show the answer

The third option. Facts that must survive a session belong in storage outside the window, found by a student ID. The window ends with the session, and the manual index is shared, not personal.

Finding the right manual page 6 min

The other kind of memory is a large, shared body of text: the machine manuals. They are too long to put in every call, so you do not. You fetch the few pieces that match the question. This is retrieval: searching a stored collection at question time and putting only the best matches into the window.

The standard recipe, from LangChain's RAG tutorial, has two phases (LangChain, Build a RAG agent):

  • Ahead of time: load the documents, split them into chunks (small pieces; the tutorial uses about 1,000 characters with 200 overlapping so a sentence is not cut off from its neighbor), and store them with an index that supports searching by meaning, called embeddings in a vector store.
  • At question time: search the index with the question, take the best few chunks, and put them in the prompt for the model to answer from.

Retrieval-augmented generation, or RAG, is the name for answering with retrieved text added to the prompt.

This is exactly why retrieval fits your budget and the evidence from earlier: the window carries a few hundred relevant words instead of a whole manual, which costs less on every call and avoids the middle-of-a-long-input problem.

The same tutorial separates two designs. In a fixed pipeline, your code always retrieves once, then answers. In an agentic setup, retrieval is a tool the model can call, so it decides whether and what to search, possibly several times (LangChain). Anthropic calls a related habit just-in-time retrieval: keep lightweight references such as file paths, and load the content with tools only when needed (Effective context engineering). The fixed pipeline is cheaper and predictable. The agentic form handles questions that need two lookups, such as "compare the bandsaw and scroll saw speeds."

A common mix-up

"Retrieval makes the model learn the manuals." It does not change the model at all. The chunks are pasted into this one call's window and are gone from it afterward, unless the program puts them in again. If the search returns the wrong chunk, the model answers from the wrong text, so search quality is part of answer quality.

Check yourself

A student asks about the laser cutter's focus setting. In a retrieval design, what goes into the window for that question?

Show the answer

The third option. Retrieval brings in only the best matches. Your manuals are not in the model's training, so without retrieved text it cannot quote them.

Worked example and practice 7 min

Now put the pieces together. Try each step in your head first, then open the answer.

Worked example

A student returns on Monday and asks: "Can I use the bandsaw? And what blade speed for quarter-inch aluminum?" Design what the assistant puts in context, loads, and saves.

Step 1: what facts does this need?

Show the answer

Two facts. Is this student trained on the bandsaw (personal, changes over time)? And the speed advice (shared, written in the manual). Different facts, different homes.

Step 2: where does the training status come from?

Show the answer

From notes outside the window. At session start, the program looks up the student's record by ID and puts one line in the context, such as "bandsaw: trained Oct 3". No model call is needed for this lookup.

Step 3: how is the speed advice found?

Show the answer

By retrieval. Search the indexed bandsaw manual with the question and take the best 3 chunks. The window holds those chunks, not the manual.

Step 4: what is in the window for the first call?

Show the answer

The system prompt and tool descriptions, the training line, the question, and the 3 chunks. Nothing else, which keeps the input small and every token useful.

Step 5: what gets saved when the visit ends?

Show the answer

Only what a future visit needs: any new training completed and any booking made. The full transcript is not saved, because reading it back would cost tokens on every later visit.

Your turn

A different student asks: "Book the 3D printer for Thursday afternoon, and remind me how to change the filament." Work through the same five questions. Step 1 is given: the facts are the student's printer training status, the calendar, and the filament steps in the manual. Decide steps 2 to 5 yourself: where each fact comes from, what is in the window, and what is saved.

Show a solution

Step 2: training status is looked up by student ID from notes, as one line in the window. The calendar is a tool call (check, then book), whose results enter the window.

Step 3: filament steps are retrieved: search the printer manual and take the best chunks.

Step 4: the window holds the system prompt and tools, the training line, the question, the filament chunks, and then the calendar result once it returns. After booking, that calendar result can be cleared from later calls if the task runs long.

Step 5: save the new booking and nothing else about this chat.

Summary 2 min

  • The context window is everything the model sees on one call. The model keeps nothing between calls; your program re-sends the history.
  • A full window costs money on every call and can hurt recall, so aim for the smallest set of useful tokens.
  • Between steps, you can clear old tool results or compact the history, and both lose some detail.
  • Between sessions, memory is storage outside the window: notes you write, then read back.
  • For long manuals, retrieval puts only the best few chunks in the window.
