Context and memory: what an agent sees, keeps and looks up

By the end of this lesson you can decide, for the makerspace assistant, what goes in the model's context on each step, what gets saved between visits, and how it finds the right page in a long manual.

Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, on a small model budget. Every choice in this lesson changes what a request costs and whether the answer is right, and you will have to defend those choices at your design review.

Warm-up 1 min

Before new material, pull something out of memory. Answer in your head or on paper first.

Recall

In the agent loop, who actually runs a tool such as "check the booking calendar": the model or your program? And is each trip around the loop one model call or one long call?

Check your answer

Your program runs the tool. The model only writes a request for it. Each trip around the loop is a separate model call. That second fact matters today: if every step is a separate call, then the model cannot be carrying anything over from the last step by itself. Something has to hand it the past each time. For your assistant, that something is the code you write.

The window is all the model sees 4 min

Start with the big picture. A model does not remember anything between calls. Everything it knows about your request, it reads fresh from the text you send it that time. That text has a name.

The context window is all the text a model can look at when it writes a response, including the response itself. Anthropic's documentation calls it the model's "working memory", and separates it from the training data the model learned from (Anthropic, Context windows). Think of it as the model's desk: small, and cleared and rebuilt for every call. Unlike a program's memory, nothing on it carries over by itself.

The window is measured in tokens, the small pieces of text a model reads and writes, roughly a short word or part of a word ("bandsaw" is probably two or three). Your earlier lesson said a model writes one token at a time; the window limit counts the tokens going in and the tokens coming out.

What is inside it? Everything in the request counts (Anthropic, Context windows):

  • the system prompt, your standing instructions to the model;
  • the tool definitions, text telling the model each tool's name and what it does, such as "check_calendar: looks up free time slots";
  • every message so far, including the results that tools returned;
  • the model's own reply, as it is written.

Your program builds that list and sends it again, in full, on every call. For your assistant, this means the manual text and the student's training status reach the model only if your code puts them in that call.

A common mix-up

"The model remembers our chat." It feels true because chat apps show a continuous conversation. But the continuity is your program re-sending the history. This is why "memory" in an agent is a design job: you choose what gets re-sent.

Check yourself

The assistant answers a student's second question in a chat, and it refers correctly to the first question. What made that possible?

Show the answer

The third option. The program re-sent the earlier messages with the new one. The model keeps nothing between calls on its own, and training data cannot hold a conversation that had not happened yet.

Why a full window costs you twice 4 min

If the whole history is re-sent each call, you might ask: why not give the model everything, always? Because a large window costs you in two ways: money and quality.

Cost grows every step

You pay by tokens, and the input is re-sent on each call. In an agent, one request may take five model calls. Call 5 re-sends everything from calls 1 to 4, plus the tool results. So a long manual page returned in step 1 is paid for again in every later step of that request. Under a small budget, this is the part that bites.

One tool softens it: prompt caching, where the provider charges less for a repeated start of the prompt, such as the system prompt and tool definitions you send on every call. It lowers the price, but cached tokens still take up room in the window (Anthropic, Context windows), so it does not fix a window that is too full.

A rough picture, with made-up numbers: say the system prompt and tool definitions are 1,000 tokens, and each step adds 500 tokens of new text. Call 1 sends about 1,500 tokens. Call 2 sends about 2,000. Call 5 sends about 3,500. Add them up and the five calls send about 12,500 input tokens, even though only 3,500 distinct tokens were ever written. The bill follows the sum, not the last window. That is why a request with many steps costs far more than the same text sent once.

Quality can drop as it fills

Anthropic's guide describes context rot: as the number of tokens in the window grows, the model's ability to recall information from it decreases. It treats the window as an "attention budget" that every added token uses up, meaning the model's focus is spread thinner with each token added (Anthropic, Effective context engineering for AI agents). The Context windows page agrees that more context is not automatically better, and that curating what is in the window matters as much as how much room there is.

An independent, peer-reviewed study from 2023 found something specific. When a model had to find a relevant passage in a long input, accuracy was often highest when the passage was at the start or the end, and fell when it sat in the middle (Liu et al., Lost in the Middle). It tested the models of that time, so treat it as a warning, not a measurement of today's models. A window of a million tokens may fit every manual you own, but fitting is not using well: you pay for every token on every call, and recall may weaken. Pasting a whole 200-page manual in is expensive and risky.

The goal, in Anthropic's words, is the smallest set of high-signal tokens that gets the job done. Keep that sentence in mind: it is the rule behind the rest of this lesson.

Keeping a long task alive 5 min

So what is kept between steps of one task? By default, all of it: the history only grows. That is fine for a three-step booking. It is a problem for a long task, such as a visit where a student asks ten manual questions in a row. Each answer needs a manual page, and every page stays in the window. Two fixes exist, and both give something up.

  • Clear old tool results. Once the model has used a calendar lookup or a manual page, the raw result can be dropped from later calls. Anthropic calls it one of the safest, lightest-touch forms of compaction (Anthropic, Effective context engineering), and its platform offers it as "tool result clearing" (Context windows).
  • Compaction. Compaction means that when the conversation nears the limit, the agent summarizes it and starts a fresh window that holds the summary. You give up detail; you keep the thread.

Both are lossy, meaning they lose some detail. A summary might drop the one detail you later need, such as "this student said they are left-handed", so what you keep in a summary is a design decision, not an automatic one.

Example: ten laser cutter questions in one visit

A new student asks ten questions about the laser cutter, and each answer used one manual page returned by a tool. By question 8 the window holds seven pages plus every answer. Here is how each choice behaves, with the shape of the numbers, not real ones.

  • Do nothing. Question 8's call re-sends all seven earlier pages. Most are no longer needed, but you pay for them on every later call, and the window is closer to its limit.
  • Clear old tool results. The program drops the raw pages for questions 1 to 6 but keeps the student's questions and the model's replies. Cost per call falls, and the thread survives. What is lost: if the student asks "what did the manual say about question 3?", the page is gone and must be fetched again.
  • Compact. The agent writes a summary such as "Questions 1 to 7 answered; student is left-handed; booking pending for Friday." A fresh window starts from that summary. What is lost: anything the summary left out, such as the exact wording of a warning.

How to choose: clearing is gentler, because only text you can fetch again is dropped. Compaction is for when clearing is not enough. In both cases, anything that must outlive the visit, like "booking pending for Friday", should also be saved as a note, which is the next section.

Check yourself

A student has asked ten questions and now says, "Go back to what the manual said for question 3." You cleared old tool results earlier. What does that choice cost you now?

Show the answer

The second option. Clearing drops the raw page but keeps the questions and replies, so the cost is one more fetch. Compaction would be the choice that risks a detail being left out of a summary, and neither fix saves anything beyond the visit: that is the job of notes.

Notes that outlive the session 4 min

When the session ends, the window is gone, and the next visit starts empty. Suppose a staff member signed a student off on the laser cutter last Thursday. On Monday the assistant must still know it. That needs storage outside the window, which is memory in the lasting sense.

The simplest form is notes as memory: facts written to a file or database outside the window, which a later session reads back. Anthropic calls this structured note-taking: the agent regularly writes notes persisted outside the context window, and reloads them later (Anthropic, Effective context engineering). The DeepLearning.AI and Letta course pictures a small in-context memory and a larger store outside it, with the agent editing its saved facts (Letta course).

Who does the saving? In Anthropic's memory tool, the model asks for file operations such as view, create and edit, and your application carries them out against storage you control, such as a folder per user (Anthropic, Memory tool). That is the agent loop you already know, applied to memory: the model requests, the program acts, the result goes back.

A note is only useful if it is easy to read back. Keep each student's record short, one line per fact with a date: "laser cutter: trained 2026-10-03" and "booking: 3D printer, Thursday 2 pm". A short record loads in a few dozen tokens; a pile of chat logs would load thousands.

Two ways to read a note, and when to use each:

  • Program lookup. For a fixed fact like training status, your program finds the record by student ID, which is a unique key for that student's file, and puts one line in the window. It is cheaper and more reliable than hoping the model asks.
  • Memory tool. Use it when the model should decide what to write down, such as a preference the student mentions.

One catch: a fact copied into the window goes stale if the stored version changes mid-visit. For a fact that gates an action, such as "may use the bandsaw", read the stored record at the moment of the action, for instance with a lookup tool. You will use this in the practice.

A common mix-up

"Saving everything is safest." It is tempting, but notes you read back are re-sent into the window and cost tokens every call. Save the few facts a future session needs, such as training status and open bookings, not whole transcripts. Treat what is stored as data to check, too: the memory tool's documentation recommends validating file paths and limiting sizes (Memory tool).

The third option. Facts that must survive a session belong in storage outside the window, found by a student ID. The window ends with the session, and the manual index is shared, not personal.

Finding the right manual page 7 min

The other kind of memory is a large, shared body of text: the machine manuals. They are too long to put in every call, so you do not. You fetch the few pieces that match the question. This is retrieval: searching a stored collection at question time and putting only the best matches into the window.

The standard recipe, from LangChain's RAG tutorial, has two phases (LangChain, Build a RAG agent):

  • Ahead of time, step 1: load the documents and split them into chunks, small pieces. The tutorial uses about 1,000 characters per chunk, with 200 overlapping so a sentence is not cut off from its neighbor.
  • Ahead of time, step 2: turn each chunk into an embedding, a list of numbers that captures its meaning, so similar meanings get similar numbers. Keep the chunks and their embeddings in a vector store, a database that can search by similarity. Meaning-based search helps because a student may write "how fast to cut metal" while the manual says "blade speed, non-ferrous"; a plain keyword search would miss it.
  • At question time: search the store with the question, take the best few chunks, and put them in the prompt for the model to answer from.

Retrieval-augmented generation, or RAG, is the name for answering with retrieved text added to the prompt.

This is exactly why retrieval fits your budget and the evidence from earlier: the window carries a few hundred relevant words instead of a whole manual, which costs less on every call and avoids the middle-of-a-long-input problem.

Example: one bandsaw passage, chunked

Imagine the bandsaw manual has a section on blade speed with three parts: a table of speeds by material, a warning about cutting aluminum without lubricant, and a paragraph on changing the belt. A chunker cuts the text every so many characters, with some overlap. This is an illustration; real manuals are messier.

  • Chunk A: the end of the safety section, then the start of the speed table.
  • Chunk B: the rest of the speed table, then the start of the aluminum warning. The overlap means the sentence that introduces the warning is in both chunks, so it is not cut in half.
  • Chunk C: the rest of the warning, then the belt paragraph.

A student asks, "What blade speed for quarter-inch aluminum?"

  1. The search ranks the chunks by how close their meaning is to the question.
  2. Chunk B ranks first, because it holds the aluminum row of the table and the aluminum warning. Chunk A ranks second. Chunk C, about belts, ranks last.
  3. In this tiny manual the program takes the top two, so the window gets B and A plus the question, and C stays out. A real manual has hundreds of chunks, and the top few are a small slice of it.

What goes wrong with size:

  • Chunks too large: each one drags in unrelated text, so you pay for tokens you did not need and the useful sentence is diluted.
  • Chunks too small: a chunk can hold the warning without the table, and the model answers from half a fact.

There is no universal size. The tutorial's 1,000 characters with 200 overlap is a starting point to test on your own manuals, by asking real student questions and reading which chunks come back.

The tutorial describes a two-step retrieve-then-answer flow, and also shows retrieval as a tool an agent can call (LangChain). Which to use is the workflow-versus-agent question, a later lesson. One more option, just-in-time retrieval, keeps lightweight references such as file names and loads a file only when needed (Effective context engineering); it suits a few well-named files, such as one manual per machine, while a chunk index suits long manuals.

A common mix-up

"Retrieval makes the model learn the manuals." It does not change the model at all. The chunks are pasted into this one call's window and are gone from it afterward, unless the program puts them in again. If the search returns the wrong chunk, the model answers from the wrong text, so search quality is part of answer quality.

Worked example and practice 6 min

Now put the pieces together. Try each step in your head first, then open the answer.

Worked example

A student returns on Monday and asks: "Can I use the bandsaw? And what blade speed for quarter-inch aluminum?" Design what the assistant puts in context, loads, and saves.

Step 1: what facts does this need?

Show the answer

Two facts. Is this student trained on the bandsaw (personal, changes over time)? And the speed advice (shared, written in the manual). Different facts, different homes.

Step 2: where does the training status come from?

Show the answer

From notes outside the window. At session start, the program looks up the student's record by ID and puts one line in the context, such as "bandsaw: trained Oct 3". No model call is needed for this lookup.

Step 3: how is the speed advice found?

Show the answer

By retrieval. Search the indexed bandsaw manual with the question and take the best few chunks. The window holds those chunks, not the manual.

Step 4: what is in the window for the first call?

Show the answer

The system prompt and tool definitions, the training line, the question, and the retrieved chunks. Nothing else, which keeps the input small and every token useful.

Step 5: what gets saved when the visit ends?

Show the answer

Only what a future visit needs: any new training completed and any booking made. The full transcript is not saved, because reading it back would cost tokens on every later visit.

Notice the pattern behind all five steps: ask which kind of fact it is, then pick its home. Personal and lasting means notes. Shared and long means retrieval. Needed only for this step means the window, and it can be cleared later. Changing this sorting is the main way to move your cost up or down.

A second case: the fact changes mid-visit

Midway through a visit, a staff member signs the student off on the bandsaw, so the training status changes from "not trained" to "trained". The assistant already put "bandsaw: not trained" in the window at the start. The student asks to book the bandsaw now. Which version of the status does the model act on, and what should the program do? Think first.

Show the answer

The model acts on what is in its window, which still says "not trained". It cannot notice that the stored record changed. The program should:

  • write the new status to the stored notes, so the next visit sees it;
  • update the line in the next call's window, or let the model call a lookup tool right before booking;
  • follow the rule: for a fact that gates an action, read the stored record at the moment of the action.
Your turn

A different student asks: "Book the 3D printer for Thursday afternoon, and remind me how to change the filament." Work through the same five questions. Step 1 is given: the facts are the student's printer training status, the calendar, and the filament steps in the manual. Step 2 hint: one of these three facts is personal and lasting. Decide the rest yourself: where each fact comes from, what is in the window, and what is saved.

Then add two things for your design review. Give one reason for each placement, and compare roughly what you send against pasting the whole printer manual into the call. Last, suppose this visit runs twenty steps: what would you clear, and what would you keep?

Show a solution

Step 2: training status is looked up by student ID from notes, as one line in the window. The calendar is a tool call (check, then book), whose results enter the window.

Step 3: filament steps are retrieved: search the printer manual and take the best chunks.

Step 4: the window holds the system prompt and tools, the training line, the question, the filament chunks, and then the calendar result once it returns. After booking, that calendar result can be cleared from later calls if the task runs long.

Step 5: save the new booking and nothing else about this chat.

Reasons and cost: status is personal and lasting, so notes; the manual is shared and long, so retrieval; the calendar result matters only for this step, so the window. A few retrieved chunks cost a few hundred words per call, while the whole manual would cost thousands of tokens on every call of the request.

Twenty steps: clear the old raw calendar and manual results, which can be fetched again; keep the question, the replies and the training line; save the booking as a note before the visit ends.

Summary 1 min

  • The context window is everything the model sees on one call. The model keeps nothing between calls; your program re-sends the history.
  • A full window costs money on every call and can hurt recall, so aim for the smallest set of useful tokens.
  • Between steps, you can clear old tool results or compact the history, and both lose some detail.
  • Between sessions, memory is storage outside the window: notes you write, then read back.
  • For long manuals, retrieval puts only the best few chunks in the window.
