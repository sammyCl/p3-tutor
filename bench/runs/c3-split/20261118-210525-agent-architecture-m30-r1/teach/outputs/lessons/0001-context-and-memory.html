Context and memory: what the assistant sees, keeps and looks up

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context, in saved notes, or in a searchable index of the manuals, and give a reason.

Why this matters for you

The context window as the model's whole desk 3 min

Picture a desk. When a student asks your assistant a question, the model can only work with what you have put on the desk for this call. Between calls it keeps no conversation state, so the only conversation it can see is the text you send, plus whatever it learned in training. That desk has a name: the context window is all the text the model can reference when it writes a response, including the response itself. Anthropic's docs call it the model's "working memory" (Anthropic, Context windows).

The desk is measured in tokens, small chunks of text a model reads and writes, often a whole short word or a piece of a longer one: "laser" might be one token and "cutter" another. The window's size is counted in tokens, and so is your bill. That is why this lesson is about cost as well as correctness.

What lands on the desk? The docs list everything that counts (Anthropic, Context windows):

  • The system prompt: standing instructions you write, such as "You are the makerspace assistant."
  • The tool definitions: the list of tools you send, each with a name, a description and its inputs, so the model knows what it can ask for.
  • Every message so far, including tool results.
  • The reply the model is writing.

For your assistant, every rule, tool and manual page you add to the desk is a cost paid on every call, so what goes in the window is a budget decision.

Check yourself

A student's question is 20 tokens. Your system prompt and three tool definitions are 1,500 tokens. Roughly how much of the context window does this first call use?

Show the answer

About 1,520 tokens plus the reply. The system prompt and tool definitions are part of the request, so they count every time.

What the loop carries from step to step 6 min

Now connect this to the loop you know. Each pass through the loop is a separate model call, and the model does not keep anything from the last one. So your program resends the conversation each time. In the docs' words, each turn's input holds "all previous conversation history plus the current user message", and the reply then becomes part of the input for the next turn (Anthropic, Context windows).

In computer science terms, the model is a stateless function (same input in, nothing remembered from the last call), and the history is state your program holds and passes in as an argument. Here is one request, step by step:

  • Call 1 sends: rules, tools, the question.
  • The model replies with a request for the calendar tool.
  • Your program runs the tool and appends both the request and the result to the history.
  • Call 2 sends: rules, tools, the question, the tool request, the calendar result.
  • The model writes the final answer.

Call 2 is bigger than call 1. A request with ten tool steps makes eleven calls, so the early material is sent eleven times.

A common mix-up

"The model remembers what it did earlier in the request." It is tempting because the final answer reads as if it did. It is not true: the model only appears to remember because your program sent the earlier steps again. Drop a step from the history and, for the model, it never happened.

This gives you a cost rule for your budget: a long tool result stays in the history and is paid for again on every later call of that request. One 3,000-token manual page returned at step 1 is 3,000 more input tokens on each of the next calls.

There is a discount for resent text, called prompt caching, but those tokens still fill the window: it "changes what you pay for those tokens, not whether they count" (Anthropic, Context windows).
Worked example: the token tally

Use round numbers. System prompt plus tool definitions: 1,500 tokens. The question: 20. A manual page returned by a tool after call 1: 3,000. Each model reply that asks for a tool: 50. Each small tool result after that (calendar, booking): 100. The request takes four calls. How many input tokens do you pay for in total?

Step 1: what does call 1 send?

Show

1,500 + 20 = 1,520 tokens. Nothing else exists yet.

Step 2: what does call 2 send?

Show

Call 1's input, plus the model's tool request, plus the page: 1,520 + 50 + 3,000 = 4,570.

Step 3: what do calls 3 and 4 send, and what is the total?

Show

Each adds a 50-token request and a 100-token result to the one before: call 3 is 4,720, call 4 is 4,870. Total: 1,520 + 4,570 + 4,720 + 4,870 = 15,680 tokens. The page alone is 3,000 × 3 = 9,000 of them.

Step 4: what changes if you clear the page after call 2?

Show

Calls 3 and 4 drop 3,000 each, to 1,720 and 1,870. The total falls to 9,680, a saving of 6,000 tokens. The price is that the model can no longer see the page, so clear it only once it has been used. The next section gives this trick its name.

Show the answer

Three times. The page enters the history after call 1, then rides along on calls 2, 3 and 4.

When more context makes things worse 3 min

It is tempting to think a bigger window solves everything: paste in all the manuals. Two problems say no. The first is cost, which you just saw. The second is quality: the docs say that "more context isn't automatically better", because as the token count grows, accuracy and recall degrade, an effect called context rot. So "curating what's in context" matters as much as how much space you have (Anthropic, Context windows).

If a long task fills the window anyway, the docs describe two tools:

  • Clearing old tool results: remove bulky results that are no longer needed, such as a manual page you already used.
  • Compaction: summarize the earlier conversation so the task can continue in less space.

Both of these are trade-offs: you free space and lose detail. A rule of thumb: clear when the bulk is a finished tool result, like a manual page you have used; compact when the conversation itself has grown long; and save to notes anything you cannot afford to lose. That last case leads to the next section. The memory tool docs say it directly, for long agents: "compaction keeps the active context small... and memory preserves the information that must survive summarization" (Anthropic, Memory tool).

Token counting is available before you send a request, so you can measure a request's size in code and decide what to trim, rather than guessing (Anthropic, Context windows).
Try it

A student's chat has run long: six pasted manual pages and a lot of back-and-forth, and the student has just said their training status changed. Which do you do with the pages, with the chat, and with the status change: clear, compact or save to notes?

Check your answer

Clear the six pages (finished tool results). Compact the long chat if it still grows. Save the status change to notes, because it must survive both and the next visit.

Think it through

A teammate says: "Our sponsor's budget is small, but the window is huge, so let's put all 40 machine manuals in the system prompt." Give two reasons this is a poor design before you open the answer.

Check your answer

Cost: all those tokens are sent, and paid for, on every call. Quality: a crowded window can lower accuracy and recall (context rot), so the right page may be less likely to be used. The fix is to put only the relevant page in, which is retrieval, two sections ahead.

Notes that outlive the session 4 min

Everything so far lives only as long as one conversation. When the student leaves and returns next week, the history is gone unless your program saved it. For "remember each student's training status", you need memory between sessions: information stored outside the model, in your own storage, and loaded back into a later context.

The simplest form is notes. Anthropic's memory tool shows the pattern: the model can create, read, update and delete files in a /memories directory that persist between sessions. The tool is client-side: the model only requests a file operation, and your application runs it against storage you control, such as a folder or database, and returns the result in a tool result (Anthropic, Memory tool). That is the same loop you already know, with files as the tool.

Two ideas from the docs are worth keeping:

  • Just-in-time retrieval. Rather than loading all relevant information up front, the agent records what it learns and reads it back on demand, so the active context stays focused. For a three-line student file, loading it all at the start is fine; load on demand once notes grow large (Anthropic, Memory tool).
  • Assume interruption. The docs' own prompt warns that "your context window might be reset at any moment", so progress not written to memory can be lost (Anthropic, Memory tool). For you: write the training status down when it changes, not at the end.

For your assistant, a note might be a small file per student, such as /memories/students/s1234.md:

Laser cutter: training complete (2026-10-02)
3D printers: not trained
Prefers evening slots

At the start of a visit, the assistant views that file and has the student's status in its context for the whole conversation, at a cost of a few dozen tokens.

Notes need housekeeping. The docs advise capping file sizes, expiring files nobody has read in a long time, and validating paths so the model cannot reach files outside /memories (Anthropic, Memory tool). Student records are also personal data, so decide who may see them.
A common mix-up

"A bigger context window is the same as memory." It is not: the window holds only what your program sends in each call, so nothing carries over to a new conversation unless your program saves it and sends it again. The window is the desk; memory is the filing cabinet the desk is stocked from.

Check yourself

A student finishes laser-cutter training today. Where should the assistant record it so it is known at next month's visit?

Show the answer

The student's saved note file. Only stored data survives the end of the session.

Retrieval: fetching one page from a long manual 7 min

Notes work for small, personal facts. A 200-page laser cutter manual is different: too large to load, and the student needs one paragraph of it. Picture a student asking about focal distance: your program finds the one paragraph about focusing and hands only that to the model. That is retrieval: search a store outside the model for the few pieces that match the question, and put only those into the context. The popular name for the pattern is retrieval-augmented generation, or RAG. Pinecone describes it in four stages: ingest, retrieve, augment, generate (Pinecone, Retrieval-Augmented Generation).

  • Ingest (once, ahead of time): split the manuals into chunks, short passages of text, and turn each into an embedding, a list of numbers that places texts with similar meaning near each other: "set the lens height" and "how far should the lens sit" would get nearby numbers. Store them in an index, a searchable collection of the chunks and their embeddings.
  • Retrieve (per question): turn the question into an embedding too, and find the closest chunks.
  • Augment: put those chunks into the prompt.
  • Generate: the model answers using the chunks it was given.

A runnable Python example is in Hugging Face Cookbook, Simple RAG; swap its GitHub issues for manual sections.

In an agent, retrieval is just another tool:

  1. You write a search_manuals(query) tool.
  2. The model calls it with a query.
  3. Your program runs the search and returns the top chunks as a tool result.
  4. The model answers from them.

That is why the "tool results" box in Figure 1 is where retrieved text lands. Letting the model decide when to search is sometimes called agentic RAG, and the DeepLearning.AI memory course has a lesson on it (DeepLearning.AI, LLMs as Operating Systems: Agent Memory). The simpler alternative is to search on every question before the first model call, which wastes a search when the question needs none.

The payoff for your budget: instead of 40 manuals on every call, a call carries a handful of chunks. Cost drops, and the model's attention is on the page that matters.

Chunk size is a trade-off you will tune: too small and a procedure is cut in half, too large and unrelated text costs tokens and buries the useful paragraph. Start with one manual section per chunk and test with real student questions.

The question is turned into an embedding by the same method used on the chunks, and the closest chunks come back, for example the top 4. A good index returns the "Focusing the laser" section first.

Show

Only those chunks, as a tool result, plus the question. If four chunks are 300 tokens each, that is 1,200 tokens instead of a 200-page manual. If they contain the distance, the answer is grounded in the manual.

Step 3: what if the question was worded "how far should the lens sit from the wood?"

Show

Embeddings match meaning, not only exact words, so the focusing section can still rank high. Matching is imperfect, though, which is why you test with real questions and let the model rephrase and search again if the first results look wrong.

A common mix-up

"Retrieval means the model looks it up itself." It is tempting because the answer cites the manual. In fact the search is code your program runs. The model sees only the chunks it is handed, so if the search returns the wrong chunk, the model answers from the wrong page. Retrieval quality limits answer quality.

Check yourself

Show the answer

The answer is built on the wrong page. The model only works from its context, so retrieval quality sets a ceiling on answer quality.

Worked example and your turn 5 min

The test of this lesson is placing information. For each fact, ask: does the model need it right now, in this call (context), after the session ends (notes), or only if the question touches it, out of a large store (retrieval)? A fourth source is a live tool call, such as the calendar, whose answer changes too often to save.

Worked example

A student says: "I finished my laser cutter training last week. Can I book the cutter Friday, and what speed should I use for 3 mm plywood?" Place each piece of information. Try each step before you open it.

Step 1: where does the student's training status live?

Show

In notes. It must survive between visits and is small. At the start of the visit the assistant views the student's file, which puts it into the context for this conversation.

Step 2: where does the Friday calendar come from?

Show

From a tool call. The calendar changes constantly, so a saved copy would go stale. The tool result lands in the context for this request only.

Step 3: where does the plywood speed setting come from?

Show

From retrieval. It is one paragraph in a long manual. A search_manuals call returns a few chunks, and only they enter the context.

Step 4: what stays in the context for the whole request?

Show

The rules, the tool definitions, the question, and each result as it arrives. Because they are resent, keep results short, and clear them once used.

Step 5: what do you save when the visit ends?

Show

Only facts about the student that the next visit needs and nothing else can supply, such as a status change. The booking itself lives in the booking system, so it is not copied into notes. The manual chunks are not saved either: they can be searched again.

Worked example 2: one fact in two places

The assistant retrieves the filament-loading steps for a student. The student says "got it, thanks", and the assistant is about to book a slot. What happens to those steps?

Step 1: are they still needed in the context?

Show

Not once the student has them. They are 1,000 or more tokens that every later call would pay for again. They are a good candidate for clearing.

Step 2: should they be saved in notes?

Show

No. The manual still holds them and can be searched again. Saving a copy would go stale if the manual changes.

Step 3: what is worth saving?

Show

A short fact about the student, such as "has been shown filament loading, 3D printer". It is a few tokens and it is a fact about the student, not the manual.

Show a solution
  1. Retrieval: it is a procedure inside a long manual, so search for the filament section and load only those chunks.
  2. The calendar tool, since availability changes and a saved copy would go stale.
  3. Only a change to the student's status, as a short note, because nothing else can supply it next visit. Not the manual text, the calendar answer or the booking, which live elsewhere and can be fetched again.

Summary 1 min

  • The context window is everything the model sees in one call: rules, tool definitions, history, tool results and the reply. It is the only place the model reads this conversation from, and you pay for it by the token.
  • Between steps, your program resends the history. A tool result keeps costing tokens on every later call, and a crowded window can lower accuracy (context rot).
  • Between sessions, nothing survives unless you save it, for example as notes the model reads and writes through a tool you control.
  • For large stores like manuals, retrieve a few chunks by search and put only those in the context.
