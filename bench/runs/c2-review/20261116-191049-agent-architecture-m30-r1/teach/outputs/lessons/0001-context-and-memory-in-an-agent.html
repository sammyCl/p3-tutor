Context and memory in an agent: what it sees, what it keeps, what it looks up

By the end of this lesson you can look at any piece of information in the makerspace assistant and say where it should live: in the context for this session, in saved notes between visits, or in a manual you search when needed.

Objective O3: context and memory in an agent About 30 minutes Builds on your work on the agent loop
Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training status between visits, all on a small model budget. Both problems are context and memory problems. At your design review you will be asked what the assistant keeps, what it saves and how it finds the right page, and this lesson gives you the answers and the reasons.

Two words used throughout: a session is one student's conversation with the assistant, made of several model calls. A visit is a later session, on another day.

Warm-up 2 min

Before new material, pull something out of memory. Try to answer in your head, then check.

Recall

In the agent loop, a student asks "Is the laser cutter free on Friday?" The model asks for the calendar tool. Who runs that tool, and what happens right after it returns?

Check your answer

For a tool you define yourself, such as the calendar, your program runs it, not the model. The model only writes a request for it. The program puts the result back into the conversation and calls the model again, and that repeats until the model gives a final answer. Today's lesson is about what is inside each of those calls, and what survives after the last one.

What the model sees on every call 6 min

Start with a small example. A student asks the assistant a question and gets an answer. Then the student asks a second question: "And what about 6 mm?" For the model to understand "6 mm", your program must paste the first question and answer in again. The model does not hold the conversation in its head.

Everything you paste in for one call is the context: the text the model reads before it writes (Anthropic, context engineering). It is measured in tokens. A token is a small chunk of text, roughly a word or part of one, so "acrylic" might be one or two tokens.

The context window is the most text the model can look at in one call, including the answer it writes. It works like the model's working memory, and it is separate from what the model learned in training (Claude docs, context windows). For some current models the window is up to 1 million tokens.

Everything the call carries counts toward that window:

  • the system prompt, your standing instructions to the model ("You are the makerspace assistant...");
  • the tool definitions, the descriptions of each tool, such as its name and what inputs it takes;
  • every earlier message in the conversation;
  • every tool result that came back;
  • the answer the model is about to write.

You reach the model through the Messages API, the web API your program calls. That API is stateless by default: you send the full conversation history on every call (Claude docs, Messages API). The service keeps no session for you. The docs also describe a beta feature that keeps the conversation on the server, but this lesson assumes the default.

So between steps, what is "kept" is just a Python list that your program appends to and re-sends:

messages = [{"role": "user", "content": "Is the laser cutter free Friday?"}]
reply = call_model(messages)                      # call 1
messages.append(reply)                            # the model's request for a tool
messages.append(tool_result)                      # your program runs it and adds the result
reply = call_model(messages)                      # call 2 re-sends everything above

For your assistant, this means every step re-sends the system prompt and the tool definitions too, so keep them short.

A common mix-up

"The model remembers what we already said." This is tempting because chat apps feel like a continuing conversation. In fact your program rebuilds the conversation on every call, and the model reads it fresh. Nothing from earlier calls reaches the model unless it is in the text sent this time (what it learned in training aside). This is why each step of the agent loop is a separate model call, and it is the key to everything else in this lesson.

Check yourself

The assistant answers one request in three model calls. How many times is the student's original question sent to the model?

Show the answer

Three times. The API is stateless by default, so every call re-sends the whole history, and the question sits at the top of it each time.

Why a long context costs money and accuracy 3 min

Because every call re-sends the whole stack, a long context hurts you in two ways.

It costs more

You are billed for the tokens you send in and the tokens the model writes. Each call's input includes the full history, so a bulky tool result is paid for again on every later call. The size of the window is a ceiling, not a target.

Here is an illustration with made-up round numbers. Suppose a manual is about 24,000 tokens and a session takes six model calls.

  • Paste the whole manual: 24,000 tokens × 6 calls = 144,000 input tokens.
  • Fetch three relevant passages of about 300 tokens each: 900 × 6 = 5,400 input tokens.

Real prices vary by model, but the ratio is the point, and with a small sponsor budget it decides how many questions you can afford.

It can make answers worse

More text in the window does not mean better answers. As the token count grows, accuracy and recall (how reliably the model finds a fact you put in) degrade, an effect called context rot (Claude docs). Anthropic's engineers describe context as a finite resource with an "attention budget", and say the goal is "the smallest set of high-signal tokens" that gets the result you want (Anthropic, context engineering).

Think of a desk. A bigger desk lets you spread out more paper, but you find things more slowly when the whole pile is on it.

Prompt caching can lower the price of re-sent text, but cached text still occupies the window (Claude docs). It helps the bill, not the crowding.
Apply it

A teammate suggests pasting all of a 24,000-token manual into every session "so the model never misses anything". Give two reasons against, one about money and one about answer quality.

Check your answer

Money: the manual is re-sent and billed on every call of the session, as in the 144,000-versus-5,400 comparison. Quality: context rot, where recall and accuracy drop as the window fills, so the one useful passage can get lost among thousands of irrelevant tokens.

Three ways to keep a long run inside the window 3 min

At your design review, someone will ask what your program drops from the list between calls. This section gives you the rule. A session with many steps can fill the window even when each step is small, so there are three standard moves. You set the trimming rule, either by editing the list yourself or by turning on the API's own trimming features (context editing, compaction, both currently in beta).

  • Clear old tool results. Use it when one big result is finished with. After the assistant has used a 300-line calendar listing to find a free slot, the listing is dead weight. Removing it is one of the "safest lightest touch" forms of compaction, in the source's words (Anthropic, context engineering).
  • Summarize the conversation (compaction). Use it when the whole session has grown long and the early details no longer matter, such as a student who has asked twenty questions in a row. The conversation is replaced by a summary and a new window starts from it. You trade detail for room.
  • Hand a side task to a sub-agent. A sub-agent is a separate agent run, with its own clean window, that does one job and reports back a short summary. We will weigh this properly when we reach multi-agent designs.

Here is clearing on the booking request.

  • Before: question, calendar request, 300-line listing, booking request, confirmation.
  • After: question, calendar request, "[listing cleared]", booking request, confirmation.

A follow-up can still be answered, and the next calls are lighter. A typical makerspace request is only a few steps long, so clearing is probably all you need.

Check yourself

The assistant has just booked a slot. The 300-line calendar listing is still in the history, and the student wants to ask a follow-up about settings. Which is the lightest fix?

Show the answer

Clear the old tool result. It is the lightest touch: only the stale text goes, and the question and the booking stay.

Notes that outlive the session 4 min

Everything so far lives inside one session. When it ends, the list your program built is gone unless you save it. So how does the assistant know on Thursday that a student passed laser-cutter training on Monday?

One answer is to save the whole conversation and reload it. That works, but it is bulky, and most of it is noise. The better answer is memory in the practical sense: short information stored outside the context window that a later session can load. One pattern is structured note-taking: the agent writes notes to storage outside the window and reads them back later (Anthropic, context engineering).

Claude's memory tool is a ready-made interface for this. The model can create, read, update and delete files in a /memories directory, and those files persist between sessions, but you write the handler that stores them (Claude docs, memory tool). It suits notes the model should decide to write itself. You could instead keep training status in your own database, behind a tool you write, which suits records that must be exact and shared with staff. The memory tool process looks like this:

  1. A new session starts. The model first looks in the notes ("view /memories").
  2. Your program runs that request against storage you chose, and returns the file text as a tool result.
  3. The model uses the notes in its answer.
  4. As things change, the model asks to write or edit a note.
  5. The session ends. The context vanishes. The notes remain.

Notice step 2. The memory tool is client-side, meaning your program, not the model's provider, does the work: "Claude requests file operations, and your application runs them" (Claude docs, memory tool). It is the same loop you already know, with files as the tool.

A common mix-up

"The model just remembers students." Chatbots with memory features make this feel true. But if the notes are not written, or not loaded, the Thursday session starts blank.

One design point follows from the docs: because your application runs every file operation, it must reject paths outside /memories. And for a university makerspace, store a student's training status, and not more than you need.

Check yourself

Which of these belongs in saved notes between visits?

Show the answer

The training status. It is a durable fact about one student that no other source holds. Open slots should come from the calendar tool each time, and manual text should come from retrieval.

Retrieval: fetching the right manual page 5 min

When a student asks about acrylic settings, the assistant should pull up the one relevant manual page, not paste all 60 pages. Notes hold small facts the agent wrote itself. The manuals are different: long, written by someone else, and mostly irrelevant to any one question. The tool for them is retrieval: search a large store and put only the best few passages into the context.

Classic retrieval-augmented generation (RAG) does this before the model answers (Anthropic, contextual retrieval). Your assistant can also expose the search as a tool the model calls inside the loop, as Figure 1 showed. The search itself works the same way either way.

A typical setup, built ahead of time and then used on each question:

  1. Chunk. Split each manual into chunks, pieces "usually no more than a few hundred tokens".
  2. Embed. Turn each chunk into an embedding, a list of numbers that captures its meaning, so chunks about similar ideas get similar numbers. For example, "maximum material thickness 6 mm" gets numbers close to those for "how thick can I cut?".
  3. Index. Store the lists in an index, a store built for finding the closest ones quickly. Meaning search then handles paraphrase, but can miss exact matches.
  4. Add exact-word search. BM25 scores chunks by how well they match your exact words, so it suits an error code. It keeps its own word index. Combining both gives more complete results.
  5. Insert. Put the top few chunks into the context, and let the model answer from them.

A starting rule: meaning search suits questions in everyday words, and exact-word search earns its place when users quote codes or part numbers.

Chunks can lose their surroundings: "the limit is 5 mm" does not say which machine. Anthropic's write-up fixes this by adding a short line of context to each chunk before indexing, which cut top-20 retrieval failures from 5.7% to 2.9% in their tests (Anthropic, contextual retrieval). You do not need to build that yet, but chunk quality matters.

When you can skip it

The same write-up says that if the whole knowledge base is under about 200,000 tokens (roughly 500 pages), you may be able to put it all in the prompt and skip retrieval, with prompt caching making that faster and cheaper. Your manuals might fit, so measure them. But the cost comparison from earlier still applies: at six calls per session, retrieving costs about a twenty-sixth as much input (5,400 against 144,000 tokens) and avoids crowding the window. Retrieve unless caching changes that arithmetic for your real manuals.

A common mix-up

"Retrieval and memory are the same thing." Both bring stored text into the context, which makes them tempting to merge. The difference is who wrote it and why. Notes are small facts the assistant saved about its own work, such as one student's status. Retrieval searches a large body of text that already exists, such as a manual. They can share a database, but you decide separately what goes into each.

Check yourself

A student types a made-up error code, "E-417", shown on a printer screen. Which search is best at finding the manual page that mentions that exact code?

Show the answer

Exact-word search. Codes and part numbers are precise strings, and BM25 matches those, while embeddings capture meaning and can miss an exact match.

Recall, then check

Why is the manual chunked before it is searched, instead of searching whole manuals?

The point is to bring only the right few chunks of a few hundred tokens each into the context. A whole manual would be too big, would cost on every call, and could bury the answer.

Worked example: one booking request, six decisions 3 min

A rule of thumb for sorting any piece of information:

  • a durable fact about one student that nothing else holds: notes;
  • large, fixed text where each question needs a small part: retrieval;
  • live data that changes, or the working steps of this session: a tool result in the context.
Worked example

A student types: "I want the laser cutter on Friday afternoon. What settings for 3 mm acrylic?" The assistant has a notes store, a manual search tool, a calendar tool and a booking tool. For each step, try your own answer first, then open it. The data is invented for the example.

Step 1: where would "is this student trained?" be stored?

Show the answer

In notes. It is a durable fact about one student. The assistant reads the notes first, and they say "laser cutter training passed on Monday". That one line goes into the context, not the student's whole history.

Step 2: the manual is about 24,000 tokens. Paste it or retrieve?

Show the answer

Retrieve. From the cost section, pasting it across six calls is about 144,000 input tokens, against about 5,400 for three chunks. The chunks join the context. The manual stays in the store.

Step 3: where does Friday's availability come from?

Show the answer

The calendar tool, fresh each time. Availability changes, so saving it in notes would go stale. The result joins the context as a tool result.

Step 4: what happens after the booking tool runs?

Show the answer

The confirmation is appended, and the long calendar listing is now stale. Your trimming rule clears that old result so the final calls carry less. The model does not decide this on its own.

Step 5: the student says they prefer afternoons. What is saved?

Show the answer

A short note, "prefers afternoon slots". The calendar already holds the booking itself, so copying it into notes adds nothing. The preference is a durable fact that no other store holds. Keep it minimal.

Step 6: what happens to the context itself?

Show the answer

It disappears. On the next visit the context starts empty, and the assistant reads the notes again to catch up.

Summary 2 min

  • The model sees only the context of the current call. The API is stateless by default, so your program re-sends the whole history every time.
  • A long context costs money, since it is re-billed on every call, and can hurt accuracy through context rot. Keep the high-signal text only.
  • Trim a long session by clearing old tool results, summarizing, or handing a side task to a sub-agent.
  • Notes carry small durable facts between sessions; your application stores and loads them.
  • Retrieval searches big text such as manuals and brings in only a few chunks.
