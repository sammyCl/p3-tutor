Context and memory in an agent: what it sees, what it keeps, what it looks up

By the end of this lesson you can look at any piece of information in the makerspace assistant and say where it should live: in the context for this request, in saved notes between visits, or in a manual you search when needed.

Objective O3: context and memory in an agent About 30 minutes Builds on your work on the agent loop
Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training status between visits, all on a small model budget. Both problems are context and memory problems. At your design review you will be asked what the assistant keeps, what it saves and how it finds the right page, and this lesson gives you the answers and the reasons.

Your program runs the tool, not the model. The model only writes a request for it. The program puts the result back into the conversation and calls the model again, and that repeats until the model gives a final answer. Today's lesson is about what is inside each of those calls, and what survives after the last one.

What the model sees on every call 5 min

A language model does not hold a running conversation in its head. Each time your program calls it, the model sees one block of text and writes the next piece. That block is the context: the set of tokens included when the model is asked to write (Anthropic, context engineering). A token is a small chunk of text, roughly a word or part of one.

The context window is the most text the model can look at in one call, including the answer it writes. It works like the model's working memory, and it is separate from what the model learned in training (Claude docs, context windows). Windows are measured in tokens. For some current models the window is up to 1 million tokens.

Everything the call carries counts toward that window:

  • the system prompt (your standing instructions);
  • the definitions of your tools, such as "check_calendar";
  • every earlier message in the conversation;
  • every tool result that came back;
  • the answer the model is about to write.

Here is the part that surprises people who have only used a chat app. The Messages API is stateless: "you always send the full conversational history to the API" (Claude docs, Messages API). Stateless means the service keeps nothing between calls. If you are used to a web server, think of an HTTP request with no session cookie: it must carry everything the server needs.

So between steps of one request, what is "kept" is just a Python list that your program keeps appending to and re-sends.

A common mix-up

"The model remembers what we already said." This is tempting because chat apps feel like a continuing conversation. In fact your program rebuilds the whole conversation on every call, and the model reads it fresh. Nothing is remembered unless it is in the text sent this time. This is why the loop you learned earlier is a series of separate model calls, and it is the key to everything else in this lesson.

Check yourself

The assistant answers one request in three model calls. How many times is the student's original question sent to the model?

Show the answer

Three times. The API is stateless, so every call re-sends the whole history, and the question sits at the top of it each time.

Why a long context costs money and accuracy 5 min

Because every call re-sends the whole stack, a long context hurts you in two ways.

It costs more

You are billed for the tokens you send in and the tokens the model writes. Each call's input includes the full history, so a bulky tool result is paid for again on every later call in that request. The size of the window is a ceiling, not a target.

Here is an illustration with made-up round numbers, to show the shape of the problem. Suppose you pasted a manual of about 24,000 tokens into the context, and the request takes six model calls. You send the manual six times: about 144,000 input tokens for one student question. Now suppose instead you fetch three relevant passages of about 500 tokens each. That is 1,500 tokens, sent six times: about 9,000. Real prices vary by model, but the ratio is the point, and with a small sponsor budget the ratio decides how many questions you can afford.

It can make answers worse

More text in the window does not mean better answers. As the token count grows, accuracy and recall degrade, an effect called context rot (Claude docs). Anthropic's engineers describe context as a finite resource with an "attention budget", and say the goal is "the smallest set of high-signal tokens" that gets the result you want (Anthropic, context engineering).

Think of it like a desk. A bigger desk lets you spread out more paper, but you find things more slowly when the whole pile is on it.

Prompt caching can lower the price of re-sent text, but cached text still occupies the window (Claude docs). It helps the bill, not the crowding.

Money: the same tokens are re-sent and billed on every call. Quality: context rot, where recall and accuracy drop as the window fills. Both push you toward putting only the high-signal text in the window.

Three ways to keep a long run inside the window 5 min

A request that takes many steps can fill the window even when each step is small. Three standard moves keep it in check.

  • Clear old tool results. After the assistant has used a 300-line calendar listing to find a free slot, the listing is dead weight. Clearing removes it from the history and is one of the "safest, lightest touch" forms of trimming (Anthropic, context engineering; see also context editing).
  • Summarize the conversation (compaction). When a conversation nears the limit, it is summarized and a new window starts from that summary (Claude docs, compaction). You trade detail for room.
  • Hand a side task to a sub-agent. A second model call with its own clean window does a focused job, such as searching a manual, and "returns only a condensed, distilled summary", often 1,000 to 2,000 tokens, to the main agent (Anthropic, context engineering).

All three do the same thing: keep what the next step needs, and drop the rest. They differ in how much they throw away. For the makerspace assistant, a typical request is only a few steps long, so you will probably need little more than clearing. Summarizing and sub-agents matter for long sessions, and you will weigh sub-agents properly when we reach multi-agent designs.

Check yourself

The assistant has just booked a slot. The 300-line calendar listing is still in the history, and the student wants to ask a follow-up about settings. Which is the lightest fix?

Show the answer

Clear the old tool result. It is the lightest touch: only the stale text goes, and the question and the booking stay.

Notes that outlive the session 6 min

Everything so far lives inside one request. When it ends, the list your program built is gone unless you save it. So how does the assistant know on Thursday that a student passed laser-cutter training on Monday?

The answer is memory in the practical sense: information stored outside the context window that a later session can load. One pattern is structured note-taking: the agent writes notes to storage outside the window and reads them back later (Anthropic, context engineering).

Claude's memory tool is a concrete version of this. The model can create, read, update and delete files in a /memories directory, and those files persist between sessions (Claude docs, memory tool). The process looks like this:

  1. A new session starts. The model first looks in the notes ("view /memories").
  2. Your program runs that request against storage you chose, and returns the file text as a tool result.
  3. The model uses the notes in its answer.
  4. As things change, the model asks to write or edit a note.
  5. The session ends. The context vanishes. The notes remain.

Notice step 2. The memory tool is client-side: "Claude requests file operations, and your application runs them" (Claude docs, memory tool). It is the same loop you already know, with files as the tool.

A common mix-up

"The model just remembers students." It is tempting because chatbots with memory features feel that way. But the model has no storage of its own. Memory exists only if your application stores something and puts it back in front of the model next time. If the notes are not written, or not loaded, the Thursday session starts blank.

Two practical design points follow, both from the same docs. First, what goes in the notes is your decision. You can tell the model to write only what is relevant to your topic. Second, because your application runs every file operation, it is also responsible for safety: it must reject paths outside /memories, and the docs suggest capping file sizes and deleting old files (Claude docs, memory tool). For a university makerspace, that matters for privacy: store a student's training status, and not more than you need.

Retrieval: fetching the right manual page 5 min

Notes hold small facts the agent wrote itself. The manuals are different: they are long, written by someone else, and mostly irrelevant to any one question. The tool for them is retrieval: search a large store and put only the best few passages into the context. Doing this before the model answers is called retrieval-augmented generation, or RAG (Anthropic, contextual retrieval).

A typical setup works like this:

  1. Chunk. Split each manual into chunks, pieces "usually no more than a few hundred tokens".
  2. Index. Turn each chunk into an embedding, a list of numbers that captures its meaning, so chunks about similar ideas sit close together. Store these in a database built for similarity search.
  3. Search. When a question arrives, search for the closest chunks. Meaning search is good at paraphrase ("how thick can I cut?" finds "maximum material thickness") but can miss exact matches.
  4. Add exact-word search. A ranking method called BM25 matches precise words, which suits things like an error code. Combining both gives more complete results.
  5. Insert. Put the top few chunks into the context, and let the model answer from them.

All of this is from Anthropic's contextual retrieval write-up, which also notes that chunks can lose their surroundings: a chunk saying "the limit is 5 mm" does not say which machine. Adding a short line of context to each chunk before indexing cut failed retrievals from 5.7% to 3.7%, and to 2.9% when combined with exact-word search, in their tests.

When you can skip it

The same write-up says that if the whole knowledge base is under about 200,000 tokens (roughly 500 pages), you may be able to put it all in the prompt and skip retrieval, with prompt caching making that faster and cheaper. Your manuals might fit. Whether that is wise for you depends on the cost arithmetic from earlier, which is why you should measure your manuals before choosing.

A common mix-up

"Retrieval and memory are the same thing." They are tempting to merge because both bring stored text into the context. The difference is who wrote it and why. Notes are small facts the assistant saved about its own work, such as one student's status. Retrieval searches a large body of text that already exists, such as a manual. They can share a database, but you decide separately what goes into each.

Check yourself

A student types a made-up error code, "E-417", shown on a printer screen. Which search is best at finding the manual page that mentions that exact code?

Show the answer

Exact-word search. Codes and part numbers are precise strings, and BM25 matches those, while embeddings capture meaning and can miss an exact match.

Worked example

Step 1: what does the assistant do before answering?

Show the answer

It reads the student's notes. The notes say "laser cutter training passed on Monday", so booking is allowed. That one line goes into the context. The student's whole history does not.

Step 2: how does it find the acrylic settings?

Show the answer

It searches the manuals with the question. Three chunks come back, about 1,500 tokens in all, and they join the context. The 60-page manual stays in the store. The model answers from those chunks.

Step 3: where does Friday's availability come from?

Show the answer

From the calendar tool, fresh each time. Availability changes, so saving it in notes would go stale. The result is added to the context as a tool result.

Step 4: what happens after the booking tool runs?

Show the answer

The confirmation is appended to the context, and the long calendar listing is now stale. This is the moment to clear that old result so the final calls carry less. Your program does this, not the model.

Step 5: what is saved when the session ends?

Show the answer

One short note, such as "booked laser Friday 2 pm". The retrieved chunks and the calendar listing are dropped, since they can be fetched again. The context itself disappears.

Summary 2 min

  • The model sees only the context of the current call. The API is stateless, so your program re-sends the whole history every time.
  • A long context costs money, since it is re-billed on every call, and can hurt accuracy through context rot. Keep the high-signal text only.
  • Trim a long run by clearing old tool results, summarizing, or handing a side task to a sub-agent.
  • Notes carry small durable facts between sessions; your application stores and loads them.
  • Retrieval searches big text such as manuals and brings in only a few chunks.
