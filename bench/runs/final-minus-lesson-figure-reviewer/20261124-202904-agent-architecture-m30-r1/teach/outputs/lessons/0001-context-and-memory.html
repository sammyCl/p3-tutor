Context and memory: what an agent sees, keeps and looks up

By the end of this lesson you can decide, for any piece of information in the makerspace assistant, whether it belongs in the context window, in saved notes, or in a manual to be searched.

Objective O3: context and memory in an agent About 30 minutes Builds on the agent loop (what you already know)
Why this matters for you

Your assistant has to answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. All three come down to one design question: what goes in front of the model on each step. This lesson gives you the vocabulary and the rules to answer it at your design review.

Warm-up 1 min

Recall

In the agent loop, the model asks for an action such as "check the booking calendar for Friday". Who actually runs that action: the model or your program? And is each trip around the loop one model call or one long call?

Check your answer

For the tools you define, your program runs them. The model only writes a structured request for it, as text. Each trip around the loop is a separate model call. That second fact matters today: if each step is a fresh call, the model itself carries nothing over, so whatever it needs on the next step has to be sent to it again.

Tokens, the unit of everything 2 min

You know a model reads text and writes text. It does not read letters or whole words, though. It first cuts text into pieces called tokens. A token can be a whole word, part of a word, or a single character. For example, a tokenizer may split "annoyingly" into "annoying" and "ly" (Hugging Face LLM Course, Tokenizers).

For a programmer, the closest comparison is a list of strings: the model's input is a list of tokens, and so is its output. Short common words are often one token each, and long or rare words (like "bandsaw kerf") take several. The program that does the cutting is called a tokenizer, and exact counts depend on the model, so you measure them with the provider's token counter instead of guessing. For scale in your project: a three-sentence student question might be about 50 tokens, while a pasted bandsaw manual could be 20,000 (an illustrative guess, not a measurement).

Why care? Two limits are counted in tokens:

  • Size. A model can only handle so many tokens in one call. That limit on how much one call can hold is called the context window, defined next.
  • Cost. Model usage is normally billed by the tokens you send and the tokens it writes. Check your provider's price page for the actual rates; this lesson uses plain token counts so the reasoning holds for any price.

So "keep the context small" is not a style preference. It is the main lever on your sponsor's budget.

The window: all the model can see 3 min

The context window is all the text the model can look at when it writes a response, including the response itself. The Claude docs call it the model's "working memory" (Claude API docs, Context windows). Compare it with training: training is what the model learned long ago and cannot change. The window is what you hand it right now.

In computer science terms, think of RAM versus disk. The window is RAM: fast, directly usable, small, and wiped when the call ends. Anything bigger or longer-lived has to sit somewhere else and be loaded in when needed.

What fills it? Everything in the request counts, and so does the model's reply (Claude API docs). For one call from your assistant, that means:

  • the system prompt: the standing instructions you write, such as "You are the makerspace assistant";
  • the tool definitions: the name and description of each tool, such as check_calendar, which the model reads to know what it can ask for;
  • the messages so far: the student's question, the model's earlier replies and the tool results (what your program sent back, such as the calendar listing).

Anthropic's engineers list the same ingredients (Anthropic Engineering, Effective context engineering for AI agents).

This is why every tool description in your assistant's design is not free: its text sits in the window on every single call. So budget the system prompt and the tool list first, since they leave less room for manual text.

Window sizes differ by model and change over time; the Claude docs list 1 million tokens for most current Claude models and 200 thousand for some older ones. Look up your model's limit instead of memorizing one.

Why every step re-sends the history 5 min

Here is the key fact about what is kept between steps. When you call a model from code, the model keeps nothing between calls. Your program keeps a list of messages, and on every call it sends the whole list again. The docs put it this way: each user message and assistant reply accumulates in the window, and previous turns are preserved completely; each turn's input is all the earlier history plus the new message (Claude API docs).

In Python terms, the "memory" of a conversation is a list you own:

messages = []                                   # lives in YOUR program
messages.append({"role": "user", "content": question})
while True:
    reply = call_model(system, tools, messages)  # sends EVERYTHING each time
    messages.append(reply)                       # the reply joins the history
    if reply is a final answer: break
    result = run_tool(reply)                     # your code runs the tool
    messages.append(tool_result(result))         # the result joins the history

That is the agent loop you already know, now with the list made visible. (The pseudo-code names are illustrative, not a real library's API.)

What this does to cost

The sketch below shows the shape; the numbers that follow are the same made-up example.

The numbers are a made-up example. Suppose the system prompt, tool definitions and the student's question take 2,000 tokens, and each step adds about 1,000 tokens (the model's reply plus the tool result). Four calls send 2,000 + 3,000 + 4,000 + 5,000 = 14,000 tokens, though only 5,000 tokens of distinct text exist.

Early content is paid for again on every later call, so a long loop costs more per step than it looks. One bulky tool result, such as a whole manual page, is paid for on every step after it arrives. For a small budget, that gives two design rules:

  • cap the steps allowed per request;
  • make tools return short results.
Providers may offer prompt caching, which can lower the price of repeated text. The docs are clear that caching changes what you pay for those tokens, not whether they count toward the window (Claude API docs).
A common mix-up

"The model remembers what we said earlier." It feels true because chat apps behave that way. In fact the app is re-sending the transcript each time. If your program forgets to include the earlier messages, the model has no idea they happened. Try it in your head: send only "And on Friday?" with no history, and the model cannot know which machine or which booking "Friday" refers to.

The third option. The model sees exactly the request your program builds for call 5. If that request holds the full message list, it sees calls 1 to 4 as history; if your code dropped some, they are gone. Option two is wrong because earlier calls leave no trace in the model itself: the history is there only if your code re-sent it.

When the window fills up 4 min

Two problems appear as the list grows. One is hard: the request no longer fits. The other is quiet: the model gets worse before the window is full.

The quiet one has a name, context rot: as the token count grows, the model's accuracy and recall of what is in the context degrade (Claude API docs; Anthropic Engineering). Anthropic's advice follows from it: treat the window as a limited budget and aim for the smallest set of high-value tokens, not the biggest pile.

There is research evidence for this too. In the paper "Lost in the Middle", models did best when the relevant text sat at the start or the end of a long input, and worse when it sat in the middle (Liu et al., published in TACL). So pasting a whole 80-page manual into the prompt is both expensive and less reliable than it seems.

Three ways to make room

  • Clear old tool results. After the assistant has used a calendar listing, drop the raw listing from the history. Anthropic calls this one of the safest, lightest-touch ways to trim context; unlike summarizing, it drops raw results without rewriting the conversation (Anthropic Engineering).
  • Compact by summarizing. Compaction, in its full form, means summarizing the earlier conversation and starting a new window with that summary (Anthropic Engineering). Some providers now offer this on the server side, so you may not have to write it yourself (Claude API docs). The cost is that a summary can lose a detail you later needed.
  • Keep less to begin with. Return short results from tools, such as the three relevant paragraphs rather than the whole page.

The third is cheapest and is where the retrieval section below comes in.

Clearing versus compacting, on the same history

Take one long session. The history holds 20,000 tokens: 12,000 of raw tool results (calendar listings and manual pages the assistant has finished with), 6,000 of conversation, and 2,000 of system prompt and tool definitions. Compare the two fixes.

  • Clear the finished tool results. The 12,000 tokens become, say, 500 tokens of one-line outcomes ("Friday 2 pm booked"). The window drops to about 8,500 tokens, and the conversation itself is untouched word for word.
  • Compact the conversation. The 6,000 tokens of conversation become a summary of perhaps 600. The window drops further, but the summary is written by a model deciding what matters. If the student mentioned early on that they are left-handed and need the guard on the other side, the summary may drop it, and you will not find out until the assistant gets it wrong.

A rule of thumb for your design (this lesson's own advice, not a quotation): clear first, because it loses almost nothing. Compact only when clearing is not enough, and save anything that must be kept, such as a safety sign-off, to the notes store described next, so it does not depend on a summary's recall.

One more reason not to just buy a bigger window: it only delays the hard limit. You would still pay for the dead weight on every call, and context rot would still apply.

Notes that outlive a session 4 min

Everything so far lives and dies with one conversation. Your assistant also has to know that a student passed the laser cutter training last week. That needs a second kind of memory, kept outside the window.

LangChain's docs name the two kinds. Short-term memory is the message history of one conversation thread, where a thread is one chat conversation. Long-term memory is information saved across threads and sessions, and loaded back when needed (LangChain docs, Memory overview).

Anthropic describes the same idea as structured note-taking: the agent regularly writes notes to storage outside the window, such as a to-do list or a NOTES.md file, and reads them back later (Anthropic Engineering). The DeepLearning.AI course on agent memory teaches the same split: a small window, with the rest kept outside and moved in when needed (DeepLearning.AI).

For you, long-term memory is simply a database or a JSON file keyed by student ID. LangChain's storage model fits that picture: a namespace works like a folder, a key like a file name, and the value is a JSON document. The same page sorts what you might save into facts (such as training status), past experiences, and rules for behavior.

A saved note, step by step

Here is what one student's saved note might look like, as a Python dict you would store as JSON (the field names are an illustration, not a required format):

notes["student-4821"] = {
    "training": {"laser_cutter": "passed", "bandsaw": "not taken"},
    "last_booking": "laser cutter, Fri 2 pm",
    "last_advice": "drill press, aluminum: 1,200 rpm, 6 mm bit"
}
  • Written: the moment training status changes, or at the end of a session, your code updates this record. The model can request the write through a tool such as save_note, and your program performs it, just like any other tool.
  • Read: at the start of the next session, your code looks up notes["student-4821"] and puts it in the first message or the system prompt. That is about 60 tokens, which is cheap.
  • Skipped: if the write never happens, nothing breaks loudly. The next session simply starts as if the student were new, and the assistant either asks again or refuses a booking it cannot verify. Missing memory fails quietly, so test it by running two sessions in a row.

Two decisions for every saved fact

  • When to write. Write right away for facts that must not be lost, such as a safety sign-off, because a session can crash before it ends. Batch the rest at the end, which keeps the live loop simpler.
  • When to read. Load the few facts a request needs, such as this student's training status, not the whole store. Anything loaded takes up window space.
A common mix-up

"Save the entire past conversation and paste it into the next session." It sounds thorough, but it reloads every old tool result and side comment, which costs tokens and invites context rot. Save short facts instead: "laser cutter training passed on a given date" is far smaller than the chat where it came up.

Finding the right page in a long manual 5 min

The manuals are the third kind of information. They are too long for the window, they rarely change, and each question needs only a small piece. Retrieval means searching a collection for the few pieces relevant to the question and putting only those into the window. Notes hold facts about each student; retrieval is how the assistant looks up reference material that lives outside the window. Between them they give the assistant what it needs beyond one conversation.

Take the question "What blade speed for 5 mm acrylic?" Your program does not need the whole bandsaw manual, only the one or two paragraphs about speeds and acrylic. Retrieval finds those paragraphs. Here is the recipe that does it.

The LangChain tutorial shows the standard recipe (LangChain docs, Build a RAG agent). It runs in two phases. The first is done once, ahead of time:

  • Split each manual into chunks. The tutorial uses 1,000 characters with 200 characters of overlap, so text near a boundary usually appears in both neighboring chunks.
  • Embed each chunk. An embedding is a list of numbers that represents what a piece of text is about, so texts with similar meaning get similar numbers.
  • Store the embeddings in a vector store, a database built to find the nearest numbers.

The second happens on every question:

  • Search: embed the question and fetch the closest chunks. The tutorial's example returns the top 4.
  • Answer: the model writes its answer from those chunks, which are now in the window.

You can offer this to the agent as a tool, say search_manuals(query), so the model decides when to look something up. A tool saves tokens on questions that need no manual, such as "is the laser free Friday?"; searching on every question is simpler but loads chunks every time. The tutorial itself shows this agent version, in which the model chooses when to search.

Anthropic calls loading data at the moment it is needed, through tools, just-in-time retrieval. Agents can keep light references, such as file paths, and fetch the content only when they need it (Anthropic Engineering).

The payoff for your budget: four chunks of about 1,000 characters each put a few thousand characters in the window, not a whole manual. And since the 2023 Lost in the Middle study found models used the middle of long inputs less reliably, a short, focused window is the safer bet; the effect varies by model, so test yours.

One caution: embeddings are not always needed. For one short manual, pasting it in or a plain keyword search is simpler. Use embeddings when the manuals are many and long, or when students word questions differently from the manual.

Retrieval can miss. If the best chunk is not among the top few, the model never sees it and may answer from nothing. Test your search with real student questions before trusting it.

Worked example and your turn 3 min

Worked example

A student starts a new session and writes: "I finished the laser cutter training last week. Can you book it for Friday afternoon, and what power should I use for 3 mm plywood?" For each piece of information, decide where it lives. Try each step yourself before opening the answer.

Step 1: what is in the window on every call?

Show

The system prompt (the assistant's role and rules) and the tool definitions. They are the same every call, so keep them short and exact, because you pay for them each time.

Step 2: how does it know the training is done?

Show

Not from the student's word alone, and not from memory in the model. The program looks up the saved notes by student ID, at the start of the session, and loads one short fact: laser training passed. That is long-term memory.

Step 3: where does the power setting come from?

Show

Retrieval. The assistant calls search_manuals with "laser power 3 mm plywood" and gets the top few chunks of the laser cutter manual. Only those chunks enter the window.

Step 4: what happens to the calendar result?

Show

The calendar tool returns a long list of slots. After the booking is made, the list is no longer needed, so the program clears it and keeps a one-line note: "Friday 2 pm booked". That is short-term memory, trimmed.

Step 5: what is saved when the session ends?

Show

One short fact written to the student's notes, such as the booking and the settings given. The rest of the conversation is dropped. The next session starts with an empty window and loads only what it needs.

Your turn

A different student asks: "Which drill press speed for aluminum? And last time I forgot which bit size you recommended." Decide where each piece lives. The system prompt and tool definitions are in the window on every call, as in the worked example's Step 1. Now answer three questions yourself: (a) where does the speed come from, (b) where does "last time" come from, and (c) what do you save at the end?

Show a solution

(a) The speed comes from retrieval: search the drill press manual for aluminum and load the top chunks. (b) "Last time" comes from long-term memory: it only works if the previous session saved the recommended bit size in this student's notes, and the program loads that one fact. If nothing was saved, the assistant cannot know, and should say so instead of guessing. (c) At the end, save the new speed and bit size as one short note, and drop the retrieved chunks, which can be fetched again.

A second case with less help 2 min

Your turn, with only the question

A student writes: "I'm back to use the bandsaw. What blade speed for 5 mm acrylic? Also, did I already get my safety sign-off?" The assistant has just fetched a 40-slot booking list for another reason earlier in the same session. Place each item as retrieval, saved notes or the live window: (1) the blade speed, (2) the sign-off, (3) the 40-slot list. Then answer two more: (4) if the 40-slot list stays in the history for 3 more model calls and is about 3,000 tokens, how many tokens are re-sent because of it, and what does that mean for a small budget? (5) What do you save at the end?

Show a solution
  1. Blade speed: retrieval. Search the bandsaw manual and load the top few chunks.
  2. Sign-off: long-term memory, a short fact in the student's saved record, read at session start. It should not come from a conversation summary, so that it does not depend on a summary's recall.
  3. The 40-slot list: short-term memory, now stale. Clear it and keep a one-line outcome, since the question is no longer about booking.
  4. Cost of keeping it: 3,000 tokens times 3 calls is 9,000 tokens re-sent for text nobody needs. On a small budget, clearing it is free savings.
  5. At the end: save one line, "bandsaw advice given: acrylic, speed X", and drop the retrieved chunks. Which speed X is the manual's business; never invent it.

Summary 1 min

  • The context window is everything the model sees on one call, measured in tokens: system prompt, tools, messages, tool results and the reply.
  • Between steps, nothing is kept by the model; your program re-sends the whole history each call, so cost grows and old results should be cleared.
  • Between sessions, only what you save outside the window survives: short facts in a store, loaded back when needed.
  • Long manuals are searched, not pasted: retrieval puts only the few relevant chunks into the window.
  • Placement rule: facts about one student that must outlive the session go in saved notes; large, stable reference text goes in a searched store; only what this step needs goes in the window.
