The context window and its tokens 5 min

The context window is everything the model can see in one call: the text it reads and the text it writes. Anthropic's documentation describes it as the model's "working memory" and notes that it is different from the large body of text the model was trained on (Anthropic, Context windows).

Think of it like the stack and heap of one program run: whatever is not in there does not exist for that run. The model has no hidden storage of its own to fall back on.

The window is measured in tokens, the small chunks of text a model reads and writes. A token can be a whole short word, part of a longer word, or punctuation. As a rule of thumb for English, one token is about four characters, or three quarters of a word (OpenAI, What are tokens). So a 3,000-word manual chapter is roughly 4,000 tokens.

Tokens limit two things, and both matter to you:

  • Size. Each model has a maximum number of tokens it can handle in one call. If the input is too big, it must be shortened or split.
  • Cost. Model providers bill by tokens, with input and output counted separately (OpenAI). A longer input costs more and, as the DeepLearning.AI course points out, runs slower (DeepLearning.AI with Letta).

Everything in the call counts, not just the student's question. The window holds the system prompt (the standing instructions), the tool definitions, the earlier messages, the tool results, and the model's own reply (Anthropic).

Providers publish the exact window size for each model, and it changes. Look it up when you pick a model; the design logic below does not depend on the number.

Why every step re-reads everything 6 min

You know from the agent loop that each step is a separate model call. Here is the consequence for memory: the model does not carry anything over from one call to the next. What looks like "remembering the conversation" is the program re-sending the earlier messages every time. Anthropic's documentation puts it this way: each turn adds to the history, and the whole history is sent again (Anthropic, Context windows).

This is the short-term memory of an agent: the history of one conversation or one task, kept by your code and passed back in. LangChain's documentation calls this memory scoped to a single thread (LangChain, Memory). In Python terms, it is a list that you append to and send in full.

Two consequences follow for your budget:

  • A task with ten steps does not cost ten small calls. It costs ten calls, each carrying the whole history so far.
  • A big tool result, such as a full month of booking-calendar data, is carried in every later call of that task unless you remove it.

So a tool should return only what the model needs. Return "Friday 2 pm to 4 pm is free" rather than the whole calendar.

A common mix-up

"The model remembers what I said earlier in the chat." It feels true, because chat apps keep the whole conversation on screen. But the model remembers nothing between calls. The program re-sends the history. If your code forgets to include the earlier messages, the model has no idea what the student said a minute ago.

Check yourself

When the window fills up 4 min

History grows with every step, and the window has a limit. There is also a quality problem before the limit: Anthropic's engineering team describes context rot, where the model's ability to pick out the right detail declines as the amount of text grows, so context is a finite resource with diminishing returns (Anthropic, Effective context engineering). More context is not automatically better. The goal is the smallest set of high-signal text that gets the job done.

Three standard moves keep the history under control. Each one trades detail for space:

  • Trim. Drop the oldest messages and keep the recent ones. Simple, but whatever was dropped is gone. LangChain's documentation lists trimming as the basic way to handle a conversation that grows too long (LangChain).
  • Summarise (compaction). Ask the model to write a short summary of the history so far, then continue with the summary in place of the full text. Details can be lost, so the summary must keep decisions and open problems (Anthropic).
  • Clear old tool results. Once a tool's result has been used, it can usually go. This is one of the safest cuts, because the model already acted on it (Anthropic, Context windows).

For a makerspace assistant, most conversations are short, so you may rarely need any of these. They matter most for the next question: what should survive after the conversation ends?

Notes that outlive a session 5 min

When a session ends, the history list is gone. The next time a student opens the assistant, it starts with an empty window. Long-term memory is whatever you save outside the window and load back in later. LangChain's documentation separates this from short-term memory: it is stored across conversations, and organised by a key such as a user (LangChain, Memory).

The simplest version is a note: a small piece of text or data that the assistant writes down during one session and reads at the start of the next. Anthropic calls this structured note-taking, where the agent keeps notes outside the window and pulls them back when needed, for example a NOTES.md file (Anthropic, Effective context engineering). Anthropic's context-window documentation makes the same point for long-running work: save state to files so a new session can pick up where the last left off (Anthropic).

For you, a student's record might look like this in Python:

students = {
    "s1042": {
        "trained_on": ["laser cutter", "3D printer"],
        "last_booking": "laser cutter, Fri 2-4 pm",
        "prefers_units": "metric",
    }
}

At the start of a session, your code looks up the student and puts a short line into the system prompt: "This student is trained on the laser cutter and 3D printer." At the end, your code writes any change back. Two design questions decide whether this works:

  • What is worth saving? Facts that will matter next visit and are stable: training status, preferences. Not the whole chat, which costs tokens to reload and mostly will not matter.
  • Who writes it, and when? LangChain notes two options: the assistant writes memory during the conversation, or a separate step writes it afterwards in the background (LangChain). For training status, avoid trusting the model's say-so. Have your code update it from the real training records.
A student's saved record is personal data. Decide what you keep and who can see it before your review, not after.
A common mix-up

"A bigger context window means I do not need memory." A big window helps within one session, but it is empty at the start of the next one, it costs more as it fills, and context rot makes very long histories less reliable. Saved notes load a few lines; replaying every past chat would load thousands of tokens that mostly do not matter.

Check yourself

A student tells the assistant, "I prefer metric units." They return a week later. What must have happened for the assistant to know?

It was saved, then loaded. Nothing carries over between sessions unless your code stores it and puts it back into the next window.

Looking up the right manual page 5 min

Notes suit small facts about one student. Machine manuals are different: they are long, shared by everyone, and the answer to a question is usually one paragraph in hundreds of pages. Loading the whole manual into every call would be slow, costly and affected by context rot. Instead the assistant looks up only the relevant passage. This is retrieval: finding the few pieces of stored text that match a question and adding only those to the context.

Retrieval is memory in the sense that the manual lives outside the window and is brought in on demand. The DeepLearning.AI course describes the same two tiers: a small memory inside the context window, and a larger one outside it that you search (DeepLearning.AI with Letta). Anthropic calls the idea "just in time": keep light references such as file names or search queries, and load the content only when needed (Anthropic).

The Hugging Face cookbook walks through this in Python (Advanced RAG, Hugging Face Cookbook). The pieces are:

  • Chunking. Split the manual into pieces of a set size, often with a small overlap so a sentence is not cut off from its context. Each chunk is a short passage, such as one procedure.
  • Searching. Turn each chunk and the question into embeddings, lists of numbers that are close together when the texts have similar meaning, then pick the nearest chunks. This finds "how do I clear a jam" even if the manual says "removing a blockage". Keyword search is the simpler alternative and can be mixed in.
  • The top_k choice. How many chunks to return. Too few and you may miss the answer; too many and you pay for tokens and add noise. The cookbook also notes that models can lose information buried in the middle of a long context.
  • Prompting with the results. Put the chunks, labelled with their source page, plus the question into the input, and tell the model to say so if the answer is not in them. That last instruction keeps it from filling gaps with a confident guess, something you have already seen chatbots do.
The cookbook calls this pattern RAG, retrieval-augmented generation. You will see the acronym everywhere.

In an agent, retrieval can also be a tool: search_manual(query) returns a few chunks, and the model decides when to call it. That ties this lesson back to the loop.

Worked example and your turn 6 min

The question for any piece of information is the same: does it go in the window now, in a saved note, or in a searchable store? A rough guide:

Worked example

A student writes: "Can I book the laser cutter on Friday afternoon, and what settings do I use for 3 mm plywood?" Try each step yourself before you open it.

Step 1: what is in the first call?

Show

The system prompt, the tool definitions (check_calendar, book_slot, search_manual), and the student's question. Nothing else yet, so the input is small and cheap.

Step 2: how does it know the student is allowed to use the laser?

Show

Your code looks up the student's saved record before the first call and adds one line to the input: "Trained on: laser cutter." The model never has to guess or remember. This is a saved note, loaded at session start.

Step 3: where do the plywood settings come from?

Show

From the manual, not the model's training. The model calls search_manual("laser cutter 3 mm plywood settings"), gets back the top few chunks with their page labels, and answers from them. Retrieval keeps the other 190 pages out of the window.

Step 4: what happens to the calendar result?

Show

It joins the history and is re-sent on later calls. If the tool returned a full week, the cost repeats each step. Better design: have the tool return only Friday's open slots, and clear the result once the booking is made.

Step 5: what is saved when the session ends?

Show

Only what the next visit needs: the new booking, written by your code from the booking tool's confirmation. The chat itself, the settings table and the calendar data are dropped.

Summary 2 min

  • The context window is everything the model sees in one call, measured in tokens. Tokens limit its size and set the cost.
  • Between steps, the model keeps nothing. Your code re-sends the history, so every step pays for everything before it.
  • When the history grows, trim it, summarise it, or clear old tool results; more context is not automatically better.
  • Between sessions, only what you save and reload exists: small stable facts as notes for each student.
  • For long manuals, retrieve a few relevant chunks instead of loading everything.
