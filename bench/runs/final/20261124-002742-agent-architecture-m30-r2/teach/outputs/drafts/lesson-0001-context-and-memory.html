Context and memory: what an agent sees, keeps and looks up

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context window, in saved notes between sessions, or in a searchable store that the assistant looks up on demand.

Warm-up: one loop, one request 2 min

Check your answer

Your program runs the tool; the model only writes a request for it. The request takes two model calls: one that ends in the tool request, and one that reads the result and writes the answer. Hold on to "two separate calls". Today's question is what the second call can see, and the answer decides your costs.

The window: all the model ever sees 4 min

A language model does not remember anything between calls. Each call, it reads one block of text and writes the next tokens. That block is the context: everything you send in the call. A token is a chunk of text, roughly a short word or a piece of a long one. The context window is the maximum number of tokens the model can take in at once, the input plus what it writes. If something is not in the context, the model cannot use it, whatever you said to it last minute.

Anthropic's engineering team describes the context as the whole set of tokens given to the model on a call, and treats choosing what goes in it as the main design job in building agents (Effective context engineering for AI agents). For the makerspace assistant, a call's context holds:

  • the system prompt: your standing instructions ("You help students at the makerspace. Never book a machine for someone untrained.");
  • the tool descriptions: the text that tells the model what each tool does;
  • the conversation so far: the student's messages, the model's earlier replies, and every tool request and tool result;
  • anything you chose to add, such as a note about the student or a page from a manual.

Think of it as the model's desk. It can only work with what is lying on the desk for this call, and you, the programmer, decide what is put there each time.

Why a full window costs more and works worse 4 min

Two limits make you choose what goes on the desk. Both matter to a team with a small budget.

Cost

Model usage is billed mostly by tokens, and the input tokens of every call count. Because each call resends the history (Figure 1), a long loop pays for the early material again and again. The numbers below are made up to show the pattern: the prompt and tool descriptions take 2,000 tokens, and each step adds about 1,000.

One big paste, carried through three later calls, made the request about five times as expensive. LangChain's memory guide makes the same point: long conversations can overflow the window, and they add cost and latency (LangChain, Memory concepts).

Providers offer prompt caching, which makes a repeated, unchanged start of the prompt cheaper. Anthropic's retrieval article mentions it as a way to cut cost when a whole knowledge base is placed in the prompt. Check your provider's pricing before you count on it.

Attention

Fitting is not the same as being used well. Researchers testing long inputs found that accuracy falls when the relevant passage sits in the middle of a long context, compared with the start or end, and that adding more retrieved documents helped little (Liu et al., "Lost in the Middle", TACL 2024). Anthropic describes the same effect as an "attention budget": as the context grows, the model's recall of any one part tends to weaken (Anthropic). Their rule of thumb is to find the smallest set of high-signal tokens that gets the job done.

A common mix-up

"A bigger window means I can put the whole manual in and stop worrying." It is tempting because it is simple, and it can be right for a small document. But as the table shows, you pay for those tokens on every call that carries them, and the model may use them less well. Size is a ceiling, not a goal.

What survives from one step to the next 4 min

Inside one request, the loop keeps a running list of messages. Your program appends to it after every step: the model's tool request, then the tool's result. On each call it sends the list. This list is the agent's short-term memory. LangChain's docs describe the same idea: short-term memory is state held for one conversation thread, saved by a "checkpointer" so the thread can continue (LangChain, Memory concepts). In plain Python, it is a list of dicts you keep appending to.

messages = [{"role": "user", "content": "Book the laser cutter Friday at 2."}]
while True:
    reply = call_model(system_prompt, tools, messages)   # sends everything
    messages.append(reply)                               # keep what it said
    if no_tool_requested(reply):
        break
    result = run_tool(reply)                             # your program runs it
    messages.append(result)                              # keep what came back

The list only grows, so you need a plan for when it gets long. These are the common moves:

  • Trim: drop the oldest messages, or old tool results that are no longer needed. Cheap and simple, but you may lose something important.
  • Summarize (compaction): when the list nears the limit, have the model write a short summary, then start a fresh window from that summary. Anthropic calls this compaction, and notes the art is choosing what to keep and what to drop (Anthropic).
  • Keep tool results small: make the tool return only what the model needs, such as the free time slots, not the whole calendar.

The last one is the cheapest to build and usually the biggest saver.

What survives until the next visit 5 min

When the request ends and your program stops, the list of messages is gone. The next time a student opens the assistant, the model starts blank. If the assistant should know that this student finished laser-cutter training last month, your program must save that fact somewhere outside the context and put it back when needed. That is long-term memory: information stored outside the window that lasts between sessions.

LangChain's docs describe long-term memory as a store of records that you organize by a namespace (such as the student's id) and a key, and read across sessions (LangChain, Memory concepts). Anthropic describes the same idea as structured note-taking: the agent writes notes to a file outside the context window, such as a to-do list or a NOTES.md, and reads them back later (Anthropic). The Letta course goes a step further: the agent itself edits its memory using tools, deciding what is worth saving (DeepLearning.AI with Letta, LLMs as Operating Systems).

For you, the first design choice is who decides what gets saved. In a computer-science view it is a database write, and the question is whether your code or the model issues it.

FactWho should write itWhy
"Passed bandsaw training on 3 Oct"Your code, from the training systemIt is a record with consequences; a model's guess is not good enough.
"Prefers evening slots"The model, via a save-note toolLow stakes, and the model hears it in conversation.
"Booked laser cutter Fri 2 pm"Your booking toolIt is the calendar's job, not memory's.

Notes also go stale. Treat stored facts like a cache: record when they were saved, and re-check anything that can change, such as whether a training has expired.

Looking up the right page instead of carrying the manual 6 min

A manual set can run to hundreds of pages. Pasting it into every call would cost a lot (see the table earlier), so the assistant looks up the relevant page when asked. This is retrieval: searching an outside collection and putting only the best matches into the context. Retrieval is memory too, but memory of documents rather than of this student.

Anthropic's retrieval article gives a cost-based rule: if the whole knowledge base is under about 200,000 tokens, roughly 500 pages, you can put it straight in the prompt, using caching to keep it cheap; beyond that, you need retrieval (Anthropic, Introducing Contextual Retrieval). Check your manuals' total size first; you may be below the line.

If you are above it, the standard recipe, shown with Python code in LangChain's tutorial, has two phases (LangChain, Build a RAG agent):

  • Prepare once, ahead of time:
    1. Split each manual into chunks, small overlapping pieces. The tutorial uses 1,000 characters with a 200-character overlap, so a sentence cut at one edge appears whole in the next chunk.
    2. Turn each chunk into an embedding, a list of numbers that places similar meanings close together, and store them in a vector store.
  • Look up at request time:
    1. Wrap search in a tool. The model asks for it with a query such as "bandsaw blade change".
    2. Your program finds the closest chunks (the tutorial returns the top 4) and sends them back as the tool result.

Because search is a tool, it is just the loop you already know. The model decides when to search, and it can search again with different words if the first results miss. Anthropic calls loading data this way, as the agent needs it, just-in-time retrieval, in contrast with loading everything up front (Anthropic).

One caution matters for manuals. Embeddings match meaning, but error codes and part numbers are exact strings. Anthropic's article shows that adding keyword search (BM25) next to embeddings found more of the right chunks: the failure rate of retrieving the right top 20 chunks fell from 5.7% to 2.9% with hybrid search in their tests (Anthropic). Those are their figures on their data, so test on your own manuals.

Worked example and your turn: the Friday booking 7 min

Worked example

A student writes: "Book me the laser cutter for Friday at 2, and remind me how to change the lens." You must decide, piece by piece, where each fact lives. Try each question before opening the answer.

Step 1: what goes into every call?

Answer

The system prompt and tool descriptions. They are the standing rules and the menu of actions, and the model needs them each time. Keep them short, because you pay for them on every call.

Step 2: where does the student's training status live?

Answer

In a store keyed by student id, written by your code from the training records. Your program reads it when the session starts and adds one line, "laser cutter: trained, 3 Oct", to the context. The model never needs the whole record.

Step 3: how does the assistant answer the lens question?

Answer

It calls the manual-search tool with "laser cutter lens change". The program returns the top few chunks as the result. Only those chunks enter the context, not the whole manual.

Step 4: how big should the calendar tool's result be?

Answer

Only the laser cutter's slots on Friday. Anything larger stays in the context for every later call, as in the cost table.

Step 5: what is saved when the session ends?

Answer

The booking goes to the calendar through the booking tool. A note, "asked about lens cleaning; prefers afternoons", could go to the student's notes. The raw chat and the manual chunks are not saved; the chunks can always be searched again.

Your turn

Same assistant, a different request: "Which of the drill press settings did I ask about last week, and is the drill press free Monday morning?" Step 1 is given: the system prompt and tool descriptions go in every call. For each of the following, say where it lives and what enters the context: (a) last week's question, (b) the drill press's Monday bookings, (c) the drill press speed table in the manual. Then say one thing you would not save.

Show a solution

(a) Last week's question was a different session, so it is gone unless you saved it as a note. If you saved "asked about drill press speeds", read that note at session start and add one line. (b) Call the calendar tool filtered to the drill press and Monday morning; only those slots enter the context. (c) Search the manual with "drill press speed table" and add the top chunks as a tool result. Not worth saving: the full text of the chunks or the whole transcript, because they are large and can be rebuilt by search.

Summary 2 min

  • The model sees only the context you send in each call, and the window caps its size.
  • Everything in the context costs tokens on every call that carries it, and long contexts can be used less well.
  • Between steps, the message list is the memory; keep tool results small and trim or summarize when it grows.
  • Between sessions, nothing survives unless you save it to a store or notes file and load it back.
  • For long manuals, search and load only the top chunks, using keywords as well as embeddings; below roughly 200,000 tokens, putting it all in with caching may be simpler.
