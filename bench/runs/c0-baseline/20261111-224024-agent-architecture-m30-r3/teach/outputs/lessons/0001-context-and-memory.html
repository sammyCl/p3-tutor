Context and memory: what the assistant sees, keeps and looks up

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context, in saved notes, or in a manual you retrieve from, and say why.

Objective O3: context and memory in an agent About 30 minutes Builds on the agent loop (learning record 0002)
Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training status between visits, on a small budget. Those are three separate memory decisions, and each one has a different cost. At your design review you will be asked to defend them.

Warm-up 2 min

Recall

From memory: in the agent loop, the model asks for a tool. Who actually runs the tool, and what happens to the result?

Check your answer

The program around the model runs the tool. It then puts the result into the model's next input and calls the model again. That last part is today's topic: "the model's next input" is the context, and what goes into it is up to you.

The context window 5 min

Start with a student asking your assistant: "Can I use the laser cutter tomorrow at 3 pm?" Before the model writes a single word, the program has to hand it everything it needs. That bundle might look like this:

[system prompt]  You are the makerspace assistant. Be brief. Never book without confirming.
[tools]          check_calendar(machine, date), search_manuals(query), book_slot(...)
[user]           Can I use the laser cutter tomorrow at 3 pm?

That is all the model knows about this situation. It has no other window onto the makerspace. The context is the set of tokens the model is given when it generates a response, and the context window is the maximum number of tokens it can take in and produce in one request. Anthropic's docs call the window the model's "working memory" and note that it holds the system prompt, every message (including tool results and documents), your tool definitions, and the model's own output (Claude docs: Context windows). A token is a chunk of text, roughly a short word or part of a longer one; it is the unit that both the window and your bill are counted in.

A common mix-up

"The model knows the manuals, because it was trained on lots of text." Training gave it general patterns (learning record 0001), not your machine's manual, and not today's calendar. If a fact is not in the context, the model cannot read it. It can only guess, and a confident guess is exactly the outdated-fact problem you noticed with homework chatbots.

What is kept between steps 6 min

Here is a surprise that matters for your budget. A language model keeps nothing from one call to the next. Each call starts blank. The program creates the feeling of memory by sending the whole conversation again every time. The docs describe each turn's input as "all previous conversation history plus the current user message", and the reply is then added to the input of the next turn (Claude docs).

In the agent loop, a step is one model call. Follow the laser-cutter question through three steps. The numbers are token counts I made up to be plausible, so you can do arithmetic with them:

The story of the three calls:

  • Call 1 sees the system prompt and tools (about 2,000 tokens) plus the question (50). The model asks for check_calendar.
  • Call 2 sees all of call 1's input, plus the model's request (50) and the calendar result (300), so 2,400 tokens. The model asks for search_manuals.
  • Call 3 sees all of that, plus another request (50) and a manual page (3,000): 5,450 tokens. The model now writes the answer.

Total tokens the model read across the three calls: 2,050 + 2,400 + 5,450 = 9,900, even though the new information in the whole run was only about 3,500 tokens. That is why cost per request in your agent is not "tokens in the answer": it grows with the number of steps and the size of everything already in context. (Anthropic's docs note that caching a repeated prefix changes what you pay for those tokens, not whether they take up the window.)

A common mix-up

"The model remembers what happened earlier in the conversation." It does not; your program does, and resends it. This matters in two ways. First, if your program forgets to include an earlier message, the model has no idea it ever happened. Second, a "free" memory does not exist: every remembered token is paid for again on each call.

When the context gets too full 5 min

Windows are large now, up to a million tokens on many current models (Claude docs). So is the answer "put everything in and stop worrying"? No, for two reasons.

Cost and speed. From the last section: every token in context is read on every call. A bloated context is a bigger bill on each step.

Quality. Anthropic's engineers describe context rot: as the number of tokens grows, the model's ability to accurately recall information from the context decreases. They suggest treating context as a finite resource, with an "attention budget" that every new token uses up (Effective context engineering for AI agents). The docs say the same: more context is not automatically better, so what you curate matters as much as how much space is available.

A common mix-up

"A bigger context window means the assistant is better at long manuals, so we should paste the whole manual in." It is tempting because "it fits" sounds like "it works". But a 200-page manual in every call makes each step cost more, and it buries the one useful paragraph among thousands of irrelevant ones.

When a long run does fill up, the same source names the standard tools:

TechniqueWhat it doesMakerspace example
Clearing old tool resultsDrops a tool result the model has already used. The lightest option.Once the answer to "is it free at 3 pm?" is known, the 3,000-token manual page can go.
CompactionSummarises the conversation so far and continues in a fresh window with the summary.A 40-message booking chat becomes: "Student wants the laser cutter Friday; trained; slot chosen."
Sub-agentA helper works in its own window and returns only a short summary (the source cites about 1,000 to 2,000 tokens).Left for a later lesson on multi-agent systems.

Compaction is not free: a summary drops detail, and you choose what to keep. The source says Claude Code keeps architectural decisions and unresolved bugs and drops redundant tool output. For you, the equivalent is keeping the booking decisions and dropping the raw calendar dump.

What is kept between sessions: notes 5 min

A session is one conversation, from the student's first message to when it ends. Everything above lives and dies inside a session: when it ends, the message list is gone. Tomorrow's chat starts with an empty window, and the model has no idea that Maya passed her laser cutter training last week.

So anything that must survive has to be written down outside the context and read back in. Anthropic calls this structured note-taking, or agentic memory: the agent writes notes to storage outside the context window and pulls them back in later. Their example is an agent playing a game that keeps a running tally of its progress across thousands of steps (Effective context engineering). Notes are also how long tasks continue after compaction.

For your assistant, the "notes" can be as simple as a JSON file or a database row per student:

{
  "student_id": "s-4821",
  "trained": ["laser_cutter", "3d_printer"],
  "not_trained": ["cnc_router"],
  "last_booking": "laser_cutter, 2026-11-06"
}

At the start of each session your program reads that record and puts it in the context (usually in the system prompt). At the end, or when something changes, it writes the record back. You already know how to read and write JSON, so this part is plain Python and needs no new machinery. The model can also be given a tool such as save_note(...), so it decides what is worth saving. Anthropic's docs have a memory tool for that approach (memory tool, multisession pattern).

A common mix-up

"The assistant will just remember the student next time." Nothing carries over unless your program saves and reloads it. Also, do not save the whole transcript as a note: it would refill the next context with old tokens. Save facts, such as "trained on laser cutter", not conversations.

Retrieval: finding the right page 5 min

The third kind of memory is for knowledge too large to put in the context: the manuals. Retrieval means finding the few relevant pieces and placing only those in the context for the call. Anthropic describes the "augmented LLM" as a model with retrieval, tools and memory, and notes that current models can write their own search queries (Building effective agents).

There are two timings, both described in the context engineering article:

  • Before the model runs: the program searches (often by meaning, using embeddings) and puts the best passages in the context up front.
  • Just in time: the agent keeps light references, such as file names or page titles, and loads the content with a tool when it needs it. The source warns that this is slower than retrieving pre-computed data. Claude Code mixes the two: some files are loaded at the start, and others are fetched on demand.

For your assistant, a good mix is a short fixed note in the system prompt ("manuals exist for: laser cutter, 3D printer, CNC router") and a search_manuals(query) tool that returns a few short passages. The model decides when to search, using the tool's description, just as in the agent loop.

Retrieval can fail, and then the model answers from the wrong page or from nothing. Two cheap fixes: return the source (manual and page) with each passage so the answer can cite it, and tell the model in the system prompt to say "I could not find that" when the search comes back empty. Improving how search ranks pages is a topic for a later lesson.

A common mix-up

"Retrieval is the model remembering the manual." The model remembers nothing; a search tool returns text and the program puts it in the context. The model is not remembering but reading, in the same way it reads your question.

Worked example and practice 5 min

Worked example: where does each fact live?

A returning student, Maya, writes: "Book the CNC router for Thursday." Decide where each fact comes from.

  1. The assistant's rules and tool list. They are needed on every call and are small, so they go in the context, as the system prompt and tool definitions.
  2. Maya's training status. It is a durable fact about her, needed across sessions, so it lives in the saved student record, and the program loads it into the context at the start of the session. Here it says she is not trained on the CNC router.
  3. The CNC router's training requirements. They sit in a long manual, so the model calls search_manuals("CNC router training"), and only the returned passage enters the context.
  4. Thursday's calendar. It changes constantly, so it is neither saved nor in a manual: the model calls check_calendar and the result enters the context for this session only.
  5. The decision. The assistant declines to book and explains the training requirement. If the student later completes training, the program updates the saved record, so the next session starts with the right status.

Then decide: the sponsor says the assistant must also greet students by their preferred name. Where does that fact live?

Show a solution

Call 3 sees call 2's input (2,400) plus the model's request (50) plus the result (600): 3,050 tokens. The total is 2,050 + 2,400 + 3,050 = 7,500, compared with 9,900 before, a saving of 2,400 tokens, from retrieving a smaller passage alone.

The preferred name is a durable fact about the student, so it goes in the saved student record and is loaded into the context at the start of each session.

Summary 2 min

  • The context is everything the model sees in one call; the window is its size limit. The model keeps nothing between calls: the program resends the history each time, so every step costs more than the last.
  • A bigger window does not mean "put everything in": cost and recall quality both get worse as the context grows. Clear what is no longer needed, or compact the history.
  • Between sessions only saved notes survive: write down durable facts, such as training status, and reload them next time.
  • For knowledge too large to fit, such as the manuals, retrieve a few relevant passages when needed.

Say it in your own words: without looking, explain to a teammate why the assistant "remembers" within a chat but not the next day, and name the three places a fact can live.
