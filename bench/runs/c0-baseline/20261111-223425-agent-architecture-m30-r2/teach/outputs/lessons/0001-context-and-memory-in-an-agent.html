Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the model's context, in a saved note, or in a searchable manual store, and say why.

Warm-up 2 min

Recall

From memory: in the agent loop, a student asks "Is the laser cutter free Friday?" The model asks for check_calendar. Who actually runs the tool, and what happens to its result?

Check your answer

The program around the model runs the tool, not the model. It then sends the result back to the model as part of the next model call. That last part is today's topic: "part of the next call" means the result becomes text the model reads, and all such text has a limited place to live. That place is the context window.

The context window 6 min

Start with a concrete case. A student types, "Can I use the laser cutter?" Your assistant answers, "You need the safety class first." The student replies, "Which one?" To answer, the model must know what "which one" refers to. Nothing inside the model remembers the previous message. So the program has to include the earlier messages in the next request.

The context window is all the text the model can look at when it writes a response, including the response itself. The Claude docs call it the model's "working memory", and distinguish it from the large body of data the model was trained on (Claude docs: context windows). A token is the small chunk of text, roughly a word or part of a word, that models read and write; the window's size and your bill are both counted in tokens.

Everything in a request counts toward the window: the system prompt, every message, tool results, and the tool definitions you send. The reply counts too (same docs page).

Two facts follow, and both matter for your budget.

  • Size is finite. Current Claude models list windows of up to 1 million tokens, but a bigger window is not automatically better (same docs page).
  • More text means worse recall. As the token count grows, accuracy and recall degrade, a phenomenon the docs call context rot. Anthropic's engineering team frames context as a finite "attention budget" and advises finding "the smallest set of high-signal tokens" that gets the result you want (Effective context engineering for AI agents).

Cost follows the same logic: you pay for the input tokens on every call, so a long context repeated across many steps is the expensive path.

A common mix-up

"A bigger window means I can paste in everything and the assistant will use it well." It is tempting because the window size is the number on the box. But recall gets worse as the window fills, and you pay for every token on every call. Pasting all twelve machine manuals into each request would be slower, costlier and less accurate than giving the model only the right page.

What is kept between steps 5 min

Now put the window inside the agent loop. Recall that every step of the loop is a separate model call. Between calls the model keeps nothing; what carries over is whatever the program puts into the next request. In the Claude API, previous turns are preserved in the conversation you resend, and each turn's input is all the earlier history plus the new message (context windows).

So inside one request, the context grows at each step. Here is the laser-cutter question, counting only roughly:

This is why long runs get expensive: call 4 pays again for everything in calls 1 to 3. It is also where the bloat comes from. A tool that returns a whole manual chapter when you needed one paragraph makes every later call heavier.

There are three standard ways to keep a growing context under control, all described by Anthropic (context engineering):

  • Return less. Design tools to return small, useful results. For example, check_calendar returns only the free slots for the requested day, not the whole month.
  • Clear old tool results. After a tool was called deep in the history, ask whether the agent needs the raw result again. The Claude API offers context editing for this: it drops old results while keeping a record that the call occurred (context windows).
  • Compaction: when the conversation nears the limit, summarize it and start a new window with the summary. A good summary keeps decisions and unresolved problems and drops redundant output.
Compaction is lossy: the summary replaces the detail. Anything you must never lose, such as a booking confirmation number, belongs in a saved note (later in this lesson), not only in the chat.

What is kept between sessions 4 min

A session here means one conversation, from the student's first message until it ends. A new session starts with a new, empty context window. That includes the student who returns next week.

A common mix-up

"The assistant remembers me from last visit, because chatbots do." It is tempting because consumer chat apps can feel that way. But the model itself keeps nothing: what looks like memory is something the program saved and put back into the context. Your assistant remembers a student's training status between visits only if you build that.

Work through the example. Priya passed the laser-cutter safety class on Monday. On Thursday she opens a new chat. The new context holds the system prompt, the tool definitions, and her question. Her training status is in none of them. Two designs fix this:

For a fact the university already tracks, such as training status, the first design wins: the source of truth is the database, and the note would only copy it. Notes are for things nobody else is keeping. That is the next section.

Privacy: anything saved between sessions is personal data about students. Ask your instructor what the makerspace is allowed to store before you design this part.

Notes as memory 4 min

Structured note-taking means the agent regularly writes notes to storage outside the context window and reads them back later. Anthropic's examples: a coding agent keeping a to-do list or a NOTES.md file, and Claude playing Pokemon, which kept tallies and maps and, after its context was reset, read its notes and carried on (context engineering).

Anthropic's memory tool is this pattern as a feature. It is file-based and client-side: Claude asks to read or write files under a /memories folder, and your application carries out those operations against storage you control (memory tool docs). It is the agent loop again: the model asks, the program acts, the result comes back. Memory is just another tool.

What makes a good note? Short, specific, and useful to a reader who has none of the earlier conversation. A weak note: "Student asked about the printer." A strong note: "Priya, 3D printer: asked about PETG on the Prusa; manual p. 14 says bed 80 C; she will book Fri 2 pm." The strong one lets the next session resume without reconstructing anything.

A caution that you can defend at review: notes are written by a model and can be wrong. Treat them as hints and keep the system of record (the booking calendar, the training database) as the authority.

Retrieval as memory 6 min

The manuals raise a different problem. They are long, they change rarely, and no single question needs more than a page. The answer is retrieval: look up the relevant piece and put only that into the context. When you use the retrieved text to help the model write its answer, the technique is called retrieval-augmented generation, or RAG.

The basic pipeline

  1. Chunk. Split each manual into pieces of a few hundred tokens.
  2. Index. Convert each chunk to an embedding, a list of numbers that captures its meaning, so that chunks with similar meaning sit close together. Store them in a searchable database.
  3. Search. When a question arrives, find the most similar chunks and add them to the prompt.

This is described in Anthropic's Contextual Retrieval post, which also notes two limits. First, embeddings capture meaning but can miss exact matches; a keyword method called BM25 is better for exact strings such as an error code like "TS-999". For your manuals, think of a question about "error E-41": the keyword search finds that exact code while a meaning-based search might return generic error text. Combining both works better than either. Second, chunking loses context: a chunk reading "Set the bed to 80 C" does not say which machine or material it is about.

The same post's fix is to prepend a short description of where the chunk comes from before indexing it, and it reports that this cut failed retrievals by 35% (embeddings alone) to 49% (with keyword search too), measured on the top 20 chunks. Those numbers are from Anthropic's own tests on their datasets, so treat them as a sign of direction and test on your own manuals.

A cheap version of the idea suits a student team: when you chunk a manual, store the machine name and section heading with each chunk, and put them in the chunk's text.

The agent can search, too

Retrieval need not happen before the model starts. With just-in-time retrieval, the agent keeps lightweight pointers, like file names or saved queries, and uses tools to load data only when it needs it. Anthropic notes the trade-off: runtime exploration is slower than having data up front and needs good tool guidance, so a mix can suit some tasks (context engineering). For you, that means a search_manuals(machine, query) tool whose description tells the model when to use it.

A common mix-up

"If my knowledge base is small, I still need a retrieval system." Not necessarily. The Contextual Retrieval post says that a knowledge base under 200,000 tokens, about 500 pages, can simply be put in the prompt, and prompt caching makes that faster and cheaper. Retrieval earns its place when the material is larger than that, or when including it all would cost too much on every call. Check how big your manuals really are first.

Worked example and practice 6 min

Worked example

A student writes: "I want to cut 6 mm acrylic on the laser cutter on Friday afternoon. What settings, and am I cleared?" Decide where each piece of information lives.

  1. List the facts needed. Settings for 6 mm acrylic; Friday afternoon availability; the student's clearance.
  2. Settings: manual text, long and rarely changing. Use retrieval. The model calls search_manuals("laser cutter", "6 mm acrylic settings") and only the best chunk enters the context. The whole manual stays out.
  3. Availability: changes constantly. Use a tool over the live calendar. Never save it in notes, because the note would be stale by the time it is read.
  4. Clearance: a fact another system already tracks. Use a lookup tool on the training record, as in the sessions section.
  5. The student's preference for brief answers: nobody else stores it. A saved note, read at the start of the session.
  6. Check the window. The context holds the system prompt, tool definitions, the question, one manual chunk, a few calendar slots, a yes/no on clearance and a one-line note. It stays small, so calls stay cheap.
Your turn

A student writes: "Last week you told me to wait for the resin printer to cool before removing the part. How long was it, and can I book it for Tuesday?" Step 1 is done for you: the facts needed are the cooling time, what was said last week, and Tuesday's availability. Now do steps 2 to 4 yourself: for each fact, name where it lives (retrieval, live tool, saved note or the context already) and one reason.

Show a solution

Cooling time: retrieval from the printer manual, since it is stable manual text; this also fixes any doubt about what was said last week, because the manual is the authority. What was said last week: nothing in the new context holds that conversation; it exists only if the program saved a note, so the assistant should not pretend to recall it, and should answer from the manual. Tuesday's availability: a live calendar tool, because it changes and the note would go stale.

The lesson in the example is that the assistant cannot claim to remember last week unless you built a note for it.

Summary 2 min

  • The context window is all the text the model sees on one call, reply included. It is finite, costs tokens on every call, and recall gets worse as it fills.
  • Between steps, only what the program re-sends carries over, so the context grows each step. Control it with small tool results, clearing old results and compaction.
  • Between sessions, nothing carries over unless you save it: use lookup tools for facts other systems own, and notes for what nobody else stores.
  • Retrieval puts only the right manual chunk in the context. Use keyword plus embedding search, keep machine and section with each chunk, and skip retrieval if the whole knowledge base is small.
