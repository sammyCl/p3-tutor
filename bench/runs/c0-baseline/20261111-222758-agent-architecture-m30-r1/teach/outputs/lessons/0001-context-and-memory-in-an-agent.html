Context and memory in an agent

By the end of this lesson you can say exactly what your makerspace assistant sees on each step, what it forgets when a session ends, and which of three tools (the context window, retrieval and notes) to use for each thing it must know.

Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, all on a small model budget. Both of those are context-and-memory decisions, and you will have to defend them at your design review.

Warm-up 2 min

Before new material, pull two things from memory. Try to answer in your head before you open the answer.

Recall

In the agent loop, a tool has just been run for the model. Who ran it, and what happens to its result next?

Check your answer

The program around the model ran it, not the model. The program then puts the result into the model's next input and calls the model again. Today's whole lesson is about that phrase, "the model's next input": what is in it, how big it gets, and what happens to it when the session ends.

Recall

A student asks, "Is the laser cutter free tomorrow, and do I need training?" The model requests three tools one after another and then answers. How many times is the model called?

Check your answer

Four: one call per tool request, and one more to write the final answer. Remember this number. Every one of those four calls is a separate trip to the model, and each trip carries the context along with it.

The context window: what the model sees 6 min

Start with a concrete case. It is 4 pm and a student types into your assistant: "What feed rate should I use to cut 3 mm acrylic on the laser cutter?" The model has to answer that one question. What does it actually receive?

Not just the question. It receives a block of text made of several parts, and nothing else. The model cannot look at your database, your files or yesterday's chat. If it is not in that block, the model does not know it.

That block is the context: all the text the model is given for one call. The context window is the limit on how much text fits in it. Anthropic's docs call it the model's “working memory”, and note that it is different from the large body of data the model was trained on (Claude docs: Context windows). The window is counted in tokens, the small chunks of text a model reads and writes; a token is roughly three-quarters of an English word, so 1,000 tokens is about 750 words.

The docs list what counts toward the window: the system prompt, every message including tool results, your tool definitions, and the reply the model writes. (The system prompt is the standing instructions you write once, such as “You are the makerspace assistant. Be brief. Never book without confirming.”) Here is the makerspace assistant's context at the start of a request:

Two facts about the size of the window matter for your project. First, current Claude models have windows of up to a million tokens, which is several thousand pages of text, so the limit is rarely the first problem. Second, the docs warn that “more context isn't automatically better”: as the token count grows, accuracy and recall degrade, a phenomenon called context rot. Anthropic's engineering team describes the window as a finite “attention budget” and says the goal is the smallest set of high-signal tokens that gets the job done (Anthropic: Effective context engineering for AI agents).

Window sizes change with each model release. Look up the current number on the models overview page before you put one in a design document.
A common mix-up (M7)

“With a million-token window, I can paste the whole manual into every request and be done.” It is tempting because it would work in principle: the manual fits. But you pay for every token on every call, and the model finds a fact less reliably in a huge pile than in a short, relevant passage. A big window sets what is possible, not what is wise. We will fix this with retrieval in section 5.

Check yourself

Your assistant's Python program holds a variable student_id = "S-4471". On step 3 of a request, which of these does the model not see?

Show the answer

The program's variable. The model sees only the text the program puts in the context: system prompt, tool descriptions, messages and tool results. Anything else, including variables, files and databases, is invisible until your code puts it into that text.

What is kept between steps 6 min

Now the surprise. Back in lesson O1 you learned that every step of the loop is a separate model call. The model keeps nothing from one call to the next. So how does it “remember” what happened a step ago?

It doesn't. Your program does. On every step the program sends the entire conversation so far: the system prompt, the tools, the question, every earlier model request and every tool result. The Claude docs describe it as progressive accumulation: each turn's input contains all previous history plus the new message, and the model's output becomes part of the input for the next turn. Think of a colleague who falls asleep after every sentence. To keep the conversation going, you hand them the full transcript each time they wake up.

Here is that in numbers. The student asks, "Is the laser cutter free tomorrow, and what feed rate for 3 mm acrylic?" Suppose the model calls check_calendar (result: 400 tokens) and then search_manuals (result: 3,000 tokens, the pages found), and then answers.

Worked example: counting input tokens

Start: system prompt 800 + tool definitions 600 + question 30 = 1,430 tokens. Each tool request the model writes is about 50 tokens.

  1. Call 1 input: 1,430. The model writes a request for check_calendar (50 tokens).
  2. Call 2 input: 1,430 + 50 + 400 (calendar result) = 1,880. The model writes a request for search_manuals (50 tokens).
  3. Call 3 input: 1,880 + 50 + 3,000 (manual pages) = 4,930. The model writes the final answer.
  4. Total input over the request: 1,430 + 1,880 + 4,930 = 8,240 tokens, though the unique text is only about 4,900.

The reason to do this by hand: the 3,000-token result is paid for on call 3. If a fourth call followed, it would be paid for again. Big tool results are expensive for every step after they arrive.

Prompt caching can make the repeated part cheaper, but the docs are explicit that it “changes what you pay for those tokens, not whether they count” toward the window (Claude docs). Treat it as a discount to apply later, not a reason to ignore size.
Check yourself

You change search_manuals to return one page (800 tokens) instead of five (3,000 tokens). What is the effect on a request that makes six more tool calls after it?

Show the answer

The third option. A result that enters the context is resent on every later call, so shrinking it saves its difference once per later call, not once.

This gives you your first cost lever for the budget: keep tool results small. Return a few relevant passages, not whole pages; return the three calendar slots asked about, not the whole month. Anthropic's advice for tools is the same: make them token-efficient (context engineering post).

A common mix-up (M3)

“The model remembers the conversation, so the program doesn't need to resend it.” It is tempting because chat apps feel like talking to someone who remembers. Underneath, the app is resending the history for you. If your own program forgets to include an earlier message, as far as the model is concerned it never happened.

When the window fills up 4 min

A makerspace question usually takes three or four steps, so the window will not fill. But an agent that works for hundreds of steps will fill any window, and quality drops before it is full because of context rot. Three standard moves, from lightest to heaviest (Anthropic: context engineering):

MoveWhat it doesMakerspace use
Clear old tool resultsDelete a result once the model has used it; keep the fact it found.Drop the 3,000-token manual pages after the model has written down the feed rate.
CompactionAsk the model to summarise the conversation and start a new window from the summary.A long booking chat with many back-and-forth changes.
Sub-agentsA helper works in its own clean window and returns only a short summary.Not yet needed; we cover when it pays off in a later lesson.

The hard part of compaction is deciding what to keep. Anthropic suggests aiming first for keeping everything that might matter, then trimming (context engineering post). The Claude platform now offers server-side compaction so you need not write it yourself.

For your assistant, the practical conclusion is modest: set a step limit, keep tool results small, and you will rarely need these. Know the moves exist so you can answer when a reviewer asks “what happens in a very long conversation?”

What is kept between sessions: notes 6 min

A session is one conversation: from the student's first message to the moment the chat is closed. When it ends, the context is gone. The model is not changed by the chat, and nothing is stored unless your program stores it. Tomorrow, a new session starts with only the system prompt and tool definitions.

So how can the assistant know that Priya passed the laser-cutter safety training last month? Only if that fact is stored somewhere outside the model and brought back into the context. That outside store is memory in the sense that matters for agents. The simplest form is notes: text the agent writes to a file or database through a tool, and reads back later. Anthropic calls this structured note-taking, or agentic memory: the agent writes notes to storage outside the window and pulls them back in when needed. Their example was a model playing a game that tracked progress across thousands of steps and, after its context was reset, read its own notes to carry on (context engineering post).

Notice the rhythm. Memory is not one thing; it is a write step and a read step, and you design both. For the makerspace:

  • Write: when a staff member signs a student off, the assistant (or the booking system) records S-4471: laser cutter, trained, 2026-10-02.
  • Read: at the start of a session, or through a get_training_record tool, that line is loaded into the context.

Anthropic's API has a ready-made version, the memory tool, which lets the model create, read and update files in a folder that your program controls. You do not need it for a first design: a database table keyed by student ID plus one read tool is memory too. What matters is the idea.

A common mix-up (M3)

“A bigger context window gives the assistant memory between visits.” A window only holds one session's text. When the session ends, the window is empty again, however large it was. Memory between sessions needs storage outside the window.

A caution on privacy and trust: notes about students are personal data, and anything the program loads from storage goes into the model's context. Store only what the assistant needs, such as training status, and not chat transcripts. Decide with your team who may see or delete a student's record.

Retrieval: finding the right page 5 min

Notes cover what the assistant learned about a student. The manuals are a different kind of memory: a large, stable body of knowledge that does not fit comfortably in every request. Pasting it all in is the mix-up (M7) from section 1. The fix is retrieval: keep the documents outside the context, and bring in only the few passages relevant to this question.

Concrete case: the student asks about feed rates for 3 mm acrylic. The manual for the laser cutter has 120 pages. Retrieval works like this:

  1. Beforehand, split the manual into passages (a page or a section each) and store them in a searchable index.
  2. The model is given a search_manuals(query) tool. It writes a query such as “laser cutter acrylic 3 mm settings”.
  3. The program searches the index and returns the top few passages, say 800 tokens in total.
  4. Those passages enter the context as a tool result. The model reads them and answers, ideally naming the page.

This is the loop from lesson O1 again; retrieval is just a tool. Two common ways to search the index, both worth naming in your design review: keyword search matches the words in the query, and embedding search matches meaning, so “how fast to cut thin plastic” can find a page that says “acrylic feed rate”. Many systems use both. Choosing between them is a design decision for later; today it is enough to know they exist.

Anthropic describes two timings. Pre-retrieval loads relevant data up front, before the model starts. Just-in-time retrieval keeps light references, like page titles or file names, and lets the agent load the details with tools when it decides it needs them. They recommend a hybrid: preload what is stable and always needed, and explore the rest on demand (context engineering post).

A common mix-up (M8)

“Retrieval means the model reads the whole manual and picks out what it needs.” No: the model never sees the manual. It sees only the passages the search returns. So if the search misses the right page, the model cannot answer correctly from it, however good the model is. When the assistant gives a wrong feed rate, check what the search returned before you blame the model.

Check yourself

A student asks, “Why does the 3D printer's first layer keep peeling?” The assistant answers vaguely and cites nothing. What should you inspect first?

Show the answer

The passages the search returned. Retrieval quality sets the ceiling on answer quality, so read the tool result first.

Worked example and practice 6 min

Worked example: where does each fact go?

For each thing the assistant must know, choose one: system prompt, conversation context, notes, or retrieval.

  1. “Never book more than 4 hours at a time.” A rule for every request, short and stable: system prompt.
  2. “The student asked for Friday, then changed to Saturday.” Belongs to this conversation only: it lives in the context and is gone when the session ends. Nothing to store.
  3. “Sam finished the router training on Oct 9.” Specific to a person, needed in future sessions: notes (a record), read when Sam returns.
  4. “The router's maximum plunge depth.” Part of a long manual, rarely needed: retrieval, found by a search tool when asked.

The test for each: how long must it live, and how big and how specific is it? Short, always-needed and stable goes in the prompt; one conversation stays in the context; per-person and lasting goes in notes; big, shared and occasionally needed is retrieved.

Show a solution

Part 1. (a) System prompt: a stable identity for every request. (b) Notes: specific to one person, and must survive across sessions (and a staff member should be able to update it). (c) Retrieval: shared reference information from a manual, needed only occasionally.

Part 2. Call 1: 1,500. Call 2: 1,500 + 50 + 200 = 1,750. Call 3: 1,750 + 50 + 1,000 = 2,800. Call 4: 2,800 + 50 + 400 = 3,250. Total: 1,500 + 1,750 + 2,800 + 3,250 = 9,300 tokens. Compare with the unique text, about 3,200: the rest is the cost of resending.

Summary 2 min

  • The model sees only its context: system prompt, tool definitions, messages and tool results, up to the window limit. More is not better; context rot makes long contexts less reliable.
  • Between steps, the model keeps nothing. The program resends the whole history every call, so every token that enters the context is paid for again on each later call.
  • Between sessions, nothing is kept unless it is written to storage outside the model. Notes are the write-then-read pattern for per-person facts.
  • Retrieval keeps big shared documents outside the context and brings in only the few passages a question needs; the model never sees what the search does not return.

Say it in your own words: without looking up, explain to a teammate why the assistant needs a notes store to remember a student, and why we don't paste the manual into every request. Use the words “context” and “session”.
