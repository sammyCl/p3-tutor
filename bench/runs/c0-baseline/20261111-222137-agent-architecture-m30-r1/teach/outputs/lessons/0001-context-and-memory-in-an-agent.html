Context and memory in an agent: what it sees, what it keeps, how it finds things

By the end of this lesson you can sort what your makerspace assistant needs into three places (its context, a notes file kept between sessions, and a search over the manuals) and give a reason for each.

Objective O3: context and memory in an agent About 30 minutes Builds on your work on the agent loop (quiz 0001)
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's preferences between visits, on a small model budget. Where each piece of information lives decides both whether the assistant gets it right and what each request costs. This is the design decision you will defend at your review.

Warm-up 2 min

Recall

From memory: in the agent loop, the model asks for a tool. Who actually runs the tool, and what happens to its result before the next step?

Check your answer

The program around the model runs the tool. It then puts the result into the model's next input and calls the model again. Today's question is what that "next input" contains, and what happens to it when the work stops.

Start with an everyday picture. You are working a problem set at a desk. Whatever is on the desk is what you can use right now. Your notebook is in your bag, and the textbook is in the library. You will see how each of those maps to an agent.

The context window: everything the model sees 5 min

Take one request to the makerspace assistant: "Is the laser cutter free tomorrow at 3 pm, and do I need training?" Before the model writes a single word, the program has to hand it text to read. That text is more than the question. It includes the assistant's instructions, the descriptions of every tool, the conversation so far, and any tool results.

Anthropic defines the context window as all the text a model can reference when generating a response, including the response itself, and calls it the model's "working memory" (Claude docs: context windows). It is a separate thing from the large body of data the model was trained on. The model cannot use anything that is not on the desk.

The window is measured in tokens: the small chunks of text, often a word or part of a word, that a model reads and writes. Both the limit and the price are counted in tokens. The docs list what counts toward the window: the system prompt, every message (including tool results, images and documents), and your tool definitions, plus the output the model writes (context windows).

Between steps: the context grows, and so does the bill 6 min

The model does not remember the last step. Each call is separate. What looks like memory inside a loop is the program re-sending everything so far. The docs describe it this way: each turn's input holds all previous conversation history plus the new message, and the model's response becomes part of the input for the next turn (context windows).

So the loop you already know has a hidden consequence. Each step adds a tool request and a tool result to the context, and the next call pays to read all of it again.

Worked example: the cost of one request

Assume the instructions plus tool list are 2,000 tokens and the question is 50. Each tool request is about 50 tokens. The calendar result is 300, the manual page 1,500 and the training record 200.

  1. Call 1 reads 2,000 + 50 = 2,050 tokens, and the model requests check_calendar.
  2. Call 2 reads those 2,050, plus the 50-token request and 300-token result: 2,400.
  3. Call 3 adds a 50-token request and the 1,500-token manual page: 3,950, so 3,950.
  4. Call 4 adds 50 + 200 for the training record: 4,200, and the model writes the answer.
  5. Total input read: 2,050 + 2,400 + 3,950 + 4,200 = 12,600 tokens, about three times the final window size of 4,200.

That ratio is why long loops get expensive: the total grows faster than the window does. Two things follow. Tool results should be small, and the loop should have a step limit (you saw why in the loop lesson).

Prompt caching can lower the price of re-reading unchanged text, but the docs are explicit that cached text still occupies the window: caching changes what you pay, not whether it counts (context windows).
A common mix-up

"A bigger window is always better, so just put everything in." It is tempting because modern windows are huge: current Claude models list up to 1M tokens. But more is not automatically better. Anthropic notes that as token count grows, accuracy and recall degrade, a phenomenon called context rot (context windows; see also Effective context engineering). And as the worked example showed, every extra token is paid for again on every later call. The goal is the smallest set of useful tokens, not the largest.

Between sessions: by default, nothing 4 min

A session here means one conversation or task, from the first message to the last. When it ends, the context is gone. The next session starts with the instructions, the tool list and the new question, and nothing else. The model itself is unchanged by talking to you: what it learned in training does not update from your chat.

Take a student who tells the assistant on Monday, "I finished the 3D printer training." If the assistant is built as a bare loop, on Thursday it has no idea. Nobody did anything wrong. Nothing was saved.

A common mix-up

"The assistant remembers earlier chats automatically." It is tempting because chat products feel like they remember you, and a person who helped you on Monday would. But that feeling comes from features someone built: a store of saved facts, loaded into the context. Anthropic's memory tool, for example, works only when your application provides the storage, and a later conversation continues from the same memory only when your handler serves the same store (memory tool docs). Memory between sessions is something you design.

Retrieval: finding the right page 5 min

Your manuals are long. The laser cutter manual alone might be hundreds of pages. Loading all of them into every request wastes tokens (section 2) and invites context rot. Instead the assistant should fetch only the passages that answer the question. Fetching information from outside the context and placing it in the context is called retrieval.

Anthropic's engineering post describes two timings (Effective context engineering for AI agents):

  • Before the model runs. A search step, often an embedding-based one (a way to find passages with similar meaning, not only matching words), pulls likely passages into the context up front.
  • Just in time. The agent keeps light references, such as file paths, stored queries or links, and loads data itself with tools when it needs it.

The post also describes a mix: some material loaded up front for speed, and more explored on demand. It cites Claude Code as an example of this mix, where a notes file is loaded at the start and search tools are used as needed.

In your design, retrieval is a tool like any other. You write search_manuals(machine, query), describe it clearly (the tool-description work from the loop lesson), and the model calls it with a request such as ("laser cutter", "focus lens cleaning"). Your program returns a few passages with their page numbers. Returning page numbers also lets the assistant cite its source, which matters for a safety manual.

One honest trade-off: just-in-time retrieval costs extra model calls, since each search is a step in the loop, and the post notes it is slower than retrieving up front. Retrieval can also miss. If the search returns the wrong passages, the model answers from them or reports it cannot find the answer, so your search quality limits your answer quality.

Notes: memory you write on purpose 4 min

Retrieval fetches information that already exists, like a manual. Notes are the other direction: the agent writes something down so a later session, or a later part of the same long task, can read it. Anthropic calls this structured note-taking: the agent regularly writes notes to memory outside the context window and pulls them back in later, as with a to-do list or a notes file (Effective context engineering).

Anthropic's memory tool is one concrete version. Claude can create, read, update and delete files that persist between sessions. It is client-side: Claude only requests a file operation, and your application runs it against storage you control and returns the result as a tool result (memory tool docs). That is the same loop you already know. The "memory" is a tool whose storage is a folder.

For your assistant, a note for one student might look like this:

/memories/students/riley.md
- Prefers confirmations by email, not text.
- Trained: 3D printer (passed). Laser cutter: not yet.
- Usually books evenings; asked about acrylic twice.

At the start of a session the assistant reads that file, which costs a few dozen tokens and gives it a head start. The docs also name risks that are yours to handle: keep memory files from growing without bound, delete files not used for a long time, and never let a path escape the memory folder (memory tool docs). A makerspace also has a privacy duty: notes about students should hold only what helps with bookings and training.

When the context fills up 3 min

Long tasks can still fill the window. Three standard remedies, all from the Anthropic sources:

  • Compaction: when a conversation nears the limit, summarize it and start a fresh window with the summary. The engineering post advises first maximizing what the summary keeps, then trimming (Effective context engineering).
  • Clearing old tool results: drop bulky results, such as an old manual page, once they have been used. The docs list tool result clearing under context editing (context windows).
  • Sub-agents: hand a focused job to a helper with a clean window, which returns only a short summary, often 1,000 to 2,000 tokens. Whether this pays off is the topic of a later lesson.

Notes and compaction work together. The memory docs advise using both for long-running agents: compaction keeps the active context small, and memory preserves the information that must survive summarization (memory tool docs). For a makerspace chat of a few turns you will probably need neither, so start with small tool results and a step limit.

Worked example and practice 8 min

Worked example: a three-bucket plan for one request

A returning student writes: "Book me the laser cutter Friday evening. Last time you said I still needed the safety class." Decide where each piece of information lives.

  1. List what the assistant needs. Its rules, the booking tool, Friday's calendar, the student's training status, the student's contact preference and the laser cutter's safety rules.
  2. Always needed, short: context. Rules and tool descriptions go in the instructions and tool list. They are sent on every call, so keep them tight.
  3. Large and already written: retrieval. The laser cutter safety rules live in the manual, so the model calls search_manuals and only the matching passages enter the context.
  4. Changes by the minute: a tool, then context. Friday's calendar and training status come from check_calendar and check_training_record at request time, because stored copies could be stale. Their results stay in this session's context only.
  5. Small and lasting, told by the student: notes. The contact preference goes in the student's notes file. At the start of the next session it is read back in.
  6. Check the cost. The window holds rules, a few passages, two short results and one small note, not the whole manual, so each call is cheap.
Your turn (part 1: tokens)

Show a solution

Call 3 reads 2,400 + 50 + 4,500 = 6,950. Call 4 adds 50 + 200: 7,200. Total = 2,050 + 2,400 + 6,950 + 7,200 = 18,600 tokens, about 48% more than the 12,600 before, because the big result is re-read on every later call. Returning fewer, better passages saves money twice.

Summary 2 min

  • The context window is everything the model reads for one call. The model keeps nothing between calls, so the program re-sends the history each step.
  • Because of that, cost grows faster than the window, and more tokens can hurt accuracy (context rot). Keep tool results small.
  • Between sessions nothing survives unless you save it. Memory is something you design.
  • Retrieval brings the right passages from long documents into the context. Notes carry small, lasting facts across sessions.

Say it in your own words: without looking, explain to a teammate why the assistant should not load the whole manual into every request, and where a student's contact preference should go instead.
