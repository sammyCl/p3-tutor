Context and memory in an agent

By the end of this lesson you can decide, for the makerspace assistant, what goes into the model's context on each step, what gets saved between a student's visits, and how it finds the right page in a long manual.

Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status. Both are context-and-memory decisions, and both decide how much each request costs on a small budget. You will defend these choices at your design review.

Warm-up 2 min

Recall

From the agent loop: in "Is the laser cutter free on Friday?", who actually runs the calendar tool, the model or your program? And how many model calls does one trip around the loop take?

Check your answer

Your program runs the tool. The model only writes a request for it. Each step of the loop is a separate model call. That second fact is the key to today: if every step is a separate call, then the model needs to be shown what happened so far each time.

What the model can see 5 min

The big idea first: a model has no memory of its own between calls. It only knows what is in the text you send it right now, plus what it learned in training. Everything the model can use on a given call has a name: the context window, all the text it can reference when generating a response, including the response itself. The Claude docs call it the model's "working memory" and separate it from the training data (Claude docs: Context windows).

Think of it like a function in Python. The model is respond(context). It has no global variables. If something is not passed in as an argument, the function cannot see it.

The window is measured in tokens, the small pieces of text a model reads and writes (a token is a word or part of a word). A window has a size limit, and for many current models it is up to 1 million tokens (same docs page). The docs say everything in the request counts toward it: the system prompt, every message, tool results, documents, and the tool definitions. The model's own output counts too.

Why every step re-sends everything 5 min

Because each loop step is a separate call, your program has to send the history again each time. The docs describe it this way: each turn's input contains all previous conversation history plus the new message, and the model's reply becomes part of the input for the next turn (Claude docs: Context windows).

Two costs follow, and both matter for your sponsor's budget.

  • Money. You are charged by tokens, and the history is input tokens again on every step. A big tool result is paid for on every later step of the run. Prompt caching can lower the price of repeated text, but the docs are clear that it changes what you pay for those tokens, not whether they count toward the window.
  • Quality. More is not better. As the token count grows, accuracy and recall get worse, which the docs call context rot. Anthropic describes the model's attention as a budget that every new token draws down, and says the goal is "the smallest possible set of high-signal tokens" (Anthropic: Effective context engineering).
The numbers below are invented to show the shape of the cost, not real prices or real page sizes.

Say a manual is 60,000 tokens and a request takes 5 loop steps. If you paste the whole manual into context, you send it 5 times: 300,000 input tokens for one answer. If you fetch only the 2 relevant pages, about 1,500 tokens, you send 7,500. Same answer, a fortieth of the input.

A common mix-up

"A bigger context window means I can paste everything in and stop worrying." It is tempting because a 1-million-token window sounds like unlimited room. But room is not the same as accuracy: recall degrades as the context grows, and you pay for every token on every step. A large window is a limit, not a goal.

The third option. Anything left in the history is input again on each later call, unless you remove or shorten it.

Keeping a long run small 5 min

So what is kept from step to step is whatever your program puts back into the next call. By default that is everything. To keep a long run healthy, you choose what to cut. Anthropic's context-engineering article names three tools for this (Anthropic: Effective context engineering):

  • Clear old tool results. Once the model has used a 4,000-token manual section, replace it with a short stub such as "section read." The article calls this one of the lightest forms of compaction.
  • Compaction: when a conversation nears its limit, summarize it and start a new window with the summary. Keep decisions and unresolved problems; drop redundant tool output.
  • Sub-agents. A helper agent explores in its own clean window and returns only a short summary. This is a preview of a later lesson on several agents.

The Claude API also offers server-side compaction and tool-result clearing, per the context-windows docs, so you may not have to build these yourself.

The rule of thumb: trimming is lossy. A summary can drop the one detail you needed later. Cut the things that are cheap to fetch again, such as a manual page, before the things that cannot be recovered, such as what the student decided.

Think it through

At step 4 of a run, the context holds: the student's request, a 3,000-token laser cutter manual section, the calendar result "Friday 2 to 4 pm free," and your own system prompt. Which would you shorten first, and why? Answer before you open it.

Check your answer

The manual section. It is the largest and it can be fetched again if needed. The calendar result is tiny and the final booking depends on it. The system prompt is needed on every call. Shortening the section saves tokens at almost no risk.

Notes that outlive the session 5 min

Everything so far lives inside one run. When the student closes the chat, the context window is gone. The model learns nothing from the visit, because using a model does not change it. So anything that must survive until the next visit has to be written down by your program and loaded again later.

This is memory in an agent: information stored outside the context window and brought back into it on purpose. Anthropic calls the simplest form structured note-taking: the agent writes notes to storage outside the window and reads them back later. Its examples are a to-do list and a NOTES.md file, and a game-playing agent that kept notes such as progress toward a goal across context resets (Anthropic: Effective context engineering). The docs make the same point for multi-session agents: design the saved state so that recovery is quick when a new session starts (Claude docs: Context windows).

For the makerspace, a record per student is a plain Python dict saved as JSON, much like the one you may have read in class:

{
  "student_id": "s1042",
  "trained_on": ["laser cutter", "3D printer"],
  "training_expires": {"laser cutter": "2027-01-15"},
  "last_booking": "laser cutter, Fri 2-4 pm"
}

At the start of a visit, your program loads this record and puts it in the context. During the visit, the model can ask to update it through a tool, and your program saves it. The record is short, so it costs few tokens, and it is accurate because it is structured.

A common mix-up

"The assistant learns from each conversation, so it will remember students on its own." It is tempting because chatbots feel like they remember. But the model does not change between calls. Any remembering you see is notes or history that a program saved and re-sent. If your assistant must know a training status, you must store it.

Finding the right page 5 min

Notes are one kind of memory. The manuals are another: a long, fixed body of knowledge that is too big to put in context. The answer is retrieval: find the few pieces relevant to the question and put only those in context. Putting retrieved text into the prompt is called RAG (retrieval-augmented generation), per the Anthropic contextual retrieval article.

The common recipe, as that article describes it:

  • Split each manual into chunks, small pieces of at most a few hundred tokens.
  • Turn each chunk into an embedding, a list of numbers that captures its meaning, and store them in a vector database.
  • At question time, embed the question and find the chunks whose embeddings are most similar.
  • Optionally also match exact words with BM25, a keyword-search method. This catches things like an error code "TS-999," which meaning-based search can miss.
  • Put the top chunks in the context, and let the model answer from them.

There are two ways to do the fetch. Up front, your program retrieves before the first model call. Just in time, you give the model a search tool and let it fetch when it decides to. Anthropic describes keeping lightweight references and loading content through tools only when needed, often mixed with some up-front loading; its example keeps a small CLAUDE.md file in context from the start and searches for other files on demand (Anthropic: Effective context engineering). Your assistant could do the same: keep the machine list in context and search the manual only when asked about one machine.

A common mix-up

"Retrieval always finds the right page if the manual is good." Chunks can lose their meaning. The article's example: a chunk says "revenue grew by 3% over the previous quarter" but never names the company or the quarter, so a question about one company's results may miss it. A manual chunk that says "set power to 40%" without saying which machine or material has the same problem. The article's fix is to add a short generated description of where each chunk comes from before indexing, which cut failed retrievals by 35% on its tests, and 49% when combined with BM25. Adding reranking brought it to 67%.

Worked example and practice 8 min

Worked example

A student writes: "Can I book the laser cutter Friday afternoon, and what settings do I use for 3 mm acrylic?" Walk through the memory decisions. Try each step's question first, then open the answer.

Step 1: what goes into the first call?

Show the answer

The system prompt, the tool definitions, the student's question and the student's saved record (training status). Not the manuals. Training status is short and decides whether booking is allowed, so loading it up front is cheap and safe.

Step 2: how does the manual settings page arrive?

Show the answer

The model calls a manual-search tool with something like "laser cutter acrylic 3 mm settings." Your program runs retrieval and returns the top two or three chunks as the tool result. The whole manual never enters the context.

Step 3: what does the calendar result cost?

Show the answer

Little, if the tool returns only the free slots for Friday afternoon, not the whole week. Tool results stay in context on every later step, so design tools to return short, useful answers (Anthropic recommends token-efficient tool output).

Step 4: what can be trimmed before the booking step?

Show the answer

The settings chunks, once the model has written the settings into its reply. They can be fetched again, so clearing them is low risk. Keep the free slot and the student's choice, which the booking call needs.

Step 5: what is saved at the end?

Show the answer

An update to the student's record: the new booking. Nothing else. The conversation and the manual text are not saved, since the first is not needed again and the second can be retrieved.

Your turn

Next week the same student writes: "I want to use the 3D printer on Tuesday, and my print keeps failing at the first layer." Steps 1 and 2 are given. Do steps 3 to 5 yourself.

  3. What should the assistant do about the booking, and what does that tell the model?

Show a solution

3. The record says no 3D printer training, so the assistant should not book the printer. The training status in context is what lets the model say so, and your program can enforce it too.

4. It can still help: search the 3D printer manual for first-layer problems and return the top chunks, as in step 2 of the example. Failing to book does not stop the help.

5. Probably nothing about a booking. You might add a note that the student asked about 3D printer training, if the team wants it. Do not save the manual text.

Summary 2 min

  • The model sees only its context window: the text in the current request. Each loop step is a new call, so the program re-sends the history.
  • More context means more cost and, past a point, worse recall (context rot). Aim for the smallest set of useful tokens.
  • Within a run, clear or summarize what can be fetched again. Between sessions, save only what cannot be rebuilt, such as training status.
  • Retrieval fetches only the relevant manual chunks. Check that chunks keep their meaning, and add keyword matching for exact terms.

Say it in your own words: without looking, explain to a teammate why the assistant should not paste the whole laser cutter manual into every call, and what it should do instead.
