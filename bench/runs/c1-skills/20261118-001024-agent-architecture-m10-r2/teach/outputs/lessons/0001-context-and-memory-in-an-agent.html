Context and memory in an agent: what the model sees, and what it keeps

By the end of this lesson you can say what the makerspace assistant's model sees on each step, what is lost between sessions, and which of three tools (context, retrieval, notes) to use for each kind of information.

Objective O3: context and memory in an agent About 10 minutes
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits. Both are memory decisions, and each decision changes what a request costs.

Warm-up 1 min

Recall

In the agent loop, who actually runs a tool such as "check the booking calendar": the model or your program? And is each step one model call or a continuous run?

Check your answer

Your program runs the tool. The model only asks for it. Each step is a separate model call. That second fact is the key to today: if every call is separate, the model knows only what you send it in that call.

What the model sees on every call 2 min

A model has no running memory between calls. It sees only the text you send. The context window is all the text the model can use when it writes a response, including the response itself; the Claude docs call it the model's "working memory" and separate it from the training data (Claude docs: context windows).

For an agent, that text has several parts. The docs list them: the system prompt, every message (including tool results and documents), and the tool definitions. Each turn sends all the earlier history again, plus the new message.

Why a fuller window is not a better one 1.5 min

Two reasons to keep the context small. First, you pay for the input tokens on every call, so a long history is paid for again at every step. Second, context rot: as the token count grows, the model's accuracy at recalling information in it falls (Anthropic Engineering). That post calls context "a finite resource with diminishing marginal returns" and says to aim for the smallest set of high-signal tokens.

A common mix-up

"The window is huge, so I will paste in all the machine manuals." It is tempting because it needs no extra design. But you would pay for every manual on every step, and the model would find the one relevant paragraph less reliably. Curating the context matters as much as its size.

How long each kind of information lives 1.5 min

Information in an agent lives at one of three levels. The table says what holds it and when it disappears.

LevelWhat holds itGone when
Between stepsThe message list your program resendsThe request ends, or the window fills
Between sessionsA file or database your program writesYou delete it
On demandA search over documents your program runsNever stored in context; fetched per question

When a long run nears the limit, one fix is compaction: summarize the history and start a new window from the summary (Anthropic Engineering). A new session, though, starts with an empty window unless you saved something.

Fetching one manual page on demand 1.5 min

Retrieval means keeping documents outside the context and giving the model a tool to pull in only the piece it needs, when it needs it. Anthropic calls this "just-in-time" retrieval: the agent keeps lightweight references, such as file paths, and loads content at runtime with tools. The trade-off is that exploring at runtime is slower and needs well-designed tools (Anthropic Engineering).

For you: a tool search_manual(machine, question) that returns the best two or three paragraphs, not the whole laser cutter manual. In computer science terms, the manual is on disk and the context is the working set.

Writing notes the next session can read 1.5 min

Notes are the other direction: the agent writes facts to storage outside the window and reads them back later. The same post calls this structured note-taking, with a to-do list or a NOTES.md file as examples, and describes an agent that resumes after its context resets by reading its own notes (Anthropic Engineering).

For you: a small record per student, such as "completed laser cutter safety training on March 3". It is short, it must survive between visits, and no search over a manual would find it.

Worked example and your turn 1 min

Worked example

A student writes: "Can I use the laser cutter Friday afternoon?"

Step 1: what is already in context?

Show

Instructions, tool descriptions and the question. Nothing else, so the model knows nothing about this student yet.

Step 2: what must be looked up in saved notes?

Show

The student's training status. Reading one small note is cheaper than keeping every student's record in context.

Step 3: what must be retrieved from the manual?

Show

Only the booking rules paragraph for the laser cutter, not the whole manual.

Step 4: what is saved afterwards?

Show

The booking and any updated status, as a note. The long manual text is dropped from the notes.

Your turn

A student asks: "What speed should I cut 3 mm plywood at, and did I finish my training?" Step 1 is done: the context holds only the instructions, tool descriptions and this question. Decide the rest: what is retrieved, what is read from notes, and what is saved.

Show a solution

Retrieve the plywood cutting-speed paragraph from the laser cutter manual. Read this student's training note. Save nothing new unless the answer changes their status, since this answer is not a fact about the student.

Summary 0.5 min

  • The model sees only the context sent on each call; your program does the remembering.
  • Bigger context costs more on every step and recalls worse, so curate it.
  • Retrieval brings in shared documents on demand; notes carry facts about one student across sessions.

Say it in your own words: why can the assistant greet a returning student knowing their training status, if the model remembers nothing?
