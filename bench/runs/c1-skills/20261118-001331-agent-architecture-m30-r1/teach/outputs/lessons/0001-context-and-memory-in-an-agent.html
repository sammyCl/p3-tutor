Context and memory in an agent: what it sees, what it keeps, what it looks up

By the end of this lesson you can say, for the makerspace assistant, what goes into the model's context at each step, what gets saved between a student's visits, and how it finds the right page in a long manual.

Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits. Both are context-and-memory decisions, and they drive the cost of every request. You will need to defend these choices at your design review.

Warm-up 2 min

Recall

In your own words: when the assistant wants to check the laser cutter's calendar, who actually runs the calendar lookup, the model or your program? And what happens to the result?

Check your answer

Your program runs it. The model only writes a request for the tool; your code carries it out and sends the result back to the model. Today's question is what that result joins: the model's context.

The window is everything the model reads 5 min

The context window is all the text a model can look at when it writes a response, including the response itself. Anthropic's docs call it the model's "working memory" and separate it from the training data, which is a different thing (Claude Platform Docs: Context windows).

Its size is counted in tokens, the small pieces of text a model reads and writes (a token is a word or part of a word). So the window is a limit on tokens.

Computer science comparison: think of the window as the RAM of one function call. Whatever is not passed in as an argument does not exist for that call.

The docs list what counts toward the window:

  • the system prompt (your standing instructions);
  • every message in the conversation, including tool results, images and documents;
  • your tool definitions (the descriptions of each tool);
  • the response the model writes, including any thinking.

That means a tool result, say a 40-page PDF section returned by a lookup, takes room just like a student's question does.

Modern models have large windows: the docs list 1 million tokens for many current models, and 200,000 for some older ones (same page). Bigger is not automatically better, though. The docs warn that as the token count grows, accuracy and recall degrade, which they call context rot. Anthropic's engineers explain it with an "attention budget": every new token spreads the model's attention thinner, and the decline is gradual, not a cliff (Effective context engineering for AI agents).

Window sizes change with each model release. When your team picks a model, read the current number off the vendor's models table instead of trusting a number from a lesson.
A common mix-up

"A bigger window means I can paste in everything and the model will use it." It is tempting because "fits" sounds like "works." But fitting is only the limit; quality drops as the window fills with material that is not relevant, and you pay for those tokens on every call (next section). The goal is the smallest set of useful tokens, not the largest.

Why every step re-sends the whole conversation 5 min

Here is the fact that explains agent cost. The model does not keep a running memory between calls. For each turn, the input contains "all previous conversation history plus the current user message," and the reply is added to the history for the next turn (Claude Platform Docs). Your program builds that list of messages and sends it again each time.

Recall that each step of the agent loop is a separate model call. So a request with five tool calls means six model calls, and each one re-reads everything before it.

What this means for your budget, in plain terms:

  • Cost per request grows faster than the number of steps, because each step is longer than the last.
  • A big tool result early in the loop is expensive: it rides along in every later call.
  • Prompt caching can lower the price of repeated text, but the docs are explicit that cached tokens still occupy the window (Claude Platform Docs). Caching changes the bill, not the room.
A common mix-up

"The model remembers what we said earlier, so I only need to send the new message." It feels that way in a chat app, because the app resends the history for you. When you call the model from code, you are that app. If you send only the new message, the model has no idea what came before.

Check yourself

A request makes four model calls. The tool result in step 1 is 3,000 tokens. Roughly how many times is that result read in this request?

Show the answer

In every later call. The history is rebuilt and re-sent each time, so a result kept in it is read each time.

Trimming the window mid-task 5 min

Since the window fills and costs grow, a long task needs a way to shrink what is kept. Anthropic's context-engineering article describes two:

  • Clearing old tool results: once the agent has used a result, drop the bulky raw text. The article calls this one of the safest, lightest forms of trimming.
  • Compaction: near the limit, summarize the conversation and start a new window from the summary. In Claude Code's version, the summary keeps decisions, unresolved bugs and key details, and drops repeated tool output.

Both appear in the platform docs too, as server-side compaction and context editing (Claude Platform Docs; Effective context engineering).

The trade-off is plain: whatever you drop is gone from the model's view. A summary that forgets the student's equipment choice means the assistant asks again, or books the wrong machine.

For the makerspace assistant, most requests are short ("is the laser free Friday?") and never need this. Design for the short case first, and add trimming only for long sessions.

Think it through

The assistant has read a 5,000-token laser cutter safety section to answer one question, and the student now moves on to booking. What would you keep from that section in later calls, and what would you drop?

Show a sample answer

Drop the raw 5,000 tokens. Keep one line with the answer that was given and the manual page it came from, so the assistant can cite it or fetch the page again if asked. This is clearing a tool result while keeping a pointer.

Notes that outlive the conversation 6 min

Everything so far lives inside one conversation. When the session ends, the window is gone. A new session starts with an empty window, so the model does not know the student, their training, or last week's booking.

Memory between sessions is therefore something you build outside the model. The simplest form is structured note-taking: the agent writes notes to storage outside the window and reads them back later. Anthropic's article gives examples: a to-do list, a NOTES.md file, and Claude playing a video game for thousands of steps, resuming after each context reset by reading its own notes (Effective context engineering).

For your assistant, the notes are a small record per student. In Python terms, a dict saved as JSON:

{
  "student_id": "s-1042",
  "trainings": {"laser_cutter": "2026-10-03", "cnc_router": null},
  "upcoming_bookings": [{"machine": "laser_cutter", "day": "Fri"}]
}

The rhythm of a session is then:

  • Start: your program loads the student's record and puts a short version in the context (or lets the model fetch it with a tool).
  • During: the agent works as usual. If something should be remembered, such as a completed training, it calls a tool that updates the record.
  • End: nothing needs to be "remembered by the model." The record is already saved.

Two design points matter for a design review:

  • Save facts, not transcripts. A full chat log reloaded every visit would flood the window. A few fields cost almost nothing.
  • Treat the record as the source of truth for permissions. Whether a student is trained for the CNC router should come from the saved record or the booking system, written by your code, not from the model's guess or a student's claim in chat.
A common mix-up

"Using a bigger window means the assistant will remember students next week." It sounds right, but a window only exists during a conversation. Remembering across visits needs storage outside the model, which your program loads at the start of each session.

Check yourself

A student finishes laser cutter training on Monday and returns Thursday. What makes the assistant know this on Thursday?

Show the answer

The saved record. Between sessions only what you stored outside the model survives.

Fetching one page from a long manual 6 min

The same idea of "keep it outside, bring in what is needed" solves the manual problem. Rather than pasting a whole machine manual into every request, store the manuals outside and retrieve only the passages that matter for this question. Putting retrieved text into the prompt so the model can answer from it is often called retrieval-augmented generation, or RAG (Introducing Contextual Retrieval).

Two ways retrieval can happen

  • Before the model runs: your program searches the manuals using the student's question and adds the best passages to the context.
  • As a tool the model calls: the model decides to search, reads the result, and may search again. This is "just-in-time" retrieval: the agent keeps light references, such as file names or queries, and loads content at runtime. Anthropic notes it is slower and needs good tool guidance, and that a mix often works well (Effective context engineering).

How the search finds the right page

  1. Split each manual into chunks, passages of a few paragraphs.
  2. Index them two ways: embeddings, which turn text into numbers so that passages with similar meaning end up close together, and BM25, a classic keyword-matching score that is good at exact terms such as a model number.
  3. At question time, find the closest chunks and return the top few.

There is a known weakness: a chunk can lose its context. A chunk saying "set it to 3 mm" does not say which machine it is about. Anthropic's fix, contextual retrieval, adds a short note to each chunk saying where it came from before indexing. In their tests, this cut failed retrievals (top 20 chunks) from 5.7% to 2.9% when combined with BM25, and to 1.9% with reranking, a second pass that re-orders the results (Introducing Contextual Retrieval). Those are their test numbers, not a promise for your manuals.

For you, the practical version is cheaper: tag every chunk with the machine name and section title when you split the manuals.

The same article says that if a knowledge base is under about 200,000 tokens (roughly 500 pages), you can include all of it in the prompt and skip retrieval. Your manuals may be that small. Compare that against the cost lesson above: sending 500 pages on every call is possible, but expensive.
A common mix-up

"Retrieval means the model searches its own memory of the manuals." The model has never seen your manuals. Retrieval is ordinary code searching your documents and handing the matching text to the model, which then answers from that text. If the right passage is not retrieved, the model has nothing correct to work from, and may guess confidently, like the outdated facts you have seen chatbots state.

Worked example and practice 8 min

The learner here is you, and the task is the assistant's memory design for one real request. Try each step before you open its answer.

Worked example

A returning student writes: "I need to cut 3 mm acrylic on the laser cutter Friday afternoon. What power setting, and can you book me?"

Step 1: what is in the context from the start?

Show the answer

The system prompt, the tool definitions (manual search, calendar check, booking), the student's short saved record, and the question. These are read on every call, so keep them short.

Step 2: how does the assistant find the power setting?

Show the answer

It calls the manual-search tool with something like "laser cutter acrylic 3 mm power." The search returns the top two or three chunks, each labeled with the machine and section, not the whole manual.

Step 3: what happens to that result afterward?

Show the answer

It stays in the window for later calls in this request, so it was kept small. If the session ran long, you could clear it and keep one line plus the page reference.

Step 4: how does it know the student may use the laser?

Show the answer

From the saved record loaded at the start (or a lookup tool that reads it), written by your code. The student's own claim in chat is not enough.

Step 5: what is saved for next time?

Show the answer

Only the new booking, added to upcoming_bookings. Not the chat, and not the manual text. The next session loads the updated record.

Your turn

A different student asks: "What's the maximum feed speed on the CNC router, and have I finished the router training?" Step 1 is given: the context starts with the system prompt, tool definitions, the student's saved record and the question. Now answer steps 2 to 5 yourself: where does the feed speed come from, where does the training answer come from, what stays in context afterward, and what (if anything) is saved?

Show a solution
  1. Feed speed: a call to the manual-search tool for the CNC router, returning a few chunks labeled with the machine. The model reads the number from the retrieved text.
  2. Training: from the saved record, which says cnc_router: null, so not completed. The assistant should say so and not book.
  3. Kept in context: the feed speed chunk, for the rest of this request only.
  4. Saved: nothing new. No facts changed in this conversation. (You might note the question for staff, but that is a product choice.)

Summary 3 min

  • The context window is everything the model reads in one call: instructions, tool definitions, messages, tool results and its reply.
  • The model keeps nothing between calls. Your program re-sends the history every step, so cost grows with each step, and big tool results are paid for repeatedly.
  • Mid-task, you trim by clearing old tool results or summarizing; whatever you drop is gone from view.
  • Between sessions, memory is notes you store outside the model and load at the start. Save facts, not transcripts.
  • Retrieval keeps long documents outside the window and brings in only the matching chunks, so labeling chunks well matters.
