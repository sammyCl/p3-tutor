Context and memory in an agent: what the model sees, what is kept, what is found

By the end of this lesson you can write a one-page memory plan for the makerspace assistant: what goes in the model's context on each step, what is saved between visits, and how it finds the right page of a long manual.

Why this matters for you

Your mission says you must decide what the assistant keeps in context, what it saves between sessions, and how it finds the right page in a long manual. It also says model usage has a small budget. Those are one decision seen from three sides, because everything the model reads costs money.

The model then either asks for another action or writes the final answer. The program runs the tool; the model only asks for it. Today's question is what the model sees in each of those calls.

Check your answer

One call, one page of text 8 min

Start with the big picture. A model has no memory of its own between calls. Each time your program calls it, the model sees only what you send in that call, reads it, and writes a reply. Nothing else is in its head.

The text it sees is called the context: the set of tokens included when the model generates a response (Anthropic, "Effective context engineering for AI agents"). A token is a small chunk of text, often a short word or part of a word, which is the unit the model reads and writes.

The context window is the limit on how many tokens can be in that context at once. Think of a function with a fixed-size argument buffer: whatever you want the function to know must be passed in, and it cannot take more than the buffer holds. A function also keeps no state between calls unless you pass the state back in, and that is the right way to think about a model call.

For an agent, the context on one call is built by your program from several parts:

  • Instructions: the system prompt, which says what the assistant is and how it should behave.
  • Tool descriptions: the name and description of each tool the model may ask for.
  • The conversation so far: the student's messages and the model's earlier replies.
  • Tool results: what came back each time a tool ran, such as calendar rows or a manual page.
A common mix-up

"The assistant remembers our conversation, because it is the same chat." It feels that way because the chat window shows the whole history. But the model does not hold it. Your program stores the history and sends it again on every call. If your program forgets to include an earlier message, the model has no way to know it ever happened.

Check yourself

A student told the assistant "I'm on the 3D printer" in message 1. Your program builds the call for message 5 and leaves message 1 out. What does the model know about the 3D printer?

Show the answer

Nothing. The model only knows what is in the context you send, so a message left out of the call is gone for that call.

What the next step inherits 7 min

Now connect this to the loop you already know. In the agent loop, each step is a separate model call. So what carries from one step to the next? Only what your program puts into the next call. In practice that is a list of messages that grows by two entries per tool use.

Here is the list for "Is the laser cutter free on Friday?", written as Python data, shortened:

messages = [
  {"role": "user", "content": "Is the laser cutter free on Friday?"},
  # call 1 ends here; the model asks for a tool
  {"role": "assistant", "content": [tool_request("get_bookings", day="Fri")]},
  {"role": "user", "content": [tool_result("9-11 booked; 1-5 booked")]},
  # call 2 sends all three entries above; the model writes the answer
]

The shape (a user entry, an assistant entry, a tool result entry) matches how the Messages API structures a tool loop, as the memory tool documentation shows when it describes the model's request and your application's tool_result reply. The point for you is the growth. Call 2 carries everything call 1 carried, plus two more entries. Call 3 would carry all of that plus two more.

That growing list is the working memory of the agent for one task: what is kept between steps. It is simple and it works well, and it is also where cost and quality problems come from, which is the next section.

"Working memory" here is a plain label for the message list during one task. It is not a special model feature, only a name for the list your program keeps and resends.
Check yourself

An agent uses three tools in a row to answer one question. How many messages does your program send on the fourth model call, counting the original question?

Show the answer

Seven. The question is one entry, and each tool use adds a request and a result, so three tool uses add six. All of it is sent again.

Why a long context costs more and works worse 8 min

You now see why your notes say you have heard of "context window" but could not say what it limits. It limits two things at once.

The hard limit: a window that can fill

If the list of messages grows past the window, the call fails or something must be cut. A manual page returned by a tool can be thousands of tokens, so a few lookups in one task can add up quickly.

The money limit: you pay for what you send

Model usage is metered in tokens, and because the whole list is resent on each step, a task with many steps pays for the early messages again and again. That is the reason cost per request matters for your budget: a ten-step task does not cost ten small calls, it costs ten calls that each carry everything before them. Check the current price list of whichever model you choose before you estimate, since prices change.

The quality limit: attention is finite

A larger window does not mean the model uses all of it equally well. Anthropic's engineers describe context rot: as the number of tokens in the window grows, the model's ability to recall information from that context gets worse. They treat the model's ability to focus as an attention budget that every new token draws on. Their advice is to aim for the smallest set of high-signal tokens that gives the outcome you want (Anthropic, "Effective context engineering for AI agents").

So there are three reasons to keep the context lean: it cannot exceed the window, each extra token costs money on every later step, and extra tokens can make the model worse at finding the one fact that matters.

A common mix-up

"If the window is huge, I can paste in every manual and stop worrying." It is tempting because a bigger window sounds like a bigger brain. But you pay for every token on every step, and a crowded window can make recall worse. A big window raises the ceiling; it does not remove the cost or the quality problem.

Check yourself

Your assistant loads all 40 manual pages into the context at the start of every request. Which is the best description of the problem?

Show the answer

Every step pays for all 40 pages, and a crowded context can make the model less reliable at finding the right line. Whether 40 pages fit depends on the window, but cost and quality are problems even when they do.

Trim, clear, summarize 7 min

A long task needs the context kept small as it runs. There are three common moves, from lightest to heaviest. All three are choices your program makes, so they are part of your design.

  • Clear old tool results. A manual page that helped in step 2 is rarely needed verbatim in step 9. Your program replaces it with a short stub such as "page 14 was read" or removes it. Anthropic describes clearing old tool results as one of the lightest and safest forms of trimming (Anthropic).
  • Summarize (compaction). When the context nears its limit, the conversation is summarized and a new context starts from the summary. The skill is deciding what to keep: Anthropic suggests first tuning for keeping everything important (recall), then removing the excess (precision) (Anthropic). The platform also offers this as a server-side feature, compaction.
  • Hand off to a helper with a clean context. A sub-agent explores in its own fresh context and returns only a short summary to the lead agent, which keeps the lead's context lean (Anthropic). Whether this pays off is the topic of a later lesson; for now note that it is another way of controlling what sits in one context.

Summaries lose detail. If the student gave a part number in step 1 and a summary drops it, the model cannot recover it. That is why some facts should be written somewhere safer than a summary, which brings us to memory between sessions.

Think, then check

The assistant read a 3,000-token manual page in step 2 and answered from it. It is now step 8 and the page is no longer needed. Which of the three moves is the lightest fix, and what would you leave in its place?

Check your answer

Clearing the old tool result is the lightest. Leave a short stub such as "read laser cutter manual, p. 14: focus procedure", so the model knows what it already looked at and can fetch the page again if it needs it.

What a new session starts with 5 min

A session is one conversation or task from start to finish. When it ends, your program drops its message list. The next time the same student opens the assistant, the new session's context holds the system prompt, the tool descriptions and the new question, and nothing about last week.

So for anything the assistant should know across visits, someone must save it outside the model and load it into the new context. For your assistant, two kinds of fact are involved, and they should be treated differently:

Kind of factExampleWhere it should live
Records the organization ownsThis student has passed laser cutter training. Booking times.A database or the booking system, read by a tool
Things worth remembering from conversationsThis student works in acrylic and prefers late evenings.Notes the assistant writes and reads

This split is my recommendation for your design, not something a source dictates, but the reason is concrete. Training status decides who may use a dangerous machine. It should come from the system that records training, through a tool call, and not from a note the model wrote and might have written wrong. Preferences are low stakes, so notes are fine.

Check yourself

Which fact is the best candidate for a saved note rather than a record in the booking database?

Show the answer

The evening preference. Bookings and training status are records that must be correct, so they belong in the system that owns them and are read by a tool.

Notes the agent writes and reads 8 min

The simplest memory between steps and between sessions is a file the agent can write and read. Anthropic calls this structured note-taking: the agent regularly writes notes that are kept outside the context window and pulls them back in at later times, such as a to-do list or a NOTES.md file (Anthropic).

As a developer you would not need anything special for this: give the model two tools, read_note and write_note, and run them in your program. The loop is the one you know. The only new thing is what the tools do.

Anthropic's API ships a ready-made version, the memory tool. Three facts from its documentation are worth knowing:

  • It is client-side: the model asks for a file operation such as view, create or str_replace, and your application runs it against storage you control. The model never touches the disk.
  • Claude is set up to check its memory directory first and to record progress as it works, because its context might be reset at any moment.
  • Safety is on you: your handler must refuse paths outside /memories, cap file sizes, and expire old files.
A common mix-up

"Memory means the model got smarter or learned from our chats." It is tempting because the assistant seems to recall you next time. But the model's weights are not changed. A saved note is only text that your program loads back into the next context. Memory is a tool and a file, not learning.

Think, then check

A student says, "Last time you told me my acrylic was too thick for the cutter." Nothing in the new context mentions it. Name two things that must have happened for the assistant to say something sensible.

Check your answer

First, last session something wrote a note about it to a store outside the model. Second, in this session something read that note and put it in the context: the model asked for it with a tool, or your program loaded it at the start. If either step is missing, the model has no idea.

Finding the right page in a long manual 10 min

Notes are small and written by the agent. A manual is large and written by someone else. For that you need retrieval: searching a store of documents for the few pieces that answer the question, and putting only those into the context. When the retrieved text is added to the model's input so it can answer from it, the technique is called retrieval-augmented generation, or RAG (Anthropic, "Contextual Retrieval").

First, ask whether you need it

Anthropic's advice is that if the knowledge base is smaller than about 200,000 tokens (roughly 500 pages), you may be able to put the whole thing in the prompt and skip retrieval, with prompt caching making that faster and cheaper (Anthropic). Be careful, though: that advice is about feasibility and speed, and the last section showed the quality and cost worries remain. For a small budget, measure both options on real questions before choosing.

How retrieval works, in order

  • Chunk: split each manual into pieces, usually no more than a few hundred tokens each.
  • Index: store the chunks so they can be searched.
  • Search: turn the student's question into a query and get the best-matching chunks.
  • Add to context: put those few chunks in the context, usually as a tool result.
  • Answer: the model answers from them, ideally naming the page.

Two ways to search, and why you may want both

MethodHow it matchesStrong atWeak at
EmbeddingsEach chunk becomes a list of numbers that captures meaning; similar meanings land close togetherQuestions worded differently from the manualExact strings such as error codes
BM25 (keyword)Ranks by matching words and phrasesExact terms like "Error code TS-999"Different wording of the same idea

The table follows Anthropic's description: embeddings can miss exact matches, BM25 finds precise words, and combining both with rank fusion works better than either (Anthropic). A makerspace manual has both kinds of question: "why is my cut burning the edges?" (meaning) and "what does error E07 mean?" (exact code).

A chunk can lose its meaning

When a manual is cut into chunks, a chunk can stop making sense alone. Anthropic's example is the chunk "The company's revenue grew by 3% over the previous quarter", which names neither the company nor the quarter. Their fix, contextual retrieval, adds a short explanation of where the chunk comes from to each chunk before indexing. In their tests the share of failed retrievals fell from 5.7% to 2.9% with contextual embeddings and BM25 combined, and to 1.9% when reranking was added (Anthropic). Those figures come from their own test data, so treat them as a sign of direction and not a promise for your manuals.

For your manuals the same problem shows up like this: a chunk that says "Set the speed to 40%" is useless if it does not say which machine and which material. A cheap fix you can do by hand is to start each chunk with its machine name and section heading.

Retrieval is also done by the agent itself

Retrieval does not have to happen before the model runs. Anthropic describes just-in-time retrieval: the agent keeps lightweight references such as file paths, stored queries or links, and loads content with tools only when needed. The trade-off is that exploring at run time is slower than reading ready-made indexes (Anthropic). For your assistant this might mean a search_manual(machine, query) tool and a read_page(machine, page) tool, so the model finds a page and then reads only that page.

Check yourself

A student asks, "What does error E07 mean on the vinyl cutter?" Which search is most likely to find the right chunk, and why?

Show the answer

Keyword matching, ideally combined with embeddings. An exact code is a precise string, which keyword search is good at, while embeddings cover the questions worded differently from the manual.

Worked example: a memory plan for one request 10 min

Now apply it all. Try each step yourself before opening the answer.

Worked example

A student opens the assistant and writes: "Book me the laser cutter on Friday afternoon, and remind me what focus height to use for 3 mm acrylic." It is the student's second visit. For each step decide where the information comes from.

Step 1: what is in the context before the model does anything?

Show the answer

The system prompt, the tool descriptions, and the student's message. Nothing from the first visit. Keep the system prompt short, since it is paid for on every step of every request.

Step 2: how does the assistant learn this student's earlier visit?

Show the answer

It reads the student's notes. Either your program loads a small note file into the context at the start, or the model calls a read-note tool first. Either way something outside the model supplies it. A note like "uses acrylic, prefers afternoons" is enough.

Step 3: where does the focus height come from?

Show the answer

Retrieval, not memory and not the model's own guesses. The model calls search_manual with "laser cutter focus height acrylic 3 mm", and gets back two or three chunks. A confident wrong number here could damage a machine, so it should be quoted from a chunk, with the page.

Step 4: how are the booking and the training check handled?

Show the answer

Both by tools that read the system of record: one checks this student's training status, one reads and writes the calendar. Neither is trusted to a note. The tool results stay in context only as long as they are needed.

Step 5: what gets saved when the session ends?

Show the answer

One short new note, such as "booked laser Fri pm; asked about acrylic focus". The manual chunk is not saved, since it can be found again. The booking is already saved in the calendar. Only what would otherwise be lost goes into notes.

Step 6: what would you cut if the run grew long?

Show the answer

The retrieved manual chunk, once the answer has been given: replace it with a stub naming the page. Keep the student's request, the booking confirmation, and the note. Cut what can be fetched again, keep what cannot.

Your turn: plan a returning student 9 min

Same method, with the steps faded. Write your answers on paper first.

Your turn

A student returns after two weeks and writes: "Can I use the band saw yet? Also, which blade do I need for 1-inch pine?" The assistant has one note from the last visit: "Student finished the laser cutter training; wants to learn the band saw."

Step 1 is done for you: the context starts with the system prompt, the tool descriptions, the student's question, and the saved note.

Now answer these four:

  • Step 2: How does the assistant find out whether the student has band saw training, and why not from the note?
  • Step 3: How does the assistant answer the blade question?
  • Step 4: What, if anything, should be written as a new note?
  • Step 5: The whole band saw manual is 60 pages. Do you load it all? Give one reason from cost and one from quality.
Show a solution

Step 2: call a training-status tool that reads the official record. The note only says what the student wanted two weeks ago; training may have changed since, and access to a dangerous machine must rest on the record.

Step 3: retrieve. Search the band saw manual for "blade 1 inch pine", read the top chunks, and answer from them with the page named. If nothing relevant comes back, say so rather than guess.

Step 4: a short note only for what would be lost, such as "asked about band saw blades for pine; working on a pine project". The training result is already in the record.

Step 5: do not load it all. Cost: every later step in this request would pay for 60 pages again. Quality: a crowded context can make the model worse at finding the one blade chart that matters. If the manual is under about 200,000 tokens you could, so compare both on real questions.

Summary 2 min

  • The model sees only the context in the current call, and your program builds it every time. Between steps, what is kept is the message list your program resends.
  • A long context costs more on every step and can lower recall, so keep it small: clear old tool results, summarize when needed, or hand work to a helper.
  • Between sessions nothing is kept unless saved. Records that must be right live in a system read by tools; soft facts can be notes the agent writes and reads.
  • Retrieval finds the few chunks of a long manual that answer the question: chunk, index, search (embeddings plus keywords), and put only the top chunks into context.

Say it in your own words: for the makerspace assistant, name one thing that stays in the context, one thing saved as a note, one thing kept in a database, and one thing retrieved, and say why each belongs there.
