Context and memory in an agent

By the end of this lesson you can decide, for the makerspace assistant, what goes into the model's context on each step, what gets saved between visits, and how the assistant finds the right page in a long manual.

Objective O3: explain context and memory in an agent About 60 minutes Builds on your work on the agent loop (learning record 0002)
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits. Both jobs are memory problems, and both cost money: every word the model reads is billed. At your design review you will need to say what the assistant keeps, what it saves, and why. This lesson gives you the vocabulary and a method to do that.

Warm-up 4 min

Spacing helps memory: try to pull earlier material out of your head before you read on. Answer in your head or on paper, then check.

Recall 1

In the agent loop, who actually runs a tool such as "check the booking calendar": the model or your Python program? What happens to the result?

Check your answer

Your program runs it. The model only writes a request that says which tool to call and with what inputs. The program carries it out and sends the result back to the model, and the loop repeats until the model gives a final answer or a limit is hit. Today's question builds on this: "sends the result back" means the result is added to the text the model reads, and that text has a size limit.

Recall 2

A language model produces text one token at a time. Without looking back: what is the one kind of input it uses to decide the next token, besides what it learned in training?

Check your answer

The text you give it on that call: the prompt. Whatever is not in that text and not learned in training is something the model cannot use. Hold that thought; it is the whole lesson in one sentence.

What the model can see on one call 7 min

Start with the big idea. A language model has no running memory of its own. Each time your program calls it, the model reads one block of text and writes a reply. If something is not in that block, the model does not know it.

That block has a name. The context window is the most text a model can read and write in one call. The text inside it is called the context. Both are measured in tokens: small chunks of text, roughly a short word or a piece of a longer word. A page of a machine manual is often several hundred tokens.

If you know computer science, the closest comparison is working memory in a program. The context window is like RAM for one function call: fast and directly usable, but small, and wiped when the call ends. Anything you want to keep longer has to go to something like a disk or a database.

What fills the window

On each call for the makerspace assistant, the context holds several parts. Anthropic's engineering team lists these components: system prompt, tools, examples, and message history (Anthropic: Effective context engineering). In plain terms:

  • The system prompt: your standing instructions ("You help students at the makerspace. Never book a machine for someone who has not passed its training.").
  • The tool descriptions: the name and description of every tool, such as check_calendar and book_slot. These are sent on every call, so each extra tool costs tokens every time.
  • The conversation so far: the student's messages, the model's earlier replies, and the results of tools already called.
  • Anything you load in: for example, a manual page you looked up.
A common mix-up

"The model remembers my last message." It is tempting because chatbots feel like they remember. They do not. Each call starts blank. The chat app (or your program) pastes the earlier conversation back into the context every time. If your program forgets to include the earlier turns, the model has no idea they happened. Ask yourself: where, in the text of this call, is the thing I expect it to know?

Why a bigger window is not a free pass 8 min

Two facts push you to keep the context small, even when the window is large. One is money and one is quality.

The money: you pay for what the model reads

Model usage is generally billed by tokens, both the ones the model reads (input) and the ones it writes (output). Because every call re-reads the whole context, a long context makes every call more expensive. Your sponsor's budget is small, so "how many tokens go in on each call" is a design decision, not a detail. I am not quoting prices here: they change, and comparing companies is outside your mission. Check the current price list when you start building.

The quality: more text can mean worse recall

Anthropic's engineers describe context rot: as the number of tokens in the window grows, the model's ability to accurately recall information from that context decreases. They say context must be treated as a finite resource with diminishing marginal returns, and they use the image of an "attention budget" that every new token draws down (Anthropic: Effective context engineering).

The practical goal they give is the smallest set of high-signal tokens that gets you the result you want. "High-signal" means text that actually helps with this request. A 40-page manual pasted in for a question about one setting is mostly noise.

Think of a search through a long log file. The one line you need is in there, but the more lines around it, the easier it is to miss. The model has a version of that problem.

A cost sketch with made-up numbers

The numbers below are invented to show the shape of the cost, not real measurements. Suppose your fixed parts are 1,500 tokens (system prompt plus tool descriptions), the student's question is 50, a calendar result is 300, and three manual chunks are 1,500. A request that takes three calls then reads:

  • Call 1: 1,500 + 50 = 1,550 tokens read.
  • Call 2: the same, plus the calendar result: 1,850 tokens read.
  • Call 3: the same again, plus the manual chunks: 3,350 tokens read.

The total is 6,750 tokens read for a request whose "new" content is only 1,850 tokens. About 70% of the reading is repeats. Two things follow. First, the fixed 1,500 is paid on every call, so trimming it helps every request. Second, if you clear the manual chunks as soon as they have been used, a fourth call would read 1,850 instead of 3,350.

Once you have a real token counter (your API's usage report will show input tokens per call), replace my numbers with yours. The design question stays the same: which parts are paid for on every call, and which could be dropped sooner?

A common mix-up

"If the window is huge, I can paste in every manual and be done." This is tempting because it is the simplest design, and for a small enough knowledge base it can be reasonable: Anthropic's retrieval post says that under about 200,000 tokens (roughly 500 pages) you can include the whole knowledge base in the prompt and skip retrieval (Anthropic: Contextual Retrieval). But you would pay to re-read it on every call, and recall can get worse as the window fills. Whether it fits is a question to answer by counting your manuals' tokens, not by assuming.

What carries over from step to step 8 min

Now connect this to the agent loop you already know. One request can take several model calls: ask for a tool, get the result, ask for another tool, answer. Each of those is a separate call. So how does step 3 know what happened in step 1?

Your program carries it. The program keeps a list of everything so far, often called the transcript or message history, and sends the whole list to the model on every step. Each tool result is appended to the list. This is the only "memory" inside a single request.

Your learning record 0002 noted one thing not yet checked: that each step is a separate model call run by the program. Figure 2 is that point drawn out. It is also why a long request costs more than the sum of its parts would suggest: early content is re-read again and again.

When the transcript gets too big

Two techniques from Anthropic's engineering post keep it in check (Anthropic: Effective context engineering):

  • Clearing old tool results. Once the model has used a big tool result (say, a whole manual page) and moved on, you can remove it from the transcript. The post calls this one of the lightest forms of compaction. Anthropic's context-management feature does this automatically for stale tool calls and results (Anthropic: context management).
  • Compaction. When a conversation nears the window limit, you summarize it and start a fresh window with the summary. The hard part, in the post's words, is the selection of what to keep versus what to discard. A summary that drops a detail the student needs later is a bug.

Deciding what stays in the transcript

Each item in the transcript has a job. A useful habit is to ask, for each one: will the model need this again in a later step? If not, it is a candidate to clear or shrink. For the assistant, a first pass might look like this:

ItemKeep, shrink or clear?Reason
The student's requestKeepIt is the goal; every step needs it
Calendar result for FridayKeep until the booking is madeThe booking step uses the exact open slots
Three manual chunksClear after the answer is writtenLarge, and the question is finished
A failed tool call and its errorShrink to one lineThe model should know it failed, but not re-read a long stack trace
Old chit-chat ("thanks!")Clear or summarizeNo later step depends on it

The risk is always the same: if you clear something the model needs, it may guess or ask again. So clear with a reason, and test with a few full requests to see whether the final answers get worse.

Both techniques are just ordinary program logic on a list. You could write "if the transcript is over N tokens, replace tool results older than the last three with a one-line placeholder" in a few lines of Python.

What survives after the session ends 8 min

A session here means one conversation, from the student's first message to when it is over. By default, when it ends, the transcript is gone. The next time the same student visits, the assistant starts blank: it does not know the student passed laser cutter training last week.

To fix this, you add memory that lives outside the model and outside the context window. Anthropic describes the approach as structured note-taking: the agent regularly writes notes persisted to memory outside of the context window, and reads them back later (Anthropic: Effective context engineering). Their memory tool does this with files: Claude can store and retrieve information outside the context window, and the files persist across conversations. It runs client-side through tool calls, and the developer chooses where the data is stored (Anthropic: context management).

In plain terms: memory is a file or database table your program owns. The model "remembers" only because a tool wrote something there earlier and something reads it into the context now.

Memory is a read and a write, both through your code

  • Write: at a good moment (a student passes training, a booking is made), a tool saves a short fact: {"student": "...", "trained_on": ["laser cutter"], "date": "..."}.
  • Read: at the start of the next session, your program looks the student up and puts the few relevant facts into the context.

Notice what that implies: the model does not decide by magic what to remember. You decide what is worth saving, and your tools do the saving. Keep notes short and structured, so that reading them back costs few tokens.

Three places something can live

WhereLasts forExample for your assistant

What to save, and what to leave out

Saving everything feels safe, but it creates two problems: reading it back costs tokens, and old notes can turn wrong. A good test for each possible note:

  • Will it matter in a later session? A training sign-off will. "The student said hello" will not.
  • Can it go stale? A note "the laser cutter is out of service" is true today and false next week. Either store a date with it, or do not store it and check the live source instead.
  • Is there already a source of truth? Bookings live in the booking calendar. Copying them into notes gives you two versions that can disagree. Read the calendar through a tool instead.
  • Is it personal? Notes about students are personal data. Save the minimum, and ask your university what rules apply before you build. I cannot tell you what those rules are.

A good first design for your assistant: a small record per student with only the trained machines and sign-off dates, kept by the program, with everything else read live from the calendar.

A common mix-up

"If I tell the assistant something, it learns it." Tempting, since people learn from being told. But telling the model puts text in this call's context; it does not change the model. Once the context is dropped, so is the fact. Only your own code writing to storage keeps it. This also matters for safety: the training status should come from the saved record your staff trust, not from whatever a student types ("I already passed").

Finding the right manual page 9 min

Notes are one kind of outside memory. The manuals are another: a large store of facts the model should read, but only the relevant part, per question. Retrieval means finding the pieces of a large store that matter for this request and putting just those into the context. Systems that do this before the model answers are often called RAG, for retrieval-augmented generation.

How a basic retrieval system works

Anthropic's retrieval post describes the standard approach (Anthropic: Contextual Retrieval). As steps:

  • Chunking: before any student asks anything, split each manual into small pieces, typically a few hundred tokens each.
  • Indexing: prepare each chunk so it can be searched. Two methods are common, below.
  • Searching: when a question arrives, find the best-matching chunks.
  • Loading: put the top few chunks into the context with the question, and let the model answer from them.

The two search methods:

  • Embeddings (search by meaning). An embedding is a list of numbers that represents the meaning of a chunk. Chunks with similar meaning get similar numbers, so a question like "how do I stop the plastic from sticking to the bed" can find a chunk titled "First layer adhesion" even though no words match.
  • BM25 (search by keywords). An older method that scores chunks by exact word matches. It is good at things embeddings can miss, such as an error code like "E-27" or a model number.

A hybrid system runs both, merges the results, removes duplicates, and sends the top chunks to the model. For the makerspace, that is a sensible default: students ask both in plain language and with exact error codes.

Retrieval can fail, and chunks can lose their context

A chunk cut out of a manual can lose its surroundings. A chunk that says "Set it to 40%" does not say which machine. Anthropic's post reports that adding a short, chunk-specific explanation to each chunk before indexing cut the share of relevant chunks missed in the top 20 results from 5.7% to 3.7% for embeddings, to 2.9% when combined with keyword search, and to 1.9% with a reranking step added (Anthropic: Contextual Retrieval). Those numbers come from Anthropic's own tests on their datasets, so treat them as a sign of direction, not a promise for your manuals.

Here is what that looks like with one invented manual sentence. A chunk on its own:

Set the power to 40% and the speed to 12 mm/s.

The same chunk with a label added before indexing:

Laser cutter manual, section "Cutting 3 mm acrylic":
Set the power to 40% and the speed to 12 mm/s.

A student asking about "laser cutter acrylic settings" now matches the second chunk by both meaning and keywords. The first one could belong to any machine. Anthropic generates such labels with a model; you can start by building them from the manual's own headings, which costs nothing.

How big should a chunk be?

There is no single right size; it is a trade-off you test. Very small chunks match precisely but may lack the surrounding sentence that makes them meaningful. Very large chunks carry the context but waste tokens when only one line mattered, and they bring back the noise problem from earlier. Anthropic's post describes typical chunks of a few hundred tokens, which is a sensible starting point. Then try twenty real questions and see whether the right chunk appears in the top three.

A cheap version of the same idea you can try: when you split a manual, put the machine name and section heading at the top of every chunk.

Another route: let the agent fetch on demand

Instead of searching ahead of time, the agent can keep lightweight references, such as file names or saved queries, and load the content with a tool only when needed. Anthropic calls this just-in-time retrieval, notes that folder names and timestamps help the agent judge what is relevant, and that it is slower than pre-computed search, so a mix of both is often best (Anthropic: Effective context engineering). For you, that could be a read_manual_section(machine, section) tool, with a short table of contents for each machine in the context.

A common mix-up

"Retrieval makes the model know the manuals." It does not. Retrieval only copies some text into the context for this call. If the search picks the wrong chunk, the model answers from the wrong text, and may do so with confidence. Retrieval quality is a design question: test it with real student questions and check whether the right chunk shows up.

Worked example: one booking request 7 min

Now put it together. A student at the front desk types: "Can I book the laser cutter on Friday afternoon, and what's the maximum thickness of acrylic it can cut?" You decide the context, step by step. Try each question first, then open the answer.

Worked example

Step 1: what is in the context at the start?

Before the first call, what does your program put in?

Show the answer

The system prompt, the tool descriptions, the student's message, and a short saved note about this student (their trained machines). Not the manuals. The training note matters because booking depends on it, and it is a few tokens.

Step 2: what does the first call produce?

The model sees the note says "trained on laser cutter". What does it ask for?

Show the answer

Two tool requests: check_calendar for Friday afternoon, and a manual lookup for acrylic thickness. Your program runs both. The model ran nothing.

Step 3: how does the manual lookup find the answer?

Which retrieval method suits "maximum acrylic thickness", and what comes back?

Show the answer

A hybrid search over the laser cutter manual, since the question has plain words ("thickness") and exact ones ("acrylic"). The top two or three chunks come back, each labelled with the machine and section. Those chunks go into the transcript.

Step 4: what does the second call see?

What is in the context for call two, and why does it cost more than call one?

Show the answer

Everything from call one, plus the calendar result and the manual chunks, because the program resent the transcript. More tokens in means a higher cost. This is why you keep chunks few and short.

Step 5: what happens to the manual chunks afterwards?

The answer is written and the student says "book 2 pm". What do you do with the chunks?

Show the answer

Clear them from the transcript. The thickness question is finished, and re-reading the chunks for the booking steps is wasted money. The calendar result stays, because it is still needed.

Step 6: what gets saved for next time?

The booking succeeds. What goes into memory?

Show the answer

The booking itself, written by the booking tool to the calendar, which is the source of truth. Optionally a short note like "asked about acrylic thickness", only if it will help later. Do not save the whole transcript: that is costly to reload and mostly noise.

Questions to bring to your design review 3 min

Your mission asks you to defend these choices. Here are the questions a reviewer could ask, with a sketch of the shape of a good answer. Try answering each aloud first.

  • "Why not paste all the manuals into every call?" Cost on every call, possible loss of recall, and it may not fit. Count the manuals' tokens and compare to the window before deciding.
  • "What does the assistant remember about a student, and where is it stored?" Name the fields, the store, who can change it, and what you chose not to save.
  • "How do you know it finds the right page?" Describe a test: real questions, the expected chunk for each, and the share found in the top few results.
  • "What happens in a long conversation?" Say when you clear tool results or summarize, and how you check that answers do not get worse.

If you cannot answer one of these yet, that is a useful list of what to build and test next.

Summary 3 min

  • The model only uses what is in the context window on this call, plus what it learned in training. It keeps nothing between calls.
  • Inside one request, your program carries memory by resending the transcript. That grows the cost of each step, so clear stale tool results and compact when needed.
  • Between sessions, memory is storage your code writes and reads: short, structured notes, loaded only when relevant.
  • Retrieval copies just the best-matching manual chunks into the context. Hybrid search (meaning plus keywords) covers plain questions and exact codes.
  • Aim for the smallest set of high-signal tokens: it costs less and, per Anthropic, can recall better.
