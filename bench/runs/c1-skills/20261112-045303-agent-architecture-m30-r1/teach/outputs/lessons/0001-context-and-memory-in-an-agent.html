Warm-up 2 min

Recall

In the agent loop, the model asks to use a tool, such as "check the booking calendar". Which part of the system actually runs that tool, and what happens to the result?

Check your answer

Your program runs the tool, not the model. The model only writes a request. The program then sends the result back to the model in another model call, and the loop repeats. Today's question is what that next call contains: the answer is the heart of context.

The context window: everything the model can see 5 min

A language model does not look things up while it writes. It only reads the text you hand it for that call. The context window is all the text the model can reference when generating a response, including the response itself. Anthropic's documentation calls it the model's "working memory", and says it is different from the large body of data the model was trained on (Context windows, Claude docs).

If you think in computer science terms, the window is like RAM: fast, directly readable, limited in size, and wiped when the program ends. Training data is more like a compressed archive the model was built from, which it cannot reopen.

The window is measured in tokens, the small chunks of text a model reads and writes (a word is often one to three tokens). Everything in a request counts toward the window: the system prompt, every message including tool results and documents, your tool definitions, and the output the model generates (Claude docs).

For the makerspace assistant, one call might hold:

  • the system prompt: the standing instructions ("You help students at the makerspace. Never book a machine for an untrained student.");
  • the tool definitions: the descriptions of check_calendar, book_slot and so on;
  • the conversation so far: the student's messages and the assistant's replies;
  • tool results: calendar rows, manual pages.
Check yourself

A student asks the assistant about a rule that is on page 40 of the laser cutter manual, but the page was never put in the request. What can the model do?

The third option. Without the page in context, the model can guess (and may sound confident, as you have seen with chatbots and outdated facts) or request a tool that fetches the page.

Between steps: the program resends the history 4 min

Here is the part that surprises most people. The model does not remember the previous step. Each call to the model is separate, and the context for that call is whatever your program puts in it. The docs describe it this way: each turn's input is all the previous conversation history plus the current message, and the model's output becomes part of the input for the next turn (Claude docs).

So in the agent loop you already know, the program keeps a list of messages. Each step does this:

  1. The program sends the whole list to the model.
  2. The model replies, perhaps with a tool request.
  3. The program appends the reply to the list, runs the tool, and appends the tool result.
  4. The program sends the longer list again.

In Python terms, the "memory" between steps is a list called messages that your code owns and grows. If your code forgets to append a tool result, the model never sees it.

This has a direct cost consequence for your budget. A long tool result, such as a whole manual chapter, does not cost you once. It sits in the list, so it is sent as input on every later step of that request. A short request that makes five tool calls reads the early messages five times. Anthropic's docs note that even with prompt caching, which changes what you pay for repeated tokens, cached tokens still occupy the window (Claude docs).

A common mix-up

"The model remembers what happened earlier in the loop." It is tempting because a chat feels like a conversation with a person who keeps track. But the model only sees what is in the current call. If your code trimmed the list and dropped the calendar result, the model would not know there had been one, and might call the calendar tool again. The memory between steps is your list.

Check yourself

An assistant request makes four tool calls, and the first tool result is a 3,000-token manual page. Roughly how often is that page read by the model during this request?

Show the answer

The third option. The page arrives with the first tool result, so calls 2, 3, 4 and the final one that writes the answer all include it. Anthropic's context editing can clear old tool results to avoid this (Claude docs).

Why a fuller window is not a better one 4 min

Windows are large now: many current models take up to one million tokens (Claude docs, sizes by model). It is tempting to think you can paste all the manuals in and be done.

There are two reasons not to. The first is accuracy. The docs say that more context is not automatically better: as the token count grows, accuracy and recall degrade, a phenomenon called context rot (Claude docs). Anthropic's engineering team describes the model as having an "attention budget": every added token uses some of it, so context is a finite resource with diminishing returns. Their goal is "the smallest set of high-signal tokens" that gets the result you want (Effective context engineering for AI agents).

The second reason is your budget: as you just saw, every token in the list is re-read on every step.

The practice of deciding what goes into the window at each step is called context engineering. It goes beyond writing a good prompt: it curates the whole set of tokens the model sees, including tool results and history (Anthropic Engineering).

When a long task approaches the limit, there are standard moves:

  • Clearing old tool results: drop bulky results the model has already used.
  • Compaction: summarize the conversation so far and continue in a fresh window that starts with the summary. Anthropic recommends first making sure the summary keeps everything important, then trimming what is not (Anthropic Engineering).
  • Sub-agents: give a side task to a separate model call with its own clean window, which returns only a short summary, often 1,000 to 2,000 tokens (same source). You will weigh when this pays off in a later lesson.
Compaction is lossy: a summary can drop a detail that matters later, which is why the next two sections move important facts out of the window altogether.
A common mix-up

"With a million-token window, I can put every manual in the prompt." It fits, but it costs input tokens on every step and buries the one relevant paragraph among thousands of irrelevant ones, which lowers recall. A small, well-chosen context beats a huge one.

Check yourself

The second option: fetch just the relevant section, when it is needed. That is just-in-time retrieval, covered below.

Between sessions: notes saved outside the window 5 min

The window is wiped when a conversation ends. If a student comes back next week, the model starts with an empty window and no knowledge of them. A session here means one conversation, from first message to last. To remember across sessions, the assistant needs memory: information stored outside the window, in a file or database your program controls, and read back in later.

This is the same idea as writing to disk. RAM is gone when the program exits, so anything that must survive goes to a file. Anthropic's engineering team calls the agent version structured note-taking: the agent regularly writes notes to persistent memory outside the context window, and reads them back at later times, such as a to-do list or a NOTES.md file (Anthropic Engineering). The workspace you are reading this in works the same way: your tutor reads NOTES.md at the start of each session.

Anthropic's memory tool is one concrete version. It lets the model create, read, update and delete files in a /memories directory that persist between sessions. It is client-side: the model requests a file operation and your application runs it against storage you control. When the tool is on, the model checks its memory directory before starting a task (Memory tool docs).

Notice that memory is just another tool in the loop you already know. The model asks "view /memories/riley.md", your program reads the file and returns the text, and the text lands in the context window. Memory is how information gets from storage into the window; it is not a second brain.

A good note is short and specific. Notes written this way can be reloaded cheaply, while a transcript of every past conversation would flood the next window. Anthropic's docs suggest a pattern for projects that span sessions: keep a progress log of what is done and what comes next, and update it before a session ends, so that the next session starts from a known state (Memory tool docs; see also Effective harnesses for long-running agents).

A common mix-up

"If I tell the assistant something, the model learns it." Chatting does not change the model; training does, and that is out of scope for you. A fact is remembered next week only if your program saved it and loads it again. Also, because your program controls the storage, you control privacy and retention: decide what a student's record may hold, and delete old files (the docs suggest periodic expiry).

Finding the right page in a long manual 4 min

Notes are for facts the assistant writes. The manuals are different: they are long, already written, and mostly irrelevant to any one question. For these the assistant needs retrieval: finding the few pieces that matter and bringing only those into the window.

Anthropic's term is just-in-time retrieval. Instead of loading all the data up front, the agent keeps lightweight identifiers, such as file paths, stored queries or links, and uses tools to load the content when it needs it. Names, folders and timestamps give the agent clues about what is relevant. The trade-off is that exploring at run time is slower than having everything ready, so a mix of up-front and on-demand loading is often best (Anthropic Engineering).

For your assistant, a plain design might be:

  • always in context: the system prompt and a short list of the machines and their manual section names (cheap, and it tells the model what exists);
  • a tool search_manuals(query) that returns the few best-matching sections, each with a title and a short excerpt;
  • a tool read_section(id) that returns one full section only when the model asks.

That is the same idea as an index in a textbook: scan the index, then turn to one page. How search_manuals ranks sections (keyword matching, or comparing meaning) is a design choice for you to research next; the context principle is the same either way: the search tool returns a small result, and the full text is loaded only for the sections that matter.

Your tool descriptions matter here, because the model decides from them when to search and when to read. Anthropic's advice is a small set of tools that do not overlap, since if a person cannot say which tool fits, the model cannot either (Anthropic Engineering).

Worked example and practice: one booking request 6 min

Now we combine the ideas. Each step asks a question first; try it, then open the answer.

Worked example

A student writes: "I'd like the laser cutter on Friday afternoon, and can you remind me what material I can't cut?" This is their second visit.

Step 1: what is in context on the very first call?

Try it, then reveal

The system prompt, the tool definitions, the student's saved notes (read at session start), and their message. Not the manuals, and not last week's chat.

Step 2: how does the assistant know the student is trained?

Try it, then reveal

From the saved notes, such as "laser cutter training: complete". Your program wrote that note last visit, and it was loaded into this session's context.

Step 3: what goes into the message list after a calendar check?

Try it, then reveal

The model's tool request, then the calendar rows for Friday. The program appends both, so the next call can read them. Keep the rows short: only Friday, not the whole month.

Step 4: how does it answer the material question without loading the whole manual?

Try it, then reveal

It calls search_manuals("laser cutter prohibited materials"), gets a few excerpts, and calls read_section on the best one. Only that section enters the window.

Step 5: what should be saved when the session ends?

Try it, then reveal

Only durable facts: the booking made, and perhaps a preference such as "prefers afternoon slots". Not the calendar rows (they go stale) and not the manual text (it is still in storage).

Summary 2 min

  • The context window is everything the model can read in one call. Outside it, the model sees nothing.
  • Between steps, the program resends the growing message list. That list is the memory, and its size is your cost.
  • A fuller window is not better: accuracy drops (context rot) and cost rises, so keep the smallest useful context.
  • Between sessions, only saved notes survive. They reach the window through a tool call.
  • For long manuals, keep them in storage and retrieve just the section needed, just in time.
