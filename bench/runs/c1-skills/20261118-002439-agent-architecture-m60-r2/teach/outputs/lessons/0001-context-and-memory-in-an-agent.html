Context and memory in an agent: what the model sees, what survives, and how it finds a page

By the end of this lesson you can decide, for the makerspace assistant, what goes into the model's context at each step, what gets saved between sessions, and how it finds the right page in a long manual.

Warm-up 3 min

You already know the agent loop. Before we add memory to it, pull it back from your own head. Answer in your own words first, then check.

Recall

A student asks, "Is the laser cutter free on Friday?" Write the loop as a short list: what does the model produce, what does the program do, and what goes back to the model?

Check your answer

The model is called and, instead of a final answer, asks for a tool, for example check_calendar(machine="laser cutter", day="Friday"). The program (not the model) runs that tool. The result, such as "booked 2 to 4 pm, free otherwise", is added to the conversation, and the model is called again. It repeats until the model writes a final answer.

Notice the phrase "the model is called again". Today's lesson is about what is handed to the model on every one of those calls.

Recall

A language model writes text one token at a time, from patterns learned in training. Does it learn anything new from your conversation while you talk to it?

Check your answer

No. Its learned patterns are fixed after training. Anything it appears to "know" about your conversation must be in the text it is given. That single fact explains almost everything below.

What the model actually sees 7 min

Start with the big picture. A model has no hidden notebook and no ongoing awareness. On every call it gets one block of text, reads it, and writes a reply. That block is its entire view of the world for that call.

The context window is all the text a model can reference when it writes a response, including the response itself. Anthropic's documentation calls it the model's "working memory", and distinguishes it from the large body of data the model was trained on (Claude API docs: context windows). Think of it like a function's arguments: the function can only use what you pass in.

Windows are measured in tokens. A token is a small chunk of text, often a word or part of a word. Tokens matter twice: they set the limit on how much fits (the window size), and they are what you pay for. Both limits and costs are counted in tokens, not pages or words. Current Claude models have windows of up to 1 million tokens, depending on the model (context windows).

So what is in the window? According to the docs, everything in the request counts: the system prompt, every message including tool results and documents, your tool definitions, and the output the model generates.

  • System prompt: your standing instructions ("You are the makerspace assistant. Never book a machine for an untrained student.").
  • Tool definitions: the name and description of each tool the model may call.
  • Messages: the student's question, the model's earlier replies and tool requests, and the tool results.
  • The new output: what the model writes this time.
The docs also note that thinking tokens, the model's reasoning text, count toward the window and are billed as output. You do not need that detail yet; just know that "what counts" is broader than "what the student typed".
Check yourself

Which of these is not part of the text the model reads on a call?

Show the answer

The database record. The model only reads what is placed in the request. A record becomes visible to the model only after a tool fetches it and the result is added to the messages.

Why every step costs more than the last 8 min

Now connect the window to the loop you already know. Each turn of the loop is a separate model call, and the program decides what that call contains. By default, it contains everything so far.

The docs describe it this way: as the conversation advances, each user message and assistant response accumulates in the context window, and previous turns are preserved completely. Each turn's input is all previous history plus the new message, and the model's output becomes part of the input for the next turn (context windows).

This means the model does not "remember" step 1 when it is on step 3. Your program re-sends step 1 inside the step 3 request. In Python terms, the program keeps a list called messages, appends to it after every step, and passes the whole list on every call.

messages = [{"role": "user", "content": question}]
while True:
    reply = call_model(system_prompt, tools, messages)   # sees everything so far
    messages.append(reply)                               # the model's turn is kept
    if reply is a final answer:
        break
    result = run_tool(reply.tool_request)                # the program runs the tool
    messages.append(tool_result(result))                 # the result is kept too

That pseudo-code is the whole trick: the "memory" within a task is just this list. It is also why cost climbs. You pay for tokens, and every call re-sends the earlier tokens as input.

A small picture of the growth

Say the system prompt and tool definitions are 2,000 tokens, the question is 50, each tool result is 1,500 and each model turn is 100. Here is roughly what each call reads:

CallWhat is in the inputInput tokens (approx.)
1setup + question2,050
2call 1 + model turn + tool result3,650
3call 2 + model turn + tool result5,250
4call 3 + model turn + tool result6,850

Four calls read about 17,800 input tokens in total, even though only about 6,000 tokens of new text were created. The numbers are invented to show the shape, but the shape is real: input grows with every step, so a long loop costs far more than the sum of its parts. Long tool results, such as a whole manual dumped into a result, are the usual culprit.

Prompt caching can make re-sent, unchanged text cheaper, but the docs are clear that cached text still occupies the window: caching changes what you pay for those tokens, not whether they count (context windows). It is a cost tool, not a way to get more room.
A common mix-up

"The model remembers the earlier steps, so only the new step costs anything." It is tempting because a chat feels continuous. But the model keeps nothing between calls. The earlier steps are there only because your program pasted them back in, and you are billed for them each time.

Check yourself

Your assistant takes 6 steps to answer one question. Compared with a 3-step answer, what happens to the input read on the final call?

Show the answer

It is larger. History accumulates and is re-sent, so a 6-step loop reads more on its last call than a 3-step loop does on its last.

Why a fuller window is not a better one 5 min

Windows are large. If one holds up to a million tokens, why not paste in every manual and skip the cleverness? Two reasons: cost, which you just saw, and quality.

Context rot is the drop in a model's accuracy and recall as the number of tokens in its window grows. The Claude docs say that more context is not automatically better, and that this makes curating what is in context as important as how much space there is (context windows). Anthropic's engineering team describes context as a finite resource with diminishing returns, and treats the model as having an "attention budget" that each new token uses up (Effective context engineering for AI agents).

An everyday comparison for a computer science student: RAM. Having a lot of RAM does not make a program fast if it is thrashing through junk. The goal that article states is to find "the smallest possible set of high-signal tokens" that makes the result you want likely. A high-signal token is one that helps the model with this task; noise is anything that does not.

A common mix-up

"With a million-token window, the assistant can just hold every manual." It might fit, but it would cost more on every call and risk worse answers, since the relevant paragraph is buried among thousands of irrelevant ones. Fit is not the same as useful.

Your turn

The laser cutter manual is 120 pages. A student asks only about the focus height. Give one cost reason and one quality reason not to put all 120 pages in the context on every call.

Show a model answer

Cost: all 120 pages are billed as input tokens on every call, and re-sent each step. Quality: the focus paragraph is a few lines among many pages, and recall gets worse as the window fills, so the model is more likely to miss or mix up details.

Trimming the window mid-task 8 min

The first memory question is about steps: what is kept from one step to the next within a single task? The default is "everything", and the previous two sections showed why that gets expensive and noisy. So agents manage the window on purpose. There are three common moves.

  • Clear old tool results. After the model has used a calendar lookup, the raw result rarely needs to stay. Anthropic's article calls clearing old tool results one of the lightest forms of compaction (context engineering), and the API docs list tool result clearing as a context editing strategy (context windows).
  • Compact. Compaction means summarizing a conversation that is nearing its limit and starting a new window from the summary. The article says to keep things like decisions and unresolved problems and drop redundant tool output, and to tune for recall first (do not lose something important), then precision.
  • Hand off to a helper with a clean window. A sub-agent can dig through lots of material in its own window and return only a short summary, which the article puts at roughly 1,000 to 2,000 tokens. You will meet this again when we reach multi-agent designs; for now, note that it is another way to keep the main window small.

The trade is the point. Every trimming move saves tokens and loses detail. If the summary forgets that the student is only trained on the 3D printers, the assistant may later offer a laser slot. That is why what you trim is a design decision, not a default.

Some chat products trim for you, for example by dropping the oldest messages first. With the raw API, the docs say the standard behavior is to accumulate previous turns completely, so trimming is your job (context windows).
Check yourself

An agent has compacted its conversation and then gives a wrong answer about a detail from step 2. What is the most likely cause?

Show the answer

The summary left the detail out. After compaction the model sees only the summary, so a missing detail is simply gone from its view.

What a new session starts with 5 min

The second memory question is about sessions: what is kept between one visit and the next? A session here means one conversation or task, from the first message to the last. When a student closes the chat on Monday and opens it on Thursday, your program starts a new messages list.

That new list is empty. Monday's conversation is not in it, and the model does not carry anything over, because the model keeps nothing between calls in the first place. The docs state the memory tool's purpose in exactly these terms: it lets the model store and retrieve information across conversations, in files that persist between sessions (Claude API docs: memory tool).

So the rule is simple, and it has a consequence worth stating plainly:

  • Within a task, the memory is the messages list your program keeps.
  • Between sessions, the memory is whatever your program saved outside the window and then loads back in.
  • If nothing was saved, nothing is remembered. There is no third option.
A common mix-up

"Once the assistant has been told a student's training status, the model has learned it." "Learned" here would mean the model's trained patterns changed. They did not. The fact lives only in text. If that text is not saved and re-supplied, Thursday's session knows nothing about Monday. Remembering is something your program does, not something the model does.

This is why the makerspace assistant needs a store of its own. A student's training status is a fact that must outlive any single conversation, and it must be right, because it decides whether a booking is allowed.

Check yourself

A student told the assistant on Monday that they finished the laser safety course. On Thursday the assistant asks them again. Which is the best explanation?

Show the answer

Nothing saved the fact. A new session begins with an empty window, so a fact survives only if the program stored it and loaded it back.

Notes the agent writes for later 8 min

The simplest memory that survives sessions is a note. Anthropic's article calls this structured note-taking: the agent regularly writes notes that are persisted outside the context window and pulled back in later. Its examples are to-do lists and a NOTES.md file, and it describes an agent that kept progress notes across context resets (context engineering). You are looking at the same idea right now: this workspace has a NOTES.md that your tutor reads at the start of every session.

Notes solve both problems from the last sections. They survive a new session, and they survive compaction, because they live outside the window. The cost is that they come back into the window when read, so they should be short and organized.

The memory tool: notes as files

Claude's API ships a ready-made version, the memory tool. The model asks to view, create, edit, delete or rename files under a /memories folder. The docs say it operates client-side: Claude requests the operation and your application runs it against storage you control, returning the result as a tool result (memory tool). That is exactly the loop you already know, with a file store as the tool.

Notice what the docs say about where it lives: memory is entirely in your application, so a later conversation continues from the same memory only when your handler serves the same store. And your code must restrict every operation to /memories to block paths like ../../secrets.env.

What deserves a note

  • Facts that must outlive the session: a student's trainings, preferences such as "prefers morning slots".
  • Progress on unfinished work: "booking half-made, waiting for the student to choose a time".
  • Decisions and why: so the next session does not redo the reasoning.

What does not deserve one: raw tool output, anything already available from a reliable system, and anything sensitive you would not want stored. The docs advise capping file sizes, expiring old notes, and adding checks for sensitive data before writing.

A common mix-up

"Notes the model wrote are as reliable as a database." A note is text the model chose to write, and it can be incomplete or out of date. For a fact that gates an action, such as "is this student certified for the laser?", store it in a system of record that your program checks, and let the model's notes carry softer context. This is a design judgment, not a rule from a source, so be ready to defend it either way at your review.

Check yourself

Who actually reads and writes the files when the model uses the memory tool?

Show the answer

Your application. The model requests, your code executes, and the data stays where you put it.

Finding one page in a long manual 9 min

Notes cover what the assistant learns. Manuals are different: they are large, they already exist, and the assistant must find the right part. Retrieval means fetching only the pieces of a large body of text that are relevant to the current question, and putting just those into the window. It is memory for reference knowledge rather than for experience.

First check: do you need it at all?

Anthropic's retrieval guide gives a size rule: if a knowledge base is under about 200,000 tokens (roughly 500 pages), you can put all of it in the prompt and skip retrieval, and prompt caching makes that faster and cheaper (Introducing Contextual Retrieval). Keep in mind the context rot point: fits does not mean best. But for a handful of short manuals, a simple design may win on both effort and budget.

How retrieval works when you do need it

The common pattern is called retrieval-augmented generation, or RAG. The same guide describes its parts (Contextual Retrieval):

  • Chunking: split each manual into small pieces, usually a few hundred tokens or fewer.
  • Embeddings: a separate model turns each chunk into a list of numbers, a vector, that encodes its meaning. Chunks with similar meaning get similar vectors, so a search can match "how high do I set the lens" to a chunk about "focus distance" even when the words differ.
  • Keyword search (BM25): a ranking method that finds exact words. It helps with unique terms like an error code, which meaning-based search can miss.
  • Combine and pass on: merge the results of both searches, take the top chunks, and add them to the prompt of the main model. The guide found that passing the top 20 chunks worked better than 5 or 10.

Where retrieval goes wrong

The guide points out that chunking can destroy context: a chunk reading "Set it to 40 percent" no longer says which machine or material it is about. Its fix, contextual retrieval, adds a short explanation of where the chunk comes from to each chunk before it is indexed. In Anthropic's tests, the share of cases where the right chunk was missing from the top 20 fell from 5.7 percent to 2.9 percent with contextual embeddings plus contextual keyword search, and to 1.9 percent with reranking added (Contextual Retrieval). Those are their test results on their data, so treat them as a sign of direction, not a promise for your manuals.

For your manuals, the same lesson is cheap to apply: when you chunk, keep the machine name and section title with every chunk.

Another way: let the agent fetch just in time

Retrieval need not be a fixed pipeline. The context engineering article describes just-in-time retrieval: the agent holds lightweight identifiers such as file paths or stored queries, and loads content with tools only when needed. It notes this is slower than pre-loading and needs good guidance, and that a hybrid works well: load a few things up front, fetch the rest on demand (context engineering). For you, that could be a search_manual(machine, query) tool that returns a few chunks, called by the model when a question needs it, which is just another tool in the loop.

A common mix-up

"Retrieval means the model looks things up in its training data." It does not. Retrieval is a program step that searches your documents and pastes the hits into the window. The model then reads them like any other text. If retrieval misses the right chunk, the model never sees it, and it may answer confidently from its patterns anyway. That is the outdated-but-confident answer you noticed in chatbots.

Check yourself

Your retrieval returns the wrong chunk for "what speed for acrylic?". Which fix goes after the actual cause?

Show the answer

Add the machine and section name to each chunk. The failure is in finding the chunk, so fix the index, not the model.

Which tool for which job 4 min

You now have four mechanisms. Each answers a different question, and your design review will ask which you used for what.

Notice the cost link. Each row is a way to keep tokens low: send only what this call needs, trim what it no longer needs, save what must last, and fetch what is large. That is how context design becomes cost design, which is what your sponsor's budget cares about.

Worked example: one student, two visits

Monday: a student asks, "Can I book the laser cutter Friday, and what focus height should I use for 3 mm acrylic?" Assume they are trained on the 3D printers but not yet on the laser cutter.

Step 1: what is in the window on the first call?

Show the answer

The system prompt (rules, such as "only book trained students"), the definitions of the tools (check_calendar, book_machine, search_manual, get_student_record) and the student's question. Nothing else: no manuals, since the model fetches them on demand.

Step 2: how does it learn the student's training status?

Show the answer

It calls get_student_record. The program reads the record store and returns "trained: 3D printers; laser: not trained". The status lives outside the window, so it enters only as a tool result. The assistant should now decline the booking and explain the training step.

Step 3: how does it get the focus height?

Show the answer

It calls search_manual("laser cutter", "focus height acrylic 3 mm"). Retrieval returns a few chunks, each labelled with machine and section, and they join the messages. The answer is based on that text, not on the model's patterns from training.

Step 4: what can be trimmed before the final answer?

Show the answer

If a step had returned a long calendar listing, the raw listing can be cleared once the free slots are noted. Keep the decision: "not trained on laser, booking declined". Dropping tokens that no longer matter keeps later calls cheaper and the window cleaner.

Step 5: what is saved for the next visit?

Show the answer

A short note, such as "asked for laser Friday; declined, needs laser training; wants 3 mm acrylic". The training status stays in the record store, which the training desk updates. The window is then discarded. On Thursday, the new session loads the note and the record, and does not need the Monday conversation.

Summary 3 min

  • The model sees only the context window on each call: system prompt, tool definitions, messages and its own output, all counted in tokens.
  • Within a task, memory is the message list your program resends each step. That is why cost climbs, and why trimming (clearing, compaction, helpers) is a design choice that trades detail for tokens.
  • A fuller window is not a better one: context rot means recall degrades as the window grows.
  • Between sessions nothing survives unless the program saves it outside the window: notes (such as the memory tool) for soft context, a record store for facts that gate actions.
  • Retrieval fetches only the relevant chunks of a big manual into the window; skip it if the whole knowledge base is small, and keep context with each chunk if you use it.
