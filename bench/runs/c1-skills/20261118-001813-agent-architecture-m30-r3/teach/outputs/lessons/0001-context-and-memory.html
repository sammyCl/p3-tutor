Context and memory: what an agent sees, keeps and looks up

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the model's context, in saved notes, or in a searchable library.

Recall

In the agent loop, what happens after the model asks for a tool? Who actually runs the tool, and what happens to the result?

Check your answer

The model only writes a request for the tool. Your program runs it, then sends the result back to the model in a new model call. This repeats until the model gives a final answer or a limit is hit. Today's question is what the model can see in each of those calls.

One step, one page of text 5 min

Start with the big idea: a language model has no memory of its own. Each time your program calls it, the model sees one block of text, reads it, and writes a reply. Nothing else reaches it.

That block of text is the context: "the set of tokens included when sampling from a large-language model" (Anthropic, Effective context engineering). A token is a small chunk of text, roughly a short word or part of a longer one. The context window is the maximum amount of context the model can handle in one call, and Anthropic describes it as the model's "working memory" (Anthropic, Context windows).

Think of it like a function in Python. The function can only use its arguments. It does not remember the last call. If you want it to know something, you pass it in. The context is the argument list of every model call.

What goes into that page

According to the same documentation, everything in the request counts toward the window:

  • the system prompt (your standing instructions to the model),
  • every earlier message in the conversation, including tool results and documents,
  • your tool definitions (the descriptions of what each tool does), and
  • the reply the model writes in this call.

This is why the history is not "remembered" but resent: on each turn the input contains "all previous conversation history plus the current user message" (Anthropic, Context windows). Your program does the resending.

A common mix-up

"The model remembers what I told it earlier in the chat." It feels that way because chat apps hide the resending. The truth: the model only "remembers" what your program puts back on the page. Delete a message from the history, and as far as the model is concerned, it never happened.

Check yourself

Your assistant told a student on Monday that the 3D printer needs a safety sign-off. On Tuesday the student starts a brand-new chat, and your program sends only the new question. What does the model know about Monday?

Show the answer

Nothing, unless your program sends Monday's facts again. The model has no storage between calls, so anything it needs must be on the page.

Why a bigger window is not the answer 4 min

Current Claude models have large windows; many hold up to 1M tokens (Anthropic, Context windows). So why not paste all the machine manuals into every call and be done? Two reasons: money, and quality.

Money: you pay for the page every time

Models are billed by tokens, and the input you send counts. Because the whole page is resent on each call, a large page in a looping agent is paid for again at every step. Techniques such as prompt caching change what you pay for repeated text, but "cached prompt prefixes still occupy the context window" (Anthropic, Context windows), so they lower the price rather than the size.

Here is an illustrative calculation (the numbers are made up to show the shape, not real prices). Say the manuals total 60,000 tokens and a request takes 5 loop steps. Pasting all the manuals means sending about 60,000 × 5 = 300,000 tokens of manual text. Pasting only the 3 relevant sections of 500 tokens each means about 1,500 × 5 = 7,500. That is a forty-fold difference for the same answer.

Quality: more text can make the model worse

The second reason is context rot: "as token count grows, accuracy and recall degrade" (Anthropic, Context windows). Anthropic's engineers treat context as a limited resource with diminishing returns, and aim for "the smallest set of high-signal tokens" that gets the job done (Anthropic, Effective context engineering). A computer-science way to say it: the window is like RAM, not a hard drive. Having more of it does not mean you should fill it.

Window sizes change with each model release, so check the current numbers in the provider's documentation before putting one in a design review.
A common mix-up

"If the window is huge, I can skip retrieval and notes." It is tempting because it removes work. But a huge window is still erased between calls (it holds only what you send), it costs more the fuller it gets, and recall drops as it fills. Curating what goes in matters as much as how much fits.

Check yourself

Your team proposes loading all 40 machine manuals into every request because the window is large enough. Which is the strongest objection?

Show the answer

You pay for the text at every step, and recall may drop as the context fills. Whether it fits is the wrong question.

What carries over from step to step 5 min

Inside a single request, the agent loop builds up history. Each step appends the model's tool request and the tool's result, then the whole list goes to the model again. The history is just a Python list that your program keeps growing and resends.

Left alone, this list only grows. Anthropic's context-engineering article describes three ways to keep it in check (Anthropic, Effective context engineering):

  • Clear old tool results. Once the assistant has used a calendar listing, it rarely needs the raw listing again. Removing it is described there as a lightweight form of compaction.
  • Compaction. Near the window limit, summarize the conversation and start a fresh window with that summary, keeping key decisions and dropping repeated detail.
  • Sub-agents. A helper agent does a messy search in its own clean window and returns only a condensed summary, often 1,000 to 2,000 tokens. Whether that pays off is a topic for a later lesson.

For a makerspace booking, a request is short, so you will probably not need compaction. Clearing or trimming big tool results (such as a whole week's calendar) is the cheap win to know about.

Predict before you read on

The assistant calls search_manuals and gets back 8,000 tokens of text. It uses 200 tokens of that to answer. If nothing is cleared, how much of that 8,000 will be on the page at later steps of the same request?

Check your answer

All 8,000. The result stays in the history and is resent at every later step. That is why tools should return only what is needed, and why the next section is about fetching small, relevant pieces.

What survives a closed session 5 min

Everything so far lives inside one request. A session here means one conversation with a student. When it ends, the history list is gone, and so is whatever the model "knew". For your assistant to know on Friday that a student passed laser cutter training on Monday, that fact must be written down somewhere outside the model and loaded back later.

This is memory in an agent: information stored outside the context window and put back on the page when needed. Anthropic calls one form structured note-taking: "the agent regularly writes notes persisted to memory outside of the context window" and reads them back later. Its examples are a to-do list or a NOTES.md file (Anthropic, Effective context engineering). You are using the same idea in this workspace: your tutor reads NOTES.md at the start of every session.

Two ways to save, for two kinds of fact

Kind of factExampleWhere it lives
Exact, structuredStudent ID 4821 passed laser cutter training on March 3A database or JSON file the program reads and writes
Loose, in wordsThis student prefers evening slots and works on woodA short notes file the model can read and update

For the exact facts, do not trust the model to remember them in prose. Have a tool such as get_training_status(student_id) read them from a database. That is cheaper, and a wrong training status is a safety problem, not a typo. Anthropic also documents a memory tool for letting the model store and look up notes itself; it is listed under Go further.

Saved memory also has risks: notes can go stale (training expires), and they may hold personal details. Decide what you store, for how long, and who may see it.

A student's equipment certification must be correct on every visit. Which design is safest?

Show the answer

Store it in a database and read it with a tool. Exact facts need exact storage that the program controls.

Finding the right page in a long manual 5 min

Manuals are the opposite of student records: large, mostly irrelevant to any one question, and rarely changed. You do not save them as notes, and you do not paste them in. You search them and bring back only the relevant pieces. That is retrieval: looking up the few pieces of text that answer the current question and adding them to the context.

How a typical retrieval system works

  1. Chunk each manual into pieces of a few hundred tokens, such as one section each.
  2. Index the chunks. One method turns each chunk into an embedding, a list of numbers that places text with similar meaning close together. Another is keyword matching, such as BM25, which scores chunks by shared words.
  3. Search when a question arrives: embed the question and find the nearest chunks, or match its keywords.
  4. Add the top few chunks to the context, and answer from them.

Keyword search catches exact strings that meaning-based search can miss, such as an error code like "E-204" or a model number. Meaning-based search catches paraphrases, such as "the cutter won't start" matching a section titled "Troubleshooting power faults". Combining both works better than either alone. Anthropic's tests of this approach, called contextual retrieval, reported the top-20 retrieval failure rate falling from 5.7% to 2.9% by combining embeddings with BM25 and adding a short context line to each chunk, and to 1.9% with reranking added; these are Anthropic's own measurements (Anthropic, Contextual Retrieval).

Two ways to wire retrieval into an agent

  • Before the model runs. Your program searches first and puts the results in the context. Simple and fast.
  • Just in time. The search is a tool, so the model decides when to call it and with which words, and can search again if the first results miss. Anthropic describes this as slower but more flexible, and says a mix of the two is often most effective (Anthropic, Effective context engineering).

Notice how this connects to the agent loop you already know: "search the manuals" is just another tool, and its result lands in the context like any tool result. Retrieval is memory for knowledge that does not change often; notes are memory for facts that change per student.

Check yourself

A student asks about error code "E-204" on the vinyl cutter. Which search is most likely to find the right manual section?

Show the answer

Keyword search finds exact strings like error codes. A hybrid of keyword and meaning-based search is usually best overall.

Worked example and your turn 4 min

Worked example

A student writes: "I want to cut 3 mm plywood on the laser cutter Friday afternoon. What settings, and can you book it?" Decide where each piece of information lives. Try each step before opening the answer.

Step 1: what is in the system prompt?

Try it, then reveal

The standing rules and tool definitions: you are the makerspace assistant, only book trained students, and the descriptions of get_training_status, search_manuals, check_calendar, book_slot. These are the same every call, so they are always on the page.

Step 2: how does it know the student is trained?

Try it, then reveal

Saved memory. The model calls get_training_status, and your program reads the database. One short result enters the context. Nothing about the student was "remembered" by the model.

Step 3: how does it find the plywood settings?

Try it, then reveal

Retrieval. The model calls search_manuals with "laser cutter 3 mm plywood settings". The index returns the top 3 chunks, about 1,500 tokens, not the whole 60,000-token manual.

Step 4: what happens to the calendar result?

Try it, then reveal

It enters the history after check_calendar. If it lists a whole week, it is wasteful at every later step. Better: make the tool return only Friday afternoon's open slots, or clear the result once the slot is chosen.

Step 5: what is saved when the session ends?

Try it, then reveal

The booking goes into the calendar database through book_slot. A short note such as "prefers afternoons" can go in a notes file. The chat history itself is not needed later, so it is dropped.

Your turn

A second student asks: "Which of the three 3D printers can print nylon, and am I certified on it? Book me one for Monday." Step 1 is given: the printers' specifications are in the manuals, and certification status is a per-student record.

Now do the rest: (2) Where does each fact come from, and by what tool? (3) What should the manual lookup return, and roughly how much? (4) What should the calendar tool return? (5) What is saved when the session ends?

Show a solution

2. Nylon capability comes from retrieval over the manuals through search_manuals. Certification comes from the saved record through get_training_status.

3. A few relevant chunks (the materials sections for each printer), not whole manuals, perhaps 1,000 to 2,000 tokens.

4. Only Monday's open slots for the chosen printer.

5. The booking, written to the calendar. Optionally a note on preferences. The history is discarded.

Summary 2 min

  • The model has no memory of its own: its context, the text your program sends on each call, is all it knows.
  • Within a request, history grows and is resent each step; a bigger window costs more and can hurt recall, so keep the context small and relevant.
  • Between sessions, only what your program saves survives: exact facts in a database, loose facts in notes.
  • For long manuals, retrieval brings back only the relevant chunks, ideally by combining keyword and meaning-based search.
